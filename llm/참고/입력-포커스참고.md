# 입력과 포커스 참고

입력칸, 키보드 핸들러, 자동완성, 포커스 이동을 만지기 전에 읽는 문서다. 클릭이 조용히 사라지거나 포커스가 `body`로 떨어지는 사고는 이 프로젝트에서 네 번 이상 재발했고, 원인은 모두 아래 몇 가지다.
각 항목은 규칙, 증상, 해결, 출처(일지) 순이다.

# 공용 부품

- `utils/focusNextElement.ts`: 문서 순서상 컨테이너 **뒤**에 오면서 컨테이너에 속하지 않는 첫 포커스 가능 요소로 이동. `compareDocumentPosition`으로 앞뒤를 가른다. 다음 칸을 ref로 엮지 않는 이유는 "마지막 칸에서 답안란으로"까지 같은 규칙으로 덮기 위해서다.
- `utils/focusFirstElement.ts`: 컨테이너 안의 첫 포커스 가능 요소. 선택자를 바꿔 쓸 수 있다(`explore/consts.ts`의 `ANSWER_INPUT_SELECTOR`는 라디오를 빼고 버튼을 넣는다. 라디오가 입력란보다 먼저 렌더되고, 범주형은 첫 선택지 버튼에 포커스가 가야 숫자키가 참고사항에 글자로 들어가지 않기 때문이다).
- `utils/consts.ts`의 `FOCUSABLE_SELECTOR`가 둘의 공통 선택자다. **readOnly input도 `input:not([disabled])`에 걸린다.** 표의 고정 헤더처럼 포커스가 닿으면 안 되는 칸은 `isEditable={false}` 입력칸이 아니라 input이 아닌 요소(`<strong>` 등)로 그린다. 그러지 않으면 `focusFirstElement`가 그 칸을 잡고, 입력칸을 평면 인덱스로 세는 코드(`MatrixField`의 `focusCell`)도 어긋난다.
  출처: [2026-08-31](../일지/2026-08-31-도구-일본어-매핑.md)
- `word/useSuggestionFocus.ts`: 입력칸 + 추천 목록을 한 포커스 단위로 묶는 훅. 컨테이너 `focusin`/`focusout` + `contains(relatedTarget)` 가드가 원형이며 5곳에서 동형 반복되어 추출됐다.
- `word/WordField`(공백 에코 + `onEnter`/`onArrowDown`/`onEmptyBackspace`/`onEscape`), `sentence/SentenceField`(`Tab` 삽입, `Ctrl+Enter`, `rows`/`textareaRef`)가 제어 입력칸의 원자다. 저장 버튼·중복 검사·추천기는 Field 밖(`WordWriter`)에 둔다. 대시보드는 기존 단어 저장을 막아야 하고 탐색은 기존 단어로 답하는 것이 정상이라 한 컴포넌트가 두 규칙을 만족할 수 없다.

# 클릭 소실: mousedown과 blur

- **요소가 blur에 반응해 움직이거나 사라지면 mouseup이 빗나가 click이 발화하지 않는다.** 토스트도 저장도 없는 무증상 실패다. 네 번 재발했다.
  1. 추천 항목 클릭 시 input blur가 click보다 먼저 와 목록이 언마운트됨 → `WordSuggestion` 루트에 `onMouseDown={preventDefault}`. Safari는 button 클릭 시 포커스를 옮기지 않아 `:focus-within` 방식은 깨진다.
  2. 마지막 칸 blur가 `flushSync`로 새 칸을 끼워 제출 버튼이 아래로 밀림 → 버튼 `onMouseDown`에서 `preventDefault`(`tools/ordering/OrderingTool.tsx`의 `keepFieldFocus`).
  3. 폼 전체에 `onFocus`/`onBlur`를 걸어 삭제 버튼 mousedown에 추천 목록이 열리며 버튼을 덮음 → 포커스 감지 범위를 입력칸 + 추천 목록만 감싸는 `div`로 좁힌다.
  4. playwright에서 추천 목록이 열린 채 제출 버튼을 클릭하면 같은 이유로 click이 안 난다 → 검증 스크립트는 다른 칸에 focus를 먼저 줘 목록을 닫고 클릭한다.
  출처: [2026-07-30](../일지/2026-07-30-단어-완성제안-포커스-연동.md), [2026-08-15 도구](../일지/2026-08-15-도구-페이지와-순서화.md), [2026-08-15 삭제 버튼](../일지/2026-08-15-개별-단어-페이지-삭제-버튼이-추천-목록에-가려짐.md), [2026-08-13](../일지/2026-08-13-관계-짓기-중복-제출-차단.md)
- **추천 목록은 조건부 마운트(`{isFocused && ...}`)가 아니라 `isVisible` prop으로 가시성을 내부화한다.** 목록 안의 모달(`WordReplaceDialog`)을 클릭하면 blur로 목록째 언마운트되어 모달이 사라진다.
  출처: [2026-08-05](../일지/2026-08-05-단어-수정삭제와-참조-교체.md)
- **입력 중 새 queryKey 로딩으로 목록이 언마운트되지 않게 `placeholderData: keepPreviousData`를 준다.** 100ms 스로틀 창에서 ArrowDown으로 진입하면 포커스가 `body`로 떨어진다.
  출처: [2026-08-07](../일지/2026-08-07-단어-입력기-화살표-키로-추천-목록-탐색.md)

# 포커스와 리마운트

- 값이 바뀌는 `select`/`input`에 값 자체를 `key`로 주면 바뀔 때마다 리마운트되어 포커스를 잃는다. 위치 기반 `key={index}`나 고정 키를 쓴다.
- 앞에 요소가 끼어드는 배열에서 키 없는 자식은 index 키가 밀려 리마운트된다. 라벨·추가용 `select`처럼 위치가 변하는 고정 요소에는 명시적 키를 둔다.
- 초안 상태(`useState`)를 URL 등 외부 값과 동기화할 때는 `useEffect(() => setDraft(value), [key])`(`QnaSearchForm`, `useRelationTypeDraft`) 또는 `key`로 리마운트(`RangeSearchForm`)한다. 리마운트는 다른 입력칸의 초안까지 날리므로 범위를 확인한다(`RecentListSection`의 `key={rangeKey}`에 필터 키를 섞지 않는 이유).
- 기존 일지의 React key 중복 경고 사례: 한 페이지에서 `SentenceWriter`와 `SentenceDocuments`가 둘 다 `key={sentenceId}`였다.

# 상태 갱신과 포커스 순서

- **`focus()`를 상태 갱신보다 먼저 부른다.** 리렌더로 목록이 언마운트되기 전에 포커스가 밖으로 나가야 갈 곳을 잃지 않는다. 초기화도 같다. `focusFirstElement` 먼저, `setWords(EmptyWords)` 나중. 반대로 하면 마지막 칸의 blur가 이전 `words` 클로저로 빈 칸을 하나 더 붙인다.
  출처: [2026-08-06](../일지/2026-08-06-대상-단어-칸의-키보드-흐름.md), [2026-08-15](../일지/2026-08-15-도구-페이지와-순서화.md)
- **새 칸을 추가한 직후 그 칸으로 포커스를 보내야 하면 `flushSync`로 DOM에 먼저 만든다.** 자식 `leaveField`의 `onFocusChange(false) → focusNextElement` 순서에서 새 칸이 DOM에 없으면 엉뚱한 곳으로 간다.
- **추천 선택 경로는 `onChange(value)` 직후 blur가 와서 부모의 배열이 stale하다.** 추가/삭제는 함수형 업데이트(`setWords(prev => ...)`)로 쓴다.
  출처: [2026-08-07](../일지/2026-08-07-알려주기-예문-단어-칸-동적-추가삭제.md)
- **제출 성공 후 입력란이 즉시 살아 있지 않으면(`refetch`로 언마운트) ref 플래그를 켜고 렌더 후 effect가 소비한다.** `useExplore`의 `isFocusPending`. 입력란이 리셋 전후로 언마운트되지 않으면 `onSuccess`에서 동기 `focus()`로 충분하다(`useRelationEditor`).
  출처: [2026-08-06 탐색](../일지/2026-08-06-탐색-제출-후-답안-입력란-포커스.md), [2026-08-06 관계](../일지/2026-08-06-관계-제출-후-첫-입력폼-포커스.md)
- **제출 경로가 여럿(form submit, 필드 `onSubmit`, 단축키)이면 포커스 복귀는 mutation `onSuccess` 한 곳에서 한다.** 모든 경로를 한 번에 덮는 유일한 지점이다.

# 키 이벤트

- **한글 조합 중의 Enter/Backspace/ESC/숫자키는 `nativeEvent.isComposing`으로 거른다.** 조합 확정이 이동·제출·삭제로 오인된다. 새 키 핸들러를 만들면 첫 줄이 이 가드다(`WordField`, `WordCard`, `SentenceCard`, `useChoiceShortcut`).
- **Backspace는 keydown에서 판정하고 keyup에서 실행한다.** 누르는 시점에 이미 빈 칸이어야 발화하므로 마지막 글자를 지운 release로는 삭제되지 않고, 홀드 반복으로 여러 칸이 지워지지 않는다(`extraction/computePendingBackspace.ts`, `WordField.onEmptyBackspace`).
- **화살표 이동은 keydown에서 `preventDefault` 후 즉시 실행한다.** 키 홀드 시 `repeat` keydown이 새 카드에서 이어져 연속 이동이 되고, 브라우저 기본 동작으로 캐럿이 먼저 튀는 것을 막는다. Backspace와 반대 선택인 이유가 다르다.
  출처: [2026-08-16](../일지/2026-08-16-문장-카드-화살표-키-이동.md)
- **Enter는 컨테이너 keydown이 아니라 `WordField`의 `onEnter` prop으로 받는다.** 컨테이너에서 가로채면 같은 컨테이너 안의 `WordReplaceDialog` 입력까지 Enter를 빼앗긴다. 대상 단어 칸의 Enter는 `leaveField`(다음 칸으로 이동)이고 제출이 아니다. 무응답 허용 유형에서 암묵 제출이 회피 관계를 적재하기 때문이다. 답안 확정 = 참고사항으로 이동, 제출 = 참고사항에서만.
  출처: [2026-08-06](../일지/2026-08-06-알려주기-페이지.md), [2026-08-13](../일지/2026-08-13-답안-확정-시-참고사항으로-포커스-이동-후-제출.md)
- **한 줄 문장 칸(문서 제목 `document/DocumentWriter/TitleField`)은 `WordField`를 감싸되 Enter를 `preventDefault`로 삼키고 `Ctrl+Enter`만 제출로 넘긴다.** `WordField`는 `onEnter`가 없으면 Enter를 무시하므로 `label > form` 안에서 폼 암묵 제출이 일어난다. 탭·개행은 `onChange`에서 `/[\t\r\n]/g`로 지워 붙여넣기까지 막는다. `Tab`은 가로채지 않는다.
  출처: [2026-08-30](../일지/2026-08-30-문서-제목-도입.md)
- **`Tab`은 문장·문서 입력기에서만 가로채 탭 문자를 넣는다(`writer/insertTabIfPressed.ts`).** `Shift+Tab`과 읽기 전용은 가로채지 않는다. 포커스가 갇히면 키보드로 폼을 못 나간다. 삽입은 `document.execCommand('insertText')`다. 값을 직접 만지면 실행취소 스택이 끊긴다. deprecated지만 `EditContext`는 아직 이르다.

- **전역 단축키(`useChoiceShortcut`)는 `checkIsTyping`으로 입력 중을 빼고, Enter는 선택지 내부나 `body`에 포커스가 있을 때만 가로챈다.** 건너뛰기 버튼의 Enter는 건너뛰기여야 한다.

# 자동완성

- 항목은 실제 `button`/`Link`이고 키보드 이동은 실제 DOM 포커스 이동이다. 가상 포커스(`aria-activedescendant`)를 쓰지 않는다. 버튼의 Enter는 브라우저가 click으로 바꿔 클릭과 한 경로가 된다.
- 마지막 항목의 ArrowDown은 첫 항목으로 순환하고, 첫 항목의 ArrowUp은 입력칸으로 복귀한다(순환하지 않는다). 순회 대상은 `'li > :first-child'`라 삭제(x) 버튼은 제외된다.
- `WordSuggestion`은 absolute(z-index 4)라 바로 아래 요소를 덮는 것이 정상이며, 그 요소에 `position`/`z-index`를 주면 안 된다.
- 존재 확인은 `isChecking = throttledValue !== value || isFetching` 동안 저장을 잠근다. 스로틀 창의 조회 결과는 이전 값에 대한 답이다.
  출처: [2026-08-07](../일지/2026-08-07-단어-입력기-화살표-키로-추천-목록-탐색.md), [2026-07-25](../일지/2026-07-25-WordWriter-존재-확인-전-저장-차단.md)
- **목록이 실제로 떠 있는지는 `suggestionRef.current !== null`로 판정한다.** `WordSuggestion`은 안 보일 조건이면 `return null`이라 ref가 null이 된다. 행렬 셀처럼 같은 키가 다른 이동과 겹칠 때 새 상태 없이 keydown 시점에 가릴 수 있다.
  출처: [2026-08-31](../일지/2026-08-31-태그-카드와-행렬-셀-단어-자동완성.md)
- **`WordField`는 `onKeyDown`을 먼저 부르고 `onArrowDown`을 별개 분기로 또 탄다.** 컨테이너가 `onKeyDown`에서 ArrowDown을 처리하면서 `onArrowDown`도 주면 이동이 이중 발화한다. 키 배분이 있는 곳(`MatrixCell`)은 `onArrowDown`을 쓰지 않고 자체 keydown에서 가른다.
  출처: [2026-08-31](../일지/2026-08-31-태그-카드와-행렬-셀-단어-자동완성.md)

# 카드 편집기

- 카드 목록은 불변 연결 리스트(`extraction/cardList.ts`)이고 카드 id가 React key다. 문장 카드(`textarea`, `\n\n\n` 분할)와 단어 카드(inline `input`, Enter 분할)가 `useCards`를 공유한다.
- 시각 행 판정과 캐럿 x는 `caretGeometry.ts`의 미러 `div` + `Range` 측정이다. keydown/keyup 캐럿 비교로는 두 번 틀렸다. 기본 동작이 캐럿을 먼저 옮기고, 문자 수로는 전각/반각 혼용에서 같은 열이 되지 않는다.
- 입력칸 높이를 내용에 맞추는 CSS는 `field-sizing: content`뿐이다. `textarea`는 치환 요소라 `height: max-content`는 `rows` 기준 높이만 주고 내용을 반영하지 않는다. 미지원 브라우저(Firefox)는 지원하지 않으며 JS 폴백(`scrollHeight` 측정)은 두지 않는다. 문서 입력기는 `min-height`를 하한으로 둔다.
