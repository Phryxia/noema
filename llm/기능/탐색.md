# 탐색

`/explore`. 시스템이 단어를 뽑아 문제를 내고, 사용자가 답하면 관계가 된다. 공통 헤더의 `탐색` 링크로 들어간다. 관계 유형의 정의와 제출 절차는 [관계](./관계.md)에 있다.

## 코드

- 디렉토리: `packages/client/src/explore/`
- 페이지: `routes/explore.tsx` -> `ExplorePage`(단어 수 확인과 조립) / `useExplore.ts`(상태·액션) / `ExploreForm`(문제·답안 렌더)
- 출제: `explore/pickQuestion.ts`(`{ status: 'ok' | 'noType' | 'noWord' }`), `word/getRandomWords.ts`
- 지시문: `explore/getQuestionPrompt.ts`. 유형별 주어진 것·답 종류·입력칸 수: `relation/questionSpecs.ts`의 `QuestionSpecs`(`isExplorable`로 출제 대상 결정, `ExploreQuestionTypes`는 `explore/consts.ts`에서 파생)
- 답안: `AnswerSection`, `TextWriterField`, `ChoiceGroup` + `useChoiceShortcut.ts`, `QuestionPrompt`, `QuestionTypeSelector`, `UsageWordCountControl`
- 제출: `explore/submitAnswer.ts`, `createAnswerWordIds.ts`, `createNewRelation.ts`(+test), `checkIsAnswerReady.ts`(+test), `getAnswerModes.ts`, `createSource.ts`
- 상수: `explore/consts.ts`(`MIN_WORD_COUNT`, localStorage 키, `ANSWER_INPUT_SELECTOR`, `SimilarityLevels`), `usageWordCountStorage.ts`
- 타입: `explore/types.ts`(`AnswerDraft`, `CommentDraft`)

## 사양

- 단어가 `MIN_WORD_COUNT`(10) 미만이면 `단어가 부족하여 문제를 생성할 수 없습니다`만 보인다.
- 문제는 저장하지 않는다. `{ type, wordIds }`만 들고 있다가 제출하면 관계가 된다. 건너뛰기는 어느 Store에도 쓰지 않는다.
- 최상단 체크박스로 출제 유형을 고른다. 상태는 localStorage `explore/checkedTypes`에 저장되고 다음 출제부터 적용된다. 단, 현재 문제가 없는 상태(`noType`/`noWord`)면 변경 즉시 재출제한다.
- 그 아래 숫자 입력으로 예문 만들기 단어 수를 정한다(기본 1, 1 이상 정수, 상한 없음, localStorage `explore/usageWordCount`). 보유 단어보다 크면 단어 부족 안내, 낮추면 즉시 재출제.
- 질문 표시: 지시문과 대상 단어를 가로 중앙 정렬. 답이 대상 단어 중 하나를 고르는 유형(삼항 격리)은 대상 단어를 따로 보이지 않는다. 생성 중 `aria-busy`. 지시문부터 답안란까지를 한 덩어리로 묶어 유형과 무관하게 같은 높이로 두고 남는 공간은 위아래로 나눈다.
- 답안란: 서술형은 단어/문장 모드 선택기 + Field(단어 설명·예문 만들기는 문장 고정, 속성·연상·삼항 합성은 단어 고정), 범주형은 `ChoiceGroup`(선택 primary, 미선택 secondary, 최초 미선택이라 제출 불가, 숫자키 `1`~`N`으로 선택). 삼항 합성은 단어 입력기 두 개를 `단어 1 + 단어 2`로 한 줄에. 출처 입력기는 없다. 출처는 제출 시 문제에서 자동으로 정해진다.
- 참고사항(`comment`)은 항상 펼쳐진 채 단어/문장으로 선택 입력, placeholder `(optional)`, 비면 `undefined`.
- 제출 키: 답안에서의 확정 입력(단어 Enter, 문장 Ctrl+Enter, 모드 라디오 Enter, 범주형에서 선택 후 Enter)은 참고사항 영역으로 포커스 이동이고, 제출은 참고사항 영역에서만 일어난다(라디오 Enter, 단어 Enter, 문장 Ctrl+Enter). 제출 버튼도 있다. 제출 직후 다음 문제가 범주형이면 첫 선택지 버튼으로 포커스를 되돌린다.
- 무응답: 예문 만들기·이항 공통점·이항 차이점만 빈 문자열 제출을 허용하며 `answer: null`로 적재한다. 나머지는 빈 답 불가, 회피는 건너뛰기.
- 제출할 수 없거나 loading/fetching 중이면 버튼 비활성. 삼항 합성 중복이면 `이미 있는 관계입니다` 토스트가 뜨고 문제는 남는다.
- 제출로 생긴 문장의 `source`는 `Harvest via NOEMA system exploration, rid=<relationId>`.

## 결정 근거와 제약

- **뽑힌 단어의 순서는 항상 무작위다.** 사람은 먼저 본 것에 끌리므로 순서가 고정되면 응답에 섞인다. `getRandomWords`가 커서 전진 때문에 정렬된 순서로 읽으므로 읽은 뒤 섞는다. 알려주기에는 적용하지 않는다.
- 출제기는 현재 무작위다. 강화학습 출제기(무의미한 "무관계" 재확인을 줄이는 것이 목적)는 구상 단계이며 별도 패키지로 재구성할 예정이다. 임베딩 실험 페이지는 2026-08-23에 제거됐다.
- 적용 시점을 `useRef`로 미루는 이유: `refetch()`는 그 시점의 `queryFn`을 즉시 실행해 직전 `setState` 값을 보지 못한다. "다음 출제부터 적용"은 현재 문제가 있을 때의 이야기이고, 문제가 없으면 다음 출제란 곧 지금이므로 즉시 재출제한다.
- `pickQuestion`이 `null` 대신 `status`를 돌려주는 이유: 유형을 안 골라 못 만든 것과 단어가 모자란 것은 사용자에게 할 말이 다르다.
- 답안 모드 유효성은 `getAnswerModes(type)` 하나를 화면과 `submitAnswer`가 함께 쓴다. 화면에서만 고정하면 저장 쪽이 옛 모드로 단어를 만들고, 저장에서만 막으면 화면과 결과가 어긋난다. `AnswerDraft.mode`는 유형과 무관하게 살아 있어 유형이 허용하지 않는 모드가 남을 수 있다.
- `AnswerDraft`(flat)와 `QuestionAnswer`(판별 유니온)는 축 복제가 아니다. flat 폼 상태는 입력 도중 유형을 바꿔도 값이 보존되게 하는 의도이고, 스펙이 상태를 해석한다. `checkIsAnswerReady`는 `default` 없는 `switch`라 kind가 늘면 컴파일러가 잡는다.
- 참고사항을 `details`로 접었다가 되돌린 이유: 접어두면 있는 줄 모른다.
- 답안 높이 통일의 실측: 범주형 82px, 서술형 단어 133px, 문장 306px. 기준은 선택기 한 줄이 더 붙는 서술형 문장 모드다. 문장 입력기 최소 높이는 탐색 안에서만 128px로 낮춰 덩어리를 348px(`calc(128px + 11rem)`)로 잡았다.
- 상한 없는 예문 단어 수로 3개 초과 단어 관계가 생길 수 있어 관계 수정 화면은 실제 단어 수만큼 칸을 보인다(`relation/resizeWords.ts`).

## 알려진 함정

- 유형 미선택 고착: `appliedTypes` ref를 갱신하는 경로가 건너뛰기·제출뿐이면 `noType` 화면에서 빠져나올 수 없다.
- 제출 후 포커스는 `refetch`로 `AnswerSection`이 언마운트되므로 ref 플래그 + effect로 미룬다. [입력-포커스참고](../참고/입력-포커스참고.md#상태-갱신과-포커스-순서).
- 숫자키·Enter 단축키와 입력 중·IME 충돌: [입력-포커스참고](../참고/입력-포커스참고.md#키-이벤트).
- 선택지·모드 선택기의 `width: fit-content`와 `margin-inline: auto`는 pico `[role=group]`에 진다. 감싸는 요소에 `justify-content: center`. [UI개발참고](../참고/UI개발참고.md#specificity-함정-가장-자주-터진다).
- 제출 절차의 트랜잭션 분리와 삼항 중복 차단: [저장개발참고](../참고/저장개발참고.md).
