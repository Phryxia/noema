# 개요

Indexed DB의 데이터 종류와 무관하게 적용되는 공통 사양을 서술한다.

- 상위문서: [기획](../기획.md)
- 개별 Store의 스키마는 [타입별 Store](../설계/저장-스토어.md)에 있다.

# 저장에 관하여

Indexed DB에 저장한다. DB 이름은 `noema`, 버전은 7이다. 타입별로 분리된 Store을 갖는다.

## Store 목록

| Store             | Key Path     | 자동 증가 |
| ----------------- | ------------ | --------- |
| `wordMeta`        | 없음         |           |
| `wordNodes`       | `nodeId`     | 쓰지 않음 |
| `recentWords`     | 없음         |           |
| `sentences`       | `sentenceId` | 씀        |
| `recentSentences` | 없음         |           |
| `documents`       | `documentId` | 씀        |
| `recentDocuments` | 없음         |           |
| `questions`       | `questionId` | 씀        |
| `relations`       | `relationId` | 씀        |
| `hourDelta`       | `beginDate`  | 쓰지 않음 |
| `hourAcc`         | `beginDate`  | 쓰지 않음 |
| `dayDelta`        | `beginDate`  | 쓰지 않음 |
| `dayAcc`          | `beginDate`  | 쓰지 않음 |
| `weekDelta`       | `beginDate`  | 쓰지 않음 |
| `weekAcc`         | `beginDate`  | 쓰지 않음 |

버전 1은 `relations`까지, 버전 2에서 통계용 6개 Store가 추가되었다. 스키마는 [대시보드 통계 구역](../설계/화면-대시보드-통계구역.md)에 있다.
`sentences`, `documents`의 `createdAt` 인덱스를 붙이는 과정에서 3, 4, 5를 소모했고,
버전 6에서 `wordNodes`에 같은 인덱스를 더했다. 경위는 [최근 목록 페이지의 커서 페이지네이션](../history/구현/저장.md)에 있다.
버전 7에서 `questions`가 추가되고 `relations`의 인덱스가 붙었다.

## 인덱스 목록

| Store       | 인덱스      | Key Path                          | 고유 |
| ----------- | ----------- | --------------------------------- | ---- |
| `sentences` | `createdAt` | `createdAt`                       | 아님 |
| `documents` | `createdAt` | `createdAt`                       | 아님 |
| `wordNodes` | `createdAt` | `createdAt`                       | 아님 |
| `questions` | `createdAt` | `createdAt`                       | 아님 |
| `relations` | `createdAt` | `createdAt`                       | 아님 |
| `relations` | `wordId`    | `wordId`                          | 아님 |
| `relations` | `wordIds`   | `wordIds` (`multiEntry`)          | 아님 |
| `relations` | `word1Id`   | `word1Id`                         | 아님 |
| `relations` | `word2Id`   | `word2Id`                         | 아님 |
| `relations` | `word3Id`   | `word3Id`                         | 아님 |
| `relations` | `answer`    | `['answer.type', 'answer.id']`    | 아님 |
| `relations` | `comment`   | `['comment.type', 'comment.id']`  | 아님 |

`wordNodes`의 `createdAt`은 단어인 노드에만 있다. Indexed DB는 Key Path가 `undefined`인 레코드를 인덱스에 넣지 않으므로,
이 인덱스는 저절로 단어 노드만 담는다. 중간 노드를 걸러내는 별도의 조건이 필요 없다.
`relations`의 인덱스들도 같은 성질을 쓴다. 관계는 유형마다 가진 필드가 다르므로, 각 인덱스가 그 유형만 저절로 담는다.
자세한 것은 [탐색 Store](../설계/저장-탐색.md)에 있다.

## 스키마 생성

`onupgradeneeded`에서 다음 규약을 따른다.

- 이 콜백은 이미 `versionchange` 트랜잭션 안이다. `event.target.transaction`을 쓰며, 별도 트랜잭션을 열지 않는다.
- `event.oldVersion`으로 분기한다. 0이면 최초 생성이다. 이후 버전을 추가할 때는 `break`가 없는 계단식 `switch`로 쌓아, 어느 버전에서 올라오든 순차 적용되게 한다.
- Store 생성과 초기값 주입을 같은 트랜잭션에서 끝낸다. 이것이 끝나기 전에는 다른 트랜잭션이 돌지 않으므로, 앱 코드는 카운터가 아직 없을 수도 있다는 분기를 가질 필요가 없다.
- **인덱스 보정은 `switch` 밖에서 버전과 무관하게 매번 돌린다.** 이미 있으면 건너뛰므로 몇 번을 타도 무해하다.
  버전 분기 안에 두면, 어떤 이유로든 그 분기를 건너뛴 채 버전만 올라간 DB가 생겼을 때 영영 인덱스가 붙지 않는다.
  버전 번호는 "무엇을 새로 만들지"를 정할 뿐이고, "있어야 할 것이 있는지"는 번호와 무관하게 확인한다.

최초 생성 시 넣을 초기값은 다음과 같다.

| Store             | 초기값                                               |
| ----------------- | ---------------------------------------------------- |
| `wordMeta`        | `trieNodeSize`는 1, `wordSize`는 0, `nextNodeId`는 1 |
| `wordNodes`       | 루트노드 `{ nodeId: 0, value: '', children: {} }`    |
| `recentWords`     | `next`는 0                                           |
| `recentSentences` | `next`는 0                                           |
| `recentDocuments` | `next`는 0                                           |

순환 큐의 `0` ~ `9`(또는 `0` ~ `3`) 칸은 미리 `null`로 채우지 않는다. `get` 결과가 `undefined`인 것과 `null`인 것을 똑같이 빈 칸으로 취급한다.

## 내보내기와 가져오기

전체 DB를 JSON 한 덩어리로 주고받는다. 항목 단위의 병합은 하지 않는다.

파일 형식은 `{ dbName, version, exportedAt, stores }`이며, `stores`는 Store 이름별 `{ key, value }` 배열이다.
Store 목록은 상수가 아니라 열려있는 연결의 `objectStoreNames`에서 얻는다. Store가 늘어도 백업 코드를 고칠 일이 없다.

- `Date`는 JSON에 담기면 문자열로 굳으므로 `{ "$date": ISO 문자열 }`로 감싸 내보내고, 가져올 때 되돌린다.
  `beginDate`처럼 Date가 키인 Store가 있어, 문자열로 굳으면 범위 조회가 조용히 깨진다.
- 가져오기는 `dbName`과 `version`이 현재와 같을 때만 허용한다. 다르면 거부하고 이유를 표시한다.
- 전체 Store를 범위로 하는 단일 `readwrite` 트랜잭션에서 전부 비우고 다시 채운다. 중간에 실패하면 트랜잭션째 되돌아간다.
- Key Path가 있는 Store는 `key`를 버리고 `put(value)`로 넣는다. 인라인 키가 값 안에 있어 ID가 보존되며,
  자동 증가 키 생성기도 넣은 키 이상으로 올라가므로 이후 발급되는 ID가 기존 항목과 겹치지 않는다.
- Key Path가 없는 Store만 `put(value, key)`로 넣는다.

## 연결 수명 주기

- `db.onversionchange`: 다른 탭이 버전을 올리려 하면 현재 연결을 닫는다. 그러지 않으면 그쪽이 영원히 `blocked`에 걸린다.
- `open` 요청의 `onblocked`: 다른 탭이 구버전 연결을 붙들고 있는 상황이다. 사용자에게 다른 탭을 닫으라고 알린다.
- 시크릿 모드나 저장소가 차단된 환경에서는 `open`이 실패할 수 있다. 이 경우 앱이 정상 동작하는 척 하지 말고 명시적으로 실패를 표시한다.

## 공통 규약

Store 이름과 Store 내부의 키는 전부 `camelCase`로 쓴다.

**ID**

- 모든 ID는 `number`다.
- `wordNodes`를 제외하면 Object Store의 자동 증가 키 생성기로 발급한다. 최초 ID는 1이며, 항목을 삭제해도 되돌아가지 않는다.
- ID를 비운 채 `add`하면 Key Path 자리에 발급된 ID가 채워진다. 발급된 값은 요청의 `result`로 얻으며, 순환 큐에 사본을 쓸 때 이 값이 필요하다.
- `wordNodes`의 `nodeId`만 예외로, `wordMeta.nextNodeId`에서 직접 발급한다. 루트노드가 0을 차지해야 하기 때문이다.
- 한 번 발급된 ID는 그 항목의 내용이 바뀌어도 불변이며, 같은 ID가 두 번 발급되는 일은 없다.
- 내용이 같아도 별개의 항목으로 취급한다. 내용을 근거로 한 중복 제거는 하지 않는다.

**날짜**

- 생성 시각은 `createdAt`, 마지막 수정 시각은 `modifiedAt`으로 통일한다.
- 수정이라는 개념이 없는 항목(관계)은 `createdAt`만 갖는다.
- 단어는 수정(개명)될 수 있으며, 수정된 적이 있을 때만 `modifiedAt`을 갖는다.
  수정은 ID를 유지한 갱신이 아니라 새 `nodeId` 발급과 참조 교체다. [단어 Store](../설계/저장-단어.md) 참고.

**트랜잭션**

- 하나의 조작이 여러 Store를 건드리면, 관련 Store 전부를 범위로 하는 단일 `readwrite` 트랜잭션에서 처리한다.
- 예를 들어 단어 1개를 추가하면 `wordMeta`, `wordNodes`, `recentWords`가 함께 바뀌므로 셋을 한 트랜잭션으로 묶는다.
- `nextNodeId`를 읽고 증가시키는 것도 같은 트랜잭션 안에서 한다.

**인덱스**

인덱스를 두는 이유는 둘이다.

- **커서 순회의 순서 자체가 그 인덱스여야 하는 경우.** `sentences`, `documents`, `wordNodes`의 `createdAt`이 그렇다.
  [최근 목록](./화면/최근-목록.md)이 날짜 범위를 잘라 내림차순 커서로 훑기 때문에, 이 순서를 Store가 직접 제공해야 한다.
  자동 증가 ID의 순서도 사실상 추가 시각 순이지만, 그 커서는 날짜 범위를 경계로 잡지 못해 범위 밖까지 훑게 된다.
  `wordNodes`는 사정이 더하다. `nodeId`의 순서는 노드가 생긴 순서라 단어가 추가된 순서와 다르고, 단어가 아닌 중간 노드까지 섞여 있다.
- **어떤 항목을 참조하는 것을 거슬러 찾아야 하는 경우.** `relations`가 그렇다.
  관계는 단어와 문장을 가리키기만 하고, 가리켜지는 쪽은 자신이 어디에 쓰였는지 모른다.
  역방향을 인덱스로 두지 않으면 매번 전수 스캔이 된다. 대상을 가리키는 필드에는 전부 인덱스를 둔다.

인덱스는 값을 넣고 뺄 때마다 갱신 비용을 치르므로, 위 두 이유에 해당하지 않으면 두지 않는다.
