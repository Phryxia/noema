# 2026-08-16 저장-탐색.md 스키마/절차 분리와 문서-문장 관계 문서 신설

## 문제

`DocumentToSentence` 관계를 더하면서 `설계/저장-탐색.md`의 `Relation` 유니온과 인덱스 표를 고쳐야 했는데, 이 문서는 이미 205줄이라
"직접 수정한 문서가 200줄을 넘으면 둘로 나눈다" 규칙에 걸렸다.

## 해결

- 시기가 아니라 성격으로 갈랐다. [탐색의 스키마](../설계/저장-탐색-스키마.md)(공용 타입·`questions`/`relations` 유니온·인덱스 표)와
  [탐색의 절차](../설계/저장-탐색-절차.md)(제출/수정/삭제 절차). 원본 `저장-탐색.md`는 목차와 "언제 어느 쪽을 보는지"만 남겼다.
  기존 링크는 모두 원본을 가리켜도 허브를 거쳐 도달한다.
- 스키마 문서에는 `RelationBase`/`WordRelationBase`/`WordRelation`/`Relation` 재편과 `documentId`/`sentenceId` 인덱스를 반영했다.
- 새 유형은 별도 문서 [문서-문장 관계 Store](../설계/저장-관계-문서문장.md)에 두었다. 탐색과 태생이 달라(문제 없음, 단일 트랜잭션 삽입) 섞이면 절차 설명이 갈라지기 때문이다.
- 화면 사양은 [문장 추출](../기획/화면/문장-추출.md)에 두고 [페이지](../기획/화면-페이지.md)에는 진입점과 관계표만 적었다.
  [저장 공통 규약](../기획/저장-공통.md)의 버전 이력과 인덱스 표도 10에 맞췄다(그동안 7에 멈춰 있었다).

# 2026-07-29 저장-탐색.md 신설

## 문제

[타입별 Store](../설계/저장-스토어.md)가 하위문서로 `설계/저장-관계.md`를 가리키고 있었으나 그 파일이 없었다.
남아 있던 내용도 폐기된 `labelNodeId`/`from`/`to` 스키마여서, 탐색 기획이 정의하는 `Relation`과 맞지 않았다.

또 [탐색 기획](../기획/탐색.md)의 타입 스케치에 구현으로 옮길 수 없는 오류가 있었다.

- `word1Id`, `word2Id`, `word3Id`가 `string`이었다. 저장 공통 규약의 "모든 ID는 `number`"와 어긋난다.
- `BinaryDifferenceQuestion`과 `BinarySimilarityQuestion`이 둘 다 `BinaryDifferenceQuestion`이라는 이름을 썼고,
  전자는 `type`까지 `'BinaryCommon'`이었다.
- 문제는 `wordsIds`, 관계는 `wordIds`로 같은 것을 다르게 불렀다.
- `Similarity`가 `enum`이었다. 이 프로젝트는 Eraseable Syntax 제약으로 `enum`을 쓸 수 없다.
- `TernaryIsolation`만 지시문이 없었다.

## 해결

사용자 판단으로 문서 이름을 `설계/저장-탐색.md`로 정했다. 담기는 것이 `relations`만이 아니라 `questions`도 있고,
둘 다 탐색 페이지 하나를 위해 존재하기 때문이다. 허브의 하위문서 링크를 이 경로로 고쳤다.

기획의 타입 스케치는 위 다섯 가지를 정정했다. `Similarity`는 리터럴 유니온으로 바꾸고,
값과 표시의 대응은 상수 배열로 둔다는 설명을 붙였다. `TernaryIsolation`의 지시문은
`다음 세 단어 중 가장 이질적인 단어를 고르세요.`로 새로 정했다.

[저장 공통 규약](../기획/저장-공통.md)의 인덱스 항목도 고쳤다. 경위는 [구현 기록](./구현/저장.md)에 있다.
참조 정리를 폐기하면서 [페이지 사양](../기획/화면-페이지.md)과 [재사용 컴포넌트](../기획/화면-컴포넌트.md)에서
"참조하던 `Relation` 비동기 삭제" 네 줄을 걷어냈다.

# 2026-07-22 구현 기록 계층별 분리

## 문제

대시보드 통계 구역 기록을 더하면서 `history/구현.md`가 227줄이 되어 200줄 상한을 넘었다.

## 해결

`history/구현/저장.md`와 `history/구현/화면.md`로 나눴다.
날짜로 자르면 대부분이 같은 날짜라 경계가 무의미하고, 다음에 또 넘칠 때 이름 붙일 곳이 없다.
반면 "Indexed DB 서비스 계층"과 "컴포넌트·CSS"는 찾는 이유 자체가 다르고, 앞으로도 이 축으로 계속 쌓인다.

원래 파일은 두 경로와 각각을 언제 보는지만 남긴 이정표가 됐다. 항목 목록은 각 문서의 개요로 옮겼다.
한 작업이 양쪽에 걸치면 무엇이 문제였는지를 기준으로 한쪽에만 적는다.
통계 구역은 화면도 만들었으나 어려웠던 것은 마이그레이션과 트랜잭션 순서라 저장 쪽에 있다.

# 2026-07-21 저장-스토어.md 관심사별 분리 및 설계 디렉토리 이동

## 문제

`기획/저장-스토어.md` 한 파일에 단어, 문장, 문서, 관계 네 타입의 Store 사양이 모두 있었다.
한 타입의 스키마를 확인하려고 다른 타입의 사양까지 읽어야 했다.
또한 이 문서는 Store 스키마와 조작 절차라는 구현 설계를 다루므로, 기획보다 설계에 속한다.

## 해결

새 디렉토리 `설계/`를 만들고 타입별로 네 문서로 나눴다. 언어적 내용은 바꾸지 않았다.

- [타입별 Store](../설계/저장-스토어.md): 허브. 상위/하위 링크만 갖는다.
- [단어 Store](../설계/저장-단어.md): `wordMeta`, `wordNodes`, `recentWords`
- [문장 Store](../설계/저장-문장.md): `sentences`, `recentSentences`
- [문서 Store](../설계/저장-문서.md): `documents`, `recentDocuments`
- [관계 Store](../설계/저장-관계.md): `relations`

문장과 문서 문서는 순환 큐 규약을 각각 단어, 문장 문서에서 빌려 쓰므로, 초입에 해당 문서로의 링크를 추가했다.
`기획.md`, `저장-공통.md`, `화면-컴포넌트.md`, `화면-페이지.md`와 본 문서의 기존 링크를 새 경로로 고쳤다.
원본 `기획/저장-스토어.md`는 삭제했다.

# 2026-07-21 기획.md "저장에 관하여" 보강

## 문제

`기획.md`의 저장 사양이 구현에 들어가기에는 구멍이 많았다. 크게 두 종류였다.

**모순과 불일치**

- Store 이름이 `wordMeta`, `wordNodes`(camel)와 `recent_words`(snake)로 섞여 있었고, 본문에는 `words_nodes`라는 오타가 있었다.
- `trie_node_size`를 "기록된 단어의 수"라고 정의해놓고 `nodeId` 발급 카운터로 쓰고 있었다. 단어를 삭제하며 이 값을 줄이면 ID가 충돌한다.
- `relations`의 Key Path가 `relationId`인데 `interface Relation`에 그 필드가 없었다.
- `Relation.from/to`가 `nodeId: number`인데 `type`은 sentence와 document까지 받았다. 이들은 `Uint8Array` UUID였으므로 타입이 맞지 않았다. 또 "관계가 관계를 연관지을 수도 있다"고 써놓고 `type`에 `'relation'`이 없었다.
- 날짜 필드가 `Sentence.date`와 `Document.createdAt`으로 갈렸다.

**누락**

- DB 이름, 버전, `onupgradeneeded` 규약이 통째로 없었다.
- 인덱스 정의가 없었다. 여러 곳에 적힌 "참조하던 Relation 전부 제거"를 어떻게 수행할지 알 수 없었다.
- 메인 페이지가 최근 문장 4개와 문서 4개를 요구하는데, 단어와 달리 이를 얻을 경로가 없었다.
- UUID v5는 (namespace, name) 쌍이 있어야 결정되는데 그 정의가 없었다. 더 큰 문제로, 내용이 바뀌면 ID도 바뀌는데 그게 Key Path였다. 수정이 곧 ID 변경이 되어 참조 관계가 깨진다.
- 단어 삭제 시 Trie 노드를 어떻게 정리하는지, 단어 문자열과 `nodeId`를 어떻게 오가는지 없었다.
- 여러 Store를 함께 건드리는 조작의 트랜잭션 범위가 없었다.

## 해결

사용자 판단을 받아 다음과 같이 정했다.

**UUID를 버리고 ID를 전부 `number`로 통일했다.** 이것이 가장 큰 변경이다. UUID v5는 내용 기반 중복 제거를 공짜로 주지만, 그 대가로 수정할 때마다 ID가 바뀐다. 노에마는 항목 자체보다 항목 사이의 관계가 핵심 가치이므로, 관계의 양 끝이 수정 한 번에 무효화되는 것은 받아들일 수 없었다. ID를 내용과 분리해 불변으로 만들고, 내용적 중복은 그냥 허용하기로 했다.

**ID 발급은 IndexedDB의 자동 증가 키 생성기에 맡겼다.** 직접 카운터를 관리하면 그것 자체가 트랜잭션 경합의 대상이 된다. 다만 `wordNodes`만 예외로 `wordMeta.nextNodeId`에서 발급하는데, Trie 루트노드가 `nodeId` 0을 차지해야 하기 때문이다. 자동 증가는 1부터 시작하므로 0을 쓸 수 없다.

**인덱스를 두지 않고 `relations` 전수 스캔으로 간다.** 삭제 시 참조 정리는 `labelNodeId`, `from`, `to` 세 곳을 다 봐야 해서 인덱스가 최소 3개 필요하다. 데이터가 얼마나 쌓일지 모르는 시점에 그 비용을 미리 내지 않기로 했다. 최적화는 실제로 느려진 다음에 한다.

**최근 문장/문서도 단어와 같은 순환 큐로 만들었다.** 날짜 인덱스에 역방향 커서를 쓰는 방법이 더 정석이지만, 인덱스를 두지 않기로 한 이상 기존 `recentWords` 방식을 그대로 확장하는 편이 일관적이다. `recentDocuments`는 문서 전체가 아니라 초입 64글자만 `preview`로 들고 있는다. 페이지가 그만큼만 쓰기 때문이다.

**단어 삭제는 가지치기로 정했다.** 노드의 `createdAt`을 지운 뒤, 자식도 없고 `createdAt`도 없는 노드를 부모 방향으로 거슬러 올라가며 제거한다. tombstone으로 두면 삭제를 반복할수록 Trie에 죽은 노드가 쌓인다.

이 밖에 `Relation.from/to`를 `RelationEnd` 타입으로 분리하며 필드명을 `nodeId`에서 `id`로 바꿨다. `type`이 `'sentence'`인데 `nodeId`라고 부르면 오해를 부른다.

## 남은 것

- 데이터 영속성(`navigator.storage.persist()`)과 백업/내보내기 규약. 별도 세션에서 다루기로 했다.
- `기획.md`가 380줄을 넘어 `CLAUDE.md`의 200줄 분할 규칙 대상이 되었다. 구현 관련 내용을 별도 문서로 빼는 작업을 새 세션에서 하기로 하고, 이번에는 분리하지 않았다.

# 2026-07-21 화면.md 재분리

## 문제

[화면 사양](../기획/화면.md)이 122줄로 분할 규칙(200줄) 대상은 아니었으나, 사용자가 더 쪼개라고 요청했다.

## 해결

내용을 바꾸지 않고 문서의 두 절을 그대로 둘로 나눴다. 경계는 원래부터 있던 최상위 헤딩이다.

- [재사용 컴포넌트](../기획/화면-컴포넌트.md): 고정폭 폰트 규칙과 입력기/추천기 4종
- [페이지 사양](../기획/화면-페이지.md): 메인과 개별 단어/문장/문서 페이지

`기획.md`의 허브 목록은 두 새 문서를 직접 가리키도록 바꿨다. 중간 허브를 두지 않는 기존 결정과 같은 이유다.
다만 `화면.md`는 지우지 않고 두 문서를 가리키는 이정표로 남겼다. 이 history를 포함해 옛 경로로 걸린 링크가 있기 때문이다.

이후 사용자 피드백에 따라, 기획 하위 네 문서의 개요에서 "어디에서 분리됐다"는 역사 서술을 전부 지우고
상위문서/하위문서 링크만 남기는 형식으로 통일했다. 디렉토리 구조와 링크가 유래를 이미 함의하기 때문이다.
역사는 history에만 적는다.

원본에 있던 두 가지 이상한 점은 수정하지 않고 그대로 옮겼다.

- 메인 페이지의 `WriterSection`에서 `DocumentWriter`의 조건이 `문장`으로 적혀 있던 오타는 사용자가 직접 수정했다.
- 개별 단어 페이지의 마지막 항목 "값은 수정돼 있는데 수정 버튼을 누르지 않은 경우"가 뒷내용 없이 끊겨 있다. 사용자 확인이 필요하다.

# 2026-07-21 기획.md 구현 사양 분리

## 문제

`기획.md`가 396줄로 `CLAUDE.md`의 200줄 분할 규칙에 걸렸다.
전체의 87%인 51~396줄이 Indexed DB 스키마와 컴포넌트 사양 같은 구현 세부였고,
동기와 데이터 개념 정의 같은 기획 본체는 앞의 49줄뿐이었다.
구현 사양 한 줄을 확인하려고 문서 전체를 읽어야 하는 상태였다.

## 해결

내용을 한 글자도 바꾸지 않고 세 문서로 옮겼다. 헤딩 레벨만 독립 문서에 맞게 한 단계씩 올렸다.

- [저장 공통 규약](../기획/저장-공통.md): 원본 51~122줄. DB 설정, 스키마 생성, 연결 수명 주기, 공통 규약.
- [타입별 Store](../설계/저장-스토어.md): 원본 124~281줄. 단어, 문장, 문서, 관계 각각의 Store.
- [화면 사양](../기획/화면.md): 원본 283~396줄. 재사용 컴포넌트와 페이지.

**"저장에 관하여"를 다시 둘로 쪼갠 이유.** 이 절만 231줄이라 통째로 빼면 그 자체가 다시 분할 규칙 대상이 된다.
경계는 데이터 타입 의존성으로 정했다. 앞쪽 절반은 어떤 데이터를 다루든 항상 적용되는 규약이고,
뒤쪽 절반은 특정 타입을 건드릴 때만 필요하다. 문장을 저장하는 코드를 쓰는 사람은 Trie 가지치기를 읽을 필요가 없다.

**허브를 3단계로 만들지 않았다.** `기획.md` → `저장.md` → `저장-공통.md`처럼 중간 허브를 두는 대신
세 문서를 평평하게 두고 `기획.md`가 직접 링크한다. 링크 한 번 더 타는 비용이 분류의 이득보다 크다.
대신 각 링크마다 단어 몇 개짜리 요약을 붙여, 목적지를 열어보지 않고도 고를 수 있게 했다.

역방향 링크도 걸었다. 세 문서 모두 초입에 원본이 `기획.md`임을 밝히고,
저장 문서 둘은 서로를, 화면 문서는 `저장-스토어.md`를 가리킨다. 컴포넌트가 읽고 쓰는 스키마가 거기 있기 때문이다.

문서 간 링크는 전부 `[제목](./상대경로)` 형태의 마크다운 링크로 쓴다. 절대경로 문자열은 쓰지 않는다.

이 작업으로 이전 항목의 "남은 것" 중 분할 건은 해소되었다. 영속성 규약은 그대로 남아 [plan](../plan.md)으로 옮겼다.
