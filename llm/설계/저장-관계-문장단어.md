# 문장-단어 관계의 경우

- 상위문서: [타입별 Store](./저장-스토어.md)
- 형제 유형인 `DocumentToSentence`는 [문서-문장 관계 Store](./저장-관계-문서문장.md)에 있다.
- 만드는 화면은 [단어 추출](../기획/화면/단어-추출.md)이다.

`SentenceToWord`는 문장 하나에서 단어 하나가 추출되었음을 뜻한다. 별도 Store 없이 `relations`에 다른 관계와 함께 저장되며,
`relationId`를 공유하므로 개별 관계 화면 `/relation/<id>`를 같이 쓴다.

## 타입

```ts
interface SentenceToWordRelation extends RelationBase {
  type: 'SentenceToWord'
  sentenceId: number
  wordId: number
}

type Relation = WordRelation | DocumentToSentenceRelation | SentenceToWordRelation
```

`questionId`도 `comment`도 없다. 문제에서 태어난 관계가 아니기 때문이다.

단어 관계가 **아닌** 유형이 둘이 되면서, `type !== 'DocumentToSentence'` 식의 판정은 전부
`relation/consts.ts`의 `NonWordRelationTypes` 집합을 보는 `checkIsWordRelation` 하나로 모았다.
`deleteRelation`의 스토어 범위와 `questions` 삭제도 이 함수를 쓴다.

## 인덱스

**새 인덱스도 `DB_VERSION` 상승도 없다.** `relations`의 `wordId`(원래 `WordExplain`용)와 `sentenceId`(원래 `DocumentToSentence`용)를 그대로 탄다.
같은 인덱스를 두 유형이 나눠 쓰게 되므로, 인덱스로 긁은 뒤 `type`으로 거르는 책임이 조회 쪽에 생긴다.

- `d2s.service`는 `sentenceId` 인덱스 결과를 `DocumentToSentence`로 거른다. 안 하면 개별 문장 페이지의 `연결된 문서`에 단어 관계가 샌다.
- `s2w.service`는 같은 인덱스 결과를 `SentenceToWord`로 거른다.
- 결과는 기본키(`relationId`) 오름차순 = 삽입 순서 = 문장 내 단어 순서라 따로 정렬하지 않는다.

`wordId` 인덱스를 공유한 대가가 아니라 이득도 있다. 단어 인덱스만 훑는 기존 코드가 이 유형을 자동으로 포함한다.

- `hasWordReferences`/`countReferencingRelations`가 세므로, 추출된 단어를 지우려 하면 `WordReplaceDialog`가 대체 단어를 요구한다.
- `replaceWordReferences`가 `wordId` 필드를 바꾸므로, 단어 개명·대체가 이 관계를 따라온다. 타입을 `Relation`으로 넓히고 `comment` 접근에 `in` 가드를 뒀다.

## 삽입 절차

`submitWordExtraction(sentenceId, values)`

1. 빈 값을 버리고(`trim`은 하지 않는다) `Set`으로 순서를 지키며 중복을 없앤다. 남은 게 없으면 throw.
2. `createdAt`을 한 번 찍는다. 단어와 관계가 이 하나를 공유한다.
3. `[wordMeta, wordNodes, recentWords, relations]`를 범위로 하는 하나의 `readwrite` 트랜잭션을 연다.
4. 값마다 `addWord`(단어 Store의 트랜잭션 스코프 헬퍼)로 Trie에 넣고 `{ nodeId, isCreated }`를 받아
   `{ type: 'SentenceToWord', sentenceId, wordId: nodeId, createdAt }`을 `relations.add`한다.
   `isCreated`가 참이면 결과가 `성공`, 거짓이면 `중복`이다.
5. 값 하나의 예외는 `try`/`catch`로 잡아 결과에만 `실패`로 적고 요청을 내보내지 않는다. 요청을 내보내면 트랜잭션 전체가 죽는다.
6. 커밋 후 `recordCreation(db, 'wordCount', 새로 만든 수)`, `recordCreation(db, 'relationCount', 만든 관계 수)`.

`addWord`는 `createWord`의 몸통을 뽑은 것이다. `createWord`는 트랜잭션을 열고 이 헬퍼를 값 1개로 부른 뒤 통계를 기록한다.
`isCreated`가 없던 시절의 `createWord`는 기존 단어를 만나면 통계를 건너뛰려고 같은 판정을 인라인으로 하고 있었다.

## 목록

- 관계 목록 `/relations`가 유형을 거르지 않으므로 그대로 나타난다. 유형 라벨은 `단어 추출`(`S2W_TYPE_LABEL`).
- 대표 표현은 `DocumentToSentence`가 쓰던 `extraction` 토큰을 일반화해 나눠 쓴다.
  토큰이 `{ child, parent }` 두 참조를 들고, `child` 영역 70% + `from parent` 영역 30%로 그린다.
  `DocumentToSentence`는 (문장, 문서), `SentenceToWord`는 (단어, 문장)이다.
- 개별 관계 화면도 `PairRelationPage`(메타 + 라벨된 참조 두 줄 + 삭제)를 `D2sRelationPage`와 나눠 쓴다.
- 개별 문장 화면의 `연관 단어` 표는 `PairTable`(`D2sTable`을 일반화한 것)에 단어 열만 남긴 것이다.
- 개별 단어 화면의 `단어를 추출한 문장` 표는 같은 `S2wTable`에 문장 열만 남긴 것이다(`wordId` 인덱스, `getSentenceToWordRelationsByWord`).
- 관계 검색(`qnaSearch.service`)의 전수 조회는 `checkIsWordRelation`으로 이 유형을 걸러낸다.

## 수정과 삭제

- 관계 수정은 없다.
- 관계 삭제는 `relations`만 지운다. `questions`에 짝이 없다. 문장과 단어는 그대로 둔다.
- 문장을 수정하면 개별 문장 화면의 관계 영향 질의 건수에 이 관계가 들어간다(`sentenceId` 인덱스).
  문장을 삭제해도 관계는 남으며 목록에서 `(삭제됨)`으로 보인다.
- 단어 수정·삭제는 위의 _인덱스_ 절대로 이 관계를 따라온다. 문서-문장 관계와 다른 점이다.
