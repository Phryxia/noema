# 저장 개발 참고

Indexed DB, 마이그레이션, 백업, 단어 Trie를 만지기 전에 읽는 문서다. 이 프로젝트의 저장 계층에서 반복해서 부딪힌 규칙과 함정을 모았다.
각 항목은 규칙, 증상, 해결, 출처(일지) 순이다. Store와 인덱스의 목록은 `db/consts.ts`, `db/indexSpecs.ts`, `db/openNoemaDB.ts`가 진실이며 여기에 베끼지 않는다.

# 트랜잭션

- **트랜잭션 안에서 IDB 요청이 아닌 Promise를 `await`하면 트랜잭션이 자동 커밋된다.** `awaitRequest`(`db/utils.ts`)로 감싼 IDB 요청은 마이크로태스크라 살아 있지만, `openNoemaDB()`·다른 트랜잭션·`fetch` 등을 기다리는 순간 대기 요청이 없어져 커밋되고 이후 요청은 `TransactionInactiveError`로 죽는다.
  헬퍼는 열린 `IDBTransaction`을 인자로 받고 자기 트랜잭션을 열지 않는 형태(`word/wordTx.ts`, `sentence/sentenceTx.ts`)로 쓴다.
  출처: [2026-07-21](../일지/2026-07-21-대시보드-단어-컴포넌트와-로직-구현.md), [2026-08-05](../일지/2026-08-05-단어-수정삭제와-참조-교체.md)
- **같은 이유로 "관계 id를 먼저 받고 문장을 만든 뒤 관계를 완성"하는 제출은 한 트랜잭션으로 묶이지 않는다.** `explore/submitAnswer.ts`가 예약 `add` → 문장 생성 → `put`으로 트랜잭션을 나누는 것은 비효율이 아니라 제약이다. 반대로 외부 대기가 없는 일괄 삽입(`extraction/submitExtraction.ts`, `submitWordExtraction.ts`, `tag/submitTags.ts`)은 한 트랜잭션에 같은 `createdAt`으로 넣는다.
  출처: [2026-07-29](../일지/2026-07-29-탐색-답안-문장의-출처.md), [2026-08-16](../일지/2026-08-16-문서문장-관계DocumentToSentence-신설.md)
- **한 트랜잭션 안에서 항목별 예외는 `try`/`catch`로 삼키고 결과에만 적는다.** 실패한 요청을 그대로 내보내면 트랜잭션 전체가 abort되어 앞서 넣은 항목까지 잃는다(`submitWordExtraction`).
  출처: [2026-08-16](../일지/2026-08-16-문장단어-관계SentenceToWord-신설.md)
- **통계 기록(`recordCreation`)은 동기 함수여야 한다.** 호출 즉시 `readwrite` 트랜잭션을 열고 쓰기는 `void`로 흘린다. `async`로 두면 `openNoemaDB()`를 기다리는 사이 `invalidateQueries`가 띄운 조회 트랜잭션이 먼저 열려 방금 넣은 값이 안 보인다. IDB는 범위가 겹치는 트랜잭션을 생성 순서대로 실행하므로 생성 순서만 확정하면 된다.
  출처: [2026-07-22](../일지/2026-07-22-대시보드-통계-구역.md)
- **`void`로 흘린 `async` 백필이 `versionchange` 트랜잭션 안에서 순서를 보장받는 이유**는 첫 `await`가 `openCursor`를 동기적으로 건 뒤에 오기 때문이다. 첫 `await` 앞에 IDB 요청이 없으면 이 보장이 깨진다(`db/countLog/backfill.ts`).
  출처: [2026-07-23](../일지/2026-07-23-통계와-총-보유의-불일치-제거.md)
- **커서 콜백 안에서 다른 Store의 `get`을 섞지 않는다.** 커서 순회 중 트랜잭션이 죽을 수 있다. 한 페이지를 다 읽은 뒤 새 트랜잭션에서 후처리한다(`RecentSource.hydrate`).
  출처: [2026-07-23](../일지/2026-07-23-최근에-추가된-단어-목록.md)
- **대용량 Store는 `getAll` 대신 커서로 순회한다.** 문서 본문이 통째로 메모리에 오른다. 존재 확인은 `get`이 아니라 `count(key)`다. `get`은 본문까지 읽는다.
  출처: [2026-07-23](../일지/2026-07-23-통계와-총-보유의-불일치-제거.md)

# 인덱스

- **Key Path가 `undefined`인 레코드는 인덱스에 들어가지 않는다.** 이것이 유형별 분리의 기본 수단이다. `wordNodes.createdAt` 인덱스가 중간 노드를 빼고 단어 노드만 담는 것, 단어를 지울 때 `createdAt`을 지우는 것만으로 인덱스에서 빠지는 것이 이 성질이다.
  출처: [2026-07-23](../일지/2026-07-23-최근에-추가된-단어-목록.md), [2026-07-29](../일지/2026-07-29-탐색용-문제관계-저장.md)
- **`relations`의 `wordId`·`sentenceId`·`documentId` 인덱스는 여러 유형이 공유한다.** `WordExplain`·`SentenceToWord`·`Tag`가 `wordId`를, `DocumentToSentence`·`SentenceToWord`·`Tag`가 `sentenceId`를 탄다. 인덱스 조회 결과는 반드시 `type`으로 거른다. 빼먹으면 개별 문장 페이지의 `연결된 문서`에 단어 관계가 새는 식으로 다른 유형이 섞여 나온다. 어느 유형이 어느 필드를 갖는지는 `relation/types.ts`에서 확인한다.
  공유의 이득도 있다. `hasWordReferences`·`replaceWordReferences`가 새 유형을 자동으로 포함해 개명·대체·삭제 게이트가 따라온다.
  출처: [2026-08-16](../일지/2026-08-16-문장단어-관계SentenceToWord-신설.md), [2026-08-17](../일지/2026-08-17-태그-관계와-태그-입력기.md)
- **"단어 관계가 아니다"를 `type !== 'DocumentToSentence'` 같은 리터럴 비교로 쓰지 않는다.** 유형이 하나 늘 때마다 전부 틀린 코드가 된다. `relation/consts.ts`의 `NonWordRelationTypes` 집합을 보는 `checkIsWordRelation` 하나만 쓴다.
  출처: [2026-08-16](../일지/2026-08-16-문장에서-단어-반자동-추출.md)
- **인덱스는 "커서 순회의 순서"이거나 "참조를 거슬러 찾기"일 때만 둔다.** 단순 조회 가속용 인덱스는 두지 않는다. 새 관계 유형은 기존 인덱스를 공유해 DB 버전을 올리지 않는 것이 먼저다(연상, 속성, 삼항 합성, 관계 짓기, 문장-단어, 태그 전부 무변경).
  출처: [2026-07-29](../일지/2026-07-29-탐색용-문제관계-저장.md), [2026-08-09](../일지/2026-08-09-연상-문제-유형-신설.md)
- **커서 `advance(n)`은 인덱스 레코드 수와 표 행 수가 같을 때만 맞다.** 그래서 `RecentSource.toEntry`는 `null`을 돌려줄 수 없다. 행을 걸러야 하면 `RecentFilter`를 넘기고, 그 경우 `getRecentPage`는 offset 점프 대신 처음부터 걸으며 통과 행을 센다(`recent/createRowJudge.ts`). `advance(0)`은 예외를 던진다.
  출처: [2026-08-19](../일지/2026-08-19-목록-페이징-상태를-query-string으로.md), [2026-08-20](../일지/2026-08-20-관계-유형-필터-포함-유형.md)
- **같은 `createdAt`이 여럿일 수 있어 다음 페이지 점프는 `continuePrimaryKey(createdAt, id)`다.** `continue(key)`로는 같은 시각 무리의 어디부터인지 지정할 수 없다.
  출처: [2026-07-23](../일지/2026-07-23-최근-목록-페이지의-커서-페이지네이션.md)
- **무작위 단어는 `getAllKeys`가 아니라 정렬한 순번으로 커서를 `advance`한다.** 단어가 수만 개면 매 출제마다 전부 읽게 된다. 정렬 때문에 뽑힌 순서가 추가 시각 순이 되므로 읽은 뒤 Fisher-Yates로 섞는다(`word/getRandomWords.ts`). 탐색에서만 섞고 알려주기는 입력 순서를 보존한다.
  출처: [2026-07-29](../일지/2026-07-29-탐색용-문제관계-저장.md), [2026-07-29](../일지/2026-07-29-탐색-페이지.md)

# 마이그레이션

- **개발서버가 켜진 채 `DB_VERSION`을 먼저 저장하면 그 번호는 영구히 소모된다.** HMR이 중간 상태를 실행해 마이그레이션 코드 없이 버전만 올라간 DB가 브라우저에 남고, `onupgradeneeded`는 다시 불리지 않는다. v3, v4, v8이 이렇게 소모됐다. 편집 순서는 마이그레이션 코드와 `indexSpecs.ts`를 먼저, `db/consts.ts`의 `DB_VERSION`을 마지막에 저장한다. 확신이 없으면 사용자에게 개발서버 종료를 먼저 요청한다. 버전 번호만 보고 마이그레이션을 걸 때는 그 번호가 이미 불완전하게 소모된 번호인지 확인한다. `openNoemaDB.ts`의 `RELATION_COUNT_VERSION = 9`가 8이 아닌 것이 그 흔적이다.
  출처: [2026-07-23](../일지/2026-07-23-최근-목록-페이지의-커서-페이지네이션.md), [2026-07-31](../일지/2026-07-31-대시보드-통계에-문답-추가.md)
- **버전 분기(`switch (event.oldVersion)`)는 "무엇을 새로 만들지"만 정한다. "있어야 할 것이 있는지"는 분기 밖에서 매번 확인한다.** `ensureIndexes`가 `indexNames.contains`로 멱등하게 보정하는 이유다. 분기 안에 두면 분기를 건너뛴 채 버전만 오른 DB가 영영 복구되지 않는다. Store 보정도 같은 원칙이다.
  출처: [2026-07-23](../일지/2026-07-23-최근-목록-페이지의-커서-페이지네이션.md), [2026-07-29](../일지/2026-07-29-탐색용-문제관계-저장.md)
- **`onupgradeneeded` 안에서는 `request.transaction`만 쓴다.** 별도 트랜잭션을 열거나 `openNoemaDB()`를 기다리지 않는다.
- **새 유형의 노출(라벨·옵션 등록)은 마지막에 저장한다.** HMR 중간 상태에서 미완성 유형이 출제되거나 저장되는 것을 막는다.
  출처: [2026-08-09](../일지/2026-08-09-연상-문제-유형-신설.md), [2026-08-13](../일지/2026-08-13-관계-짓기NamedAssociation-유형-신설.md)
- **조회 실패를 "결과 없음"으로 위장하지 않는다.** `useQuery`의 `error`를 무시하면 인덱스 부재가 빈 목록으로 보이고 기본 retry 3회로 로딩이 길어진다. 저장 계층 쿼리는 `retry: false`와 에러 문구를 둔다. `getRecentPage`는 커서를 열기 전에 인덱스 유무를 확인해 DB 버전을 담은 문구로 던진다.
  출처: [2026-07-23](../일지/2026-07-23-최근-목록-페이지의-커서-페이지네이션.md)
- **다른 탭이 구버전 연결을 붙들면 `onblocked`가 난다.** `db.onversionchange`에서 닫고 싱글턴을 비우는 것이 현재 처리이며, 사용자에게는 다른 탭을 닫으라는 문구만 띄운다.

# 백업

- **`JSON.stringify`의 replacer로는 `Date`를 잡을 수 없다.** `Date.prototype.toJSON`이 먼저 실행되어 replacer는 이미 문자열을 받는다. 값 트리를 직접 재귀하는 `backup/serialize.ts`의 `encodeValue`/`decodeValue`가 `{ "$date": ISO }`로 감싼다. `beginDate`처럼 `Date`가 키인 Store가 문자열로 굳으면 범위 조회가 예외 없이 빈 결과를 낸다.
  출처: [2026-07-23](../일지/2026-07-23-설정-페이지와-DB-내보내기가져오기.md)
- **ID는 Key Path가 있는 Store에서 `put(value)`로 넣어 보존한다.** 명시 키로 `put`하면 자동 증가 키 생성기가 그 이상으로 올라가 이후 발급이 겹치지 않는다. 분기는 `store.keyPath`로 판단한다. `lib.dom`의 `keyPath` 타입에 `null`이 없어 `=== null` 비교가 타입 오류이므로 `!store.keyPath`로 쓴다.
- **가져오기는 전체 Store 단일 `readwrite` 트랜잭션에서 비우고 채운 뒤 `queryClient.invalidateQueries()`를 필터 없이 부른다.** 덮어쓴 뒤 남는 캐시는 전부 거짓이다.
- **버전이 낮은 백업은 거부하지 않고 `backup/upgradeBackup.ts`가 현재 스키마로 승격한다.** 거부는 `version > DB_VERSION`일 때뿐이다. 스키마를 바꾸면 `upgradeBackup`과 그 테스트에 단계를 더한다.
  출처: [2026-08-23](../일지/2026-08-23-Question-제거와-QuestionSpecs-도입.md)

# 단어 Trie

- **단어 삭제는 tombstone이 아니라 참조 실교체다.** 표식 방식은 `createdAt` 인덱스가 곧 단어 목록이자 출제 모집단이라 최근 목록·추천기·통계·출제 전부가 분기를 가져야 해서 폐기했다. 관계가 참조하는 단어는 `hasWordReferences`로 막고 대체 단어를 받아 `replaceWordReferences`로 바꾼 뒤 지운다.
  출처: [2026-08-05](../일지/2026-08-05-단어-수정삭제와-참조-교체.md)
- **개명은 새 nodeId 발급 + 참조 교체다.** 새 경로 삽입을 기존 노드 제거보다 먼저 해야 공유 접두사가 지워졌다 재생성되지 않는다. 병합 확인은 트랜잭션 밖이어야 하므로 1차 호출이 `merge-required`를 돌려주고 UI가 confirm 후 `allowMerge`로 재호출하는 2단계다.
- **`createWord`는 기존 단어면 no-op으로 같은 nodeId를 돌려준다.** 중복 검사 전에 단어를 만들어도 부작용이 없고, "중복 단어를 저장하지 않는다"는 요구가 저절로 지켜진다. 부작용 없는 존재 확인은 `getWordNodeId`다. 이 함수가 `null`을 돌려주는 것은 react-query v5 `queryFn`이 `undefined`를 금지하기 때문이다.
- **`wordMeta.nextNodeId`만 자동 증가를 쓰지 않는다.** 루트가 0을 차지해야 하는데 자동 증가는 1부터 시작한다. 다른 Store의 ID는 IDB 키 생성기에 맡긴다. 직접 카운터를 관리하면 그것 자체가 경합 대상이 된다.
  출처: [2026-07-21](../일지/2026-07-21-기획md-저장에-관하여-보강.md)

# 중복 차단

- **삼항 관계(`TernaryComposition`, `NamedAssociation`)는 같은 (word1, word2, word3) id 삼중항이 있으면 제출을 막는다.** `relation/assertNotDuplicateTernaryRelation.ts`가 `submitAnswer`(탐색·알려주기 공용)와 `updateRelation`에서 불리며, 수정 시 `excludeRelationId`로 자기 자신을 제외한다. 참고사항은 비교하지 않는다. 유향이라 word1/word2를 뒤집은 조합은 별개다. 인덱스는 `word1Id`만 쓰고 메모리에서 거른다. 배치 모드와 순서화 도구는 사전 조회 `findDuplicateTernaryRelationId`로 건별 `중복` 결과를 만든다.
  이 규칙은 저장 공통 규약 "내용 기반 중복 제거를 하지 않는다"의 유일한 예외다.
