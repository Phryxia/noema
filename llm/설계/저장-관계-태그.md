# 태그 관계의 경우

- 상위문서: [타입별 Store](./저장-스토어.md)
- 형제 유형인 `SentenceToWord`는 [문장-단어 관계 Store](./저장-관계-문장단어.md)에 있다. 인덱스 공유 규약은 그 문서를 따른다.
- 만드는 화면은 [태그 입력기](../기획/화면/태그.md)다.
- 구현은 `packages/client/src/tag/`에 있다.

`Tag`는 문장 또는 문서 하나에 단어 하나를 붙였음을 뜻한다. 별도 Store 없이 `relations`에 저장되며 `/relation/<id>`를 같이 쓴다.
단어 연상(`BinaryAssociation`)과 비슷하지만 한쪽이 문장/문서고, `comment`가 없다.

## 타입

```ts
interface TagRelationBase extends RelationBase {
  type: 'Tag'
  wordId: number
}
interface SentenceTagRelation extends TagRelationBase { sentenceId: number }
interface DocumentTagRelation extends TagRelationBase { documentId: number }
type TagRelation = SentenceTagRelation | DocumentTagRelation
```

- `type`은 하나(`'Tag'`)고 대상 종류는 `sentenceId`/`documentId` 중 어느 필드가 있는지로 가른다. 판정은 `tag/checkIsSentenceTag.ts` 하나로 모았다.
  두 타입으로 나누지 않은 이유는 사용자가 개념을 하나(`Tag`)로 부르고, 유형 라벨(`태그`)도 하나이기 때문이다.
- `NonWordRelationTypes`에 `'Tag'`를 넣어 `checkIsWordRelation`이 거짓이다. `deleteRelation`은 `relations`만 지우고, 관계 검색 전수 조회에서는 빠진다.

## 인덱스

**새 인덱스도 `DB_VERSION` 상승도 없다.** `sentenceId`(문장 태그), `documentId`(문서 태그), `wordId`를 그대로 탄다.
IndexedDB 인덱스는 keyPath 필드가 없는 레코드를 건너뛰므로, 문장 태그는 `documentId` 인덱스에, 문서 태그는 `sentenceId` 인덱스에 나타나지 않는다.

- `tag.service`는 인덱스 결과를 `type === 'Tag'`로 거른다. 반대로 `d2s.service`/`s2w.service`는 자기 유형만 남기므로 개별 문장/문서 화면의 관계 표에 태그가 새지 않는다.
- `wordId` 인덱스를 타므로 단어 삭제 시 `WordReplaceDialog`가 태그를 세고, 단어 개명·대체(`replaceWordReferences`)가 태그를 따라온다.
- 문장 수정의 관계 영향 질의(`countReferencingRelations`)는 `sentenceId` 인덱스를 세므로 태그도 들어간다.
  다만 문장 입력기는 본문/출처가 그대로고 태그만 바뀐 저장이면 질의를 건너뛴다(`confirmSave`가 draft를 받는다).
  문서는 여전히 질의하지 않는다(`WordOrSentence`에 문서가 없다).

## 제출 절차: 스냅샷 차이

`submitTags(target, previous, values)` (`tag/submitTags.ts`)

- `previous`: 제출 전 스냅샷. 화면 진입 시 DB에서 읽은 `TagEntry[]`(관계 ID + 단어 값. 삭제된 단어면 값이 `''`).
- `values`: 제출 후 스냅샷. 카드 값 목록.

1. `values`에서 빈 값을 버리고 순서를 지키며 중복을 없앤다(`normalizeTagValues`, `trim` 없음). 이것이 `next`.
2. `added = next − previous.values`, `removed = previous − next`. 값(문자열)으로 비교한다.
   삭제된 단어의 entry는 값이 `''`라 `next`에 있을 수 없어 언제나 `removed`에 들어간다. 그래서 "삭제된 단어 카드는 없는 것처럼 취급하고 제출 시 그 관계를 지운다"가 따로 코드 없이 성립한다.
3. 둘 다 비면 트랜잭션을 열지 않고 `[]`를 돌려준다. 입력기는 빈 결과면 팝업을 띄우지 않는다.
4. `[wordMeta, wordNodes, recentWords, relations]` readwrite 하나. `createdAt`은 하나를 공유한다.
   - `added`마다 `addWord` → `relations.add({ type:'Tag', wordId, sentenceId|documentId, createdAt })`. 값별 예외는 잡아 `실패`로만 적는다.
   - `removed`마다 `relations.delete(entry.id)`.
5. 커밋 후 `recordCreation(wordCount, 새 단어 수)`, `recordCreation(relationCount, 추가 수)`, `recordDeletion(relationCount, 삭제 수)`.
   `recordDeletion`에 `amount` 인자를 더했다(`recordCreation`과 대칭).
6. 결과 `TagResult[]`는 `added`(카드 순) 뒤에 `removed`(이전 스냅샷 순).

예) `[a, b, c] → [c, d, b, e]`: `a` 관계 삭제, `d`·`e` 관계 추가, `b`·`c`는 그대로.

편집 중에는 어떤 DB 쓰기도 없다. 저장 버튼(또는 미저장 이탈 질의의 저장)만이 이 함수를 부른다.

## 목록

- `/relations`에는 유형 라벨 `태그`(`TAG_TYPE_LABEL`)로 나타난다. 대표 표현은 `tag` 토큰(`{ target, word }`)이며 `[문장/문서]` 영역 30% 고정 + ` ~ ` + `[단어]`.
- 개별 관계 화면은 `TagRelationPage`가 `PairRelationPage`로 `문장`/`문서` 줄과 `단어` 줄을 그린다.
- 개별 문장/문서 화면의 관계 표에는 **나오지 않는다**. 입력기가 그 역할을 한다.
- 개별 단어 화면에는 `wordId` 인덱스로 읽어(`getTagRelationsByWord`) `태그된 문장/문서` 표로 나온다.

## 수정과 삭제

- 관계 수정은 없다. 입력기에서 값을 바꾸면 삭제 + 추가다.
- `/relation/<id>`의 삭제는 `relations`만 지운다.
- 문장/문서를 삭제해도 태그 관계는 남고 목록에서 `(삭제됨) ~ [단어]`로 보인다.
