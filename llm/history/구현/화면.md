# 2026-08-16 `/relations` 대표 표현 가독성 개선

## 문제

통합 목록의 1차 표기가 읽기 불편했다. 예문 만들기는 대상 단어를 앞에 나열한 뒤 문장을 붙여 길었고,
관계 짓기의 `-[w3]→`은 화살표가 빈약했으며, 문장 추출은 문장 길이에 따라 `@ [문서]`의 위치가 행마다 흔들렸다.

## 해결

- 열을 ID / 유형 / 대표 표현 / 생성 시각으로 바꿨다.
- 토큰에 합성 종류를 더했다. `usage`(문장 id + 단어 id들)와 `extraction`(문장 id + 문서 id)은 렌더 단위가 하나의 덩어리라 낱개 토큰으로 풀면
  각 조각이 flex 아이템으로 따로 줄어드는 문제가 있었다. 해석 단계에서 `usage`는 `splitSentenceByWords`(순수, vitest)로 문장을 조각내 `segments`를 채우고,
  `UsageExpression`이 `span.truncated` 하나 안에 문장 조각 링크와 `<em>` 단어 링크를 인라인으로 그린다.
- 문장이 삭제됐거나 답이 문장이 아닌 예문 만들기는 `createUsageFallbackTokens`가 `(답변 회피)|(삭제됨)|[단어 답], 원 단어: [w1], [w2]`로 편다.
  이 헬퍼는 토큰 생성(`null`/단어 답)과 해석(삭제된 문장) 양쪽이 쓴다.
- 문장 추출은 `ExtractionExpression`이 `flex: 0 0 70%` / `flex: 0 0 30%` 두 영역으로 그려 `from`의 x 위치를 고정했다.
- 5rem 최소 폭은 사용자 요청으로 없앴다(`min-width: 0`).
- `(답변 회피)`, `(삭제됨)`은 `TextToken.isMuted`와 `.muted { color: var(--pico-muted-color) }`로 회색이다.
- 렌더 파일이 커져 `relations/RelationExpression/` 디렉토리로 나눴다(`RefLinks`, `UsageExpression`, `ExtractionExpression`).

# 2026-08-16 관계 히스토리 통합 페이지 `/relations`

## 문제

단어 관계 목록(`/relations/w2w`)과 문서-문장 관계 목록(`/relations/d2s`)이 열 구성이 달라 별도 페이지였고, 헤더에 `관계`/`문서 관계` 두 링크가 있었다.
하나의 표에 모든 유형을 시간순으로 섞어 보이려면 유형마다 다른 열(문제/응답/참고 vs 문서/문장)을 한 열로 눌러야 했다.

## 해결

- 열을 유형/ID/대표 표현/생성 시각으로 통일했다. 대표 표현은 유형별 인라인 표기(`[w1] ∩ [w2] = [답]` 등)다.
- 대표 표현은 두 단계로 만든다. `relations/computeRelationExpression`이 관계만 보고 `text`/`word`/`sentence`/`document` 토큰 배열을 만들고(순수, vitest),
  `hydrateRelationEntries`가 토큰에서 id를 모아 단어/문장/문서를 한 번에 해석해 `value`를 채운다. 어떤 id가 필요한지를 토큰 한 곳만 안다.
- `RelationExpression`이 토큰을 인라인 컴포넌트로 그린다. 셀 안은 `display: flex`이며 문장/문서 링크만 `flex: 0 1 auto; min-width: 5rem(후속 작업에서 0으로); overflow: hidden; text-overflow: ellipsis`로 줄어들고,
  단어 링크와 기호는 `flex: none`이다. 기호는 익명 텍스트로 두면 flex 컨테이너가 앞뒤 공백을 지우므로 `white-space: pre`인 `span`에 담았다.
- 행 클릭 이동(`RelationRow`)을 쓰지 않고 ID 셀만 `Link`(`search` 유지)다.
- `RecentSource.toEntry`가 유형을 거르지 않으므로 반대 유형 구간을 건너뛰는 비용이 사라졌다.
- 검색(`?q=`)은 유지하되, `qnaSearch.service`가 관계 원본을 돌려주는 `searchExactRelations`/`searchPartialRelations`를 노출하고 `useRelationSearch`가 새 표로 해석한다.
  개별 단어 페이지의 `연관 관계`와 배치 결과 표는 예전 `QnaTable`을 그대로 쓴다.
- 관계 짓기는 요청 원문의 `[w1] -[w2]→ [w3]` 대신 저장 의미(`word3`이 관계 이름)대로 `[w1] -[w3]→ [w2]`로 확정했다.
- 참고사항은 대표 표현에 없어, 참고사항으로만 일치한 검색 결과는 강조가 보이지 않는다. 판정 규칙은 그대로 두고 문서에 명시했다.
- `llm/기획/화면-페이지.md`가 직전 커밋(b04ce9c)에서 통째로 비워져 있어 `b04ce9c^`에서 복원한 뒤 `관계 목록`·`개별 관계` 절을 고쳤다.

## 알려진 한계

- (5rem 최소 폭은 후속 가독성 작업에서 폐지) 단어 링크만으로 칸을 넘치면 줄임표 없이 잘린다.
- 라우트 파일을 지우고 더한 뒤 `routeTree.gen.ts`는 vite 플러그인이 재생성하므로, 개발서버가 꺼져 있으면 `npx vite build`를 한 번 돌린 뒤 `tsc`/eslint를 돌려야 한다.

# 2026-08-16 GitHub Pages 하위 경로 라우팅

## 문제

`https://phryxia.github.io/noema/`에서 헤더(내비게이터)는 뜨는데 본문은 Not Found였고,
"NOEMA System" 링크를 누르면 주소가 `https://phryxia.github.io/`로 튀어 새로고침 시 GitHub 404가 났다.

자산과 라우터가 서로 다른 기준 경로를 봤다.
`base: './'` 덕에 `./assets/...`는 `/noema/` 아래에서도 로드됐지만,
TanStack Router에 `basepath`가 없어 `location.pathname` 전체(`/noema/`)를 라우트로 매칭해 실패했고,
`<Link to="/">`는 `href="/"`를 만들어 사이트 루트로 벗어났다.
PWA 작업 때 자산 경로만 상대로 두고 라우터는 고려하지 않은 것이 원인.

## 해결

배포 경로를 빌드 시 한 곳에서 절대경로로 주입하고 라우터가 같은 값을 쓰게 했다.

- `vite.config.ts` `base: './'` → `'/'`. dev는 원래 `/`로 동작하고 있었으므로 개발 환경 변화 없음.
- `main.tsx` `createRouter({ routeTree, basepath: import.meta.env.BASE_URL })`. dev/일반 빌드는 `/`, gh-page는 `/noema/`.
- 루트 `build-gh-page`에 `--base=/noema/` 추가. 커스텀 도메인 루트로 옮길 때는 이 플래그만 `--base=/`로 바꾸면 된다.
- 워크플로에 `cp docs/index.html docs/404.html` 스텝 추가. base가 절대경로가 되어 그동안 미뤄둔 딥링크 새로고침 fallback을 넣을 수 있게 됐다.
- manifest의 `start_url`/`scope: './'`와 `navigateFallback: 'index.html'`은 각각 manifest URL·SW URL 기준으로 해석되므로 손대지 않았다.
  SW 등록 경로는 플러그인이 base로 만들어 `/noema/sw.js`(scope `/noema/`)가 됐다.
- 검증: docs를 `/noema/`에 마운트한 정적 서버 + playwright로 루트 진입 렌더, 홈 링크 클릭 후 URL `/noema/` 유지,
  `탐색` href `/noema/explore`, `/noema/explore` 직접 진입(404 fallback 경유) 렌더 확인. 일반 `build`는 `/assets/`로 종전과 동일.

# 2026-08-16 문장 추출 최초 분할에 부호 경계 추가

## 문제

`extractSentences`의 `/.*[.!?"']?(\n\s*|$)/g`는 부호가 선택이라 사실상 줄 단위 분할이었다.
개행 없이 문장을 이어 쓴 문서는 통째로 카드 하나가 되어 사람이 `\n\n\n` 분할을 문장 수만큼 반복해야 했다.

## 해결

패턴을 `/.*?(?:[.?!"']+(?:\s+|$)|\n\s*|$)/g`로 바꿨다. 게으른 `.*?`가 "부호 연속 + 공백 1개 이상 또는 문자열 끝", 개행, 문자열 끝 중 하나를 만나는 지점에서 끊는다.
처음엔 `[.?!"']+\s*`로 공백을 선택으로 두었더니 `CLAUDE.md`가 `CLAUDE.`/`md`로 잘려 공백 필수로 바로 고쳤다.
완벽한 판정 대신 이 정도로 충분하다는 사용자 판단을 따랐고 나머지는 카드 병합으로 고친다.
테스트에 개행 없는 분할과 연속 부호 케이스를 더했다. [문장 추출 기획](../../기획/화면/문장-추출.md)의 최초 분할 항을 갱신했다.

# 2026-08-16 문장 카드 화살표 키 이동

## 문제

문장 추출 편집기의 카드 사이 이동이 병합/삭제 후 자동 포커스뿐이라 키보드만으로 카드를 오갈 수 없었다.
요구는 끝에서 Right → 다음 카드 앞, 처음에서 Left → 이전 카드 끝, 마지막 행에서 Down → 다음 카드 첫 행 같은 열,
첫 행에서 Up → 이전 카드 마지막 행 같은 열. "행"은 `field-sizing: content`로 접힌 시각 행 기준이다.

처음에는 JS 측정 없이 keydown에서 캐럿을 기억하고 keyup에서 캐럿이 안 움직였거나 끝/처음으로 밀렸으면
마지막/첫 시각 행이었다고 판정했는데 두 가지가 틀렸다.
브라우저가 keydown 기본 동작으로 캐럿을 카드 끝/처음으로 먼저 옮기고 keyup에서 카드가 바뀌어 캐럿이 두 번 뛰어 보였고,
"같은 열"을 문자 수로 계산해 반각과 전각이 섞이면 시각적으로 같은 열이 되지 않았다.

## 해결

- `caretGeometry.ts`: textarea 계산 스타일과 `clientWidth`를 복사한 숨은 미러 `div`를 만들고, 값 + U+200B 텍스트 노드에
  `Range`를 걸어 오프셋별 문자 사각형을 읽는다. `measureCaretLine`이 첫/마지막 시각 행 여부와 캐럿 x를,
  `findCaretNearX`가 도착 카드 첫/마지막 행에서 x에 가장 가까운 오프셋을 준다. 같은 행 판정은 세로 중심 차 < 줄높이/2.
- `arrowNavigation.ts`: keydown에서 `computeArrowNavigation`으로 `{ direction, x }`를 판정하고 카드가 `preventDefault` 후 즉시 `onNavigate`.
  처음엔 Backspace처럼 keyup에 옮겼으나, 키 홀드 시 `repeat` keydown이 새 카드에서 이어져 연속 이동이 되도록 keydown으로 바꿨다(Backspace는 keyup 유지).
  좌우는 `x: null`로 맨 앞/맨 끝. 측정 함수는 인자로 주입해 vitest는 가짜 측정으로 판정만 검사한다.
- `useSentenceCards.focusAdjacentCard`가 인접 카드의 textarea를 찾아 `computeArrivalCaret` 후 `focusCard`.
- 검증: playwright로 dev 서버에 붙어 문서를 만들고 추출 편집기에서 Right/Left 경계, 접힌 카드 안에서 Down/Up이 시각 행을
  먼저 이동하는지, 카드 이동 시 전각→반각 x 대응(한글 2자 ≈ 영문 4자), 마지막/첫 카드 무동작, Shift+Right 무시,
  키 홀드로 접힌 카드 3행을 지나 다음 카드까지 연속 이동을 확인. vitest 89개, tsc, eslint 통과.

- 최초 분할 정규식은 `.`이 `\r`을 줄바꿈으로 봐서 CRLF 문서의 본문을 통째로 잃는 것을 테스트로 발견해, 매칭 전에 `\r\n?`을 `\n`으로 정규화했다.

# 2026-08-13 관계 짓기(NamedAssociation) 유형 신설

## 문제

`relation/types.ts`에 선언만 있던 `NamedAssociation`(word1 --word3--> word2 유향 관계)을
알려주기·관계 목록·개별 관계 페이지에 연결하되 탐색에는 출제하지 않아야 했다.
세 단어 입력기를 `단어 1 ── 관계 ──▶ 단어 2` 한 줄로 놓고, 포커스 순서도 보이는 순서(word1 → word3 → word2)여야 하며,
word3의 Enter는 제출이 아니어야 했다.

## 해결

세 단어를 모두 대상 단어로 다루는 답안 없는 유형으로 모델링했다(`SubjectWordSpecs` 3/3, `checkIsAnswerReady`의 무응답 그룹).
저장 형태는 `TernaryIsolation`과 같아 DB 버전과 인덱스는 무변경이다.

- **시각 재배치는 렌더 계층에서만**: words 배열은 `[word1, word2, word3]`을 유지하고,
  `SubjectWordFields`의 `isDirected` 분기가 DOM을 [0, 2, 1] 순으로 그린다. 포커스/Tab/Enter 이동은
  DOM 순서를 따르므로 요구된 포커스 순서가 저절로 나온다. 제출·복원(`createRelationQuestion`,
  `getQuestionWordIds`) 로직은 배열 순서 그대로라 손댈 곳이 없었다.
- **Enter 규약은 기존 메커니즘 재사용**: 대상 단어 칸은 `onEnter=leaveField`(포커스 이동, 제출 차단)이고,
  참고사항 단어 모드는 `onEnter` 미전달이라 브라우저 기본 submit → `isSubmittable` 가드. 신규 코드 없음.
- **답안란 제거**: `RelationForm`에서 `type !== 'NamedAssociation'`일 때만 `AnswerSection`을 그린다.
  수정 페이지의 답안 복원은 `getRelationAnswer`가 `null`을 돌려줘 WordsUsage 회피와 같은 경로로 흡수된다.
- **목록 표시**: `hydrateQnaEntries`에서 문제 열은 `words.slice(0, 2)`(`getDisplayWords`),
  응답 열은 `{ kind: 'selection', word: words[2] }`로 기존 `WordLink` 렌더를 재사용했다.
- **탐색 제외**: `ExploreQuestionTypes` 상수를 만들어 `ExplorePage`가 `useExplore`/`QuestionTypeSelector`에
  `availableTypes`로 넘긴다(`lab/embedding`의 `LabQuestionTypes` 선례). `loadCheckedTypes`가
  `availableTypes.filter`라 localStorage 잔존 체크도 자동 차단된다. `pickQuestion.createNewQuestion`의
  default 분기는 컴파일 에러가 나서 명시 case로 풀어냈고, `NamedAssociation`은 throw로 막았다.
- `SubjectWordFields.tsx`가 200줄을 넘게 되어 내부 `SubjectWordField`를 같은 디렉토리의 별도 파일로 분리했다.
- HMR 안전을 위해 유형 노출(`QuestionTypeOptions`의 `{ value, label: '관계 짓기' }`)을 마지막에 저장했다.
- 기획 명세는 [알려주기](../../기획/화면/알려주기.md)에 적었다. `기획/탐색.md`는 250줄로 분리 대기 중이라
  건드리지 않았고, 탐색에 출제하지 않는 유형이므로 알려주기 문서가 맞는 자리다.

## 남은 것

- 기존 중복 금지 규칙에 따라 word3(관계 이름)도 word1/word2와 같을 수 없다. 자기 자신을 잇는
  이름이 필요해지면 `checkSubjectWordsReady`를 유형별로 완화해야 한다.

# 2026-08-08 PWA 지원

## 문제

  상대 자산 경로가 깨진다. 딥링크 직접 진입 404는 종전과 동일(악화 없음). 도메인 확정 후 별도 작업.
- **업데이트**: `registerType: 'autoUpdate'` + `main.tsx`의 `registerSW({ immediate: true })`
  (virtual:pwa-register). 새 버전 감지 시 무음 교체 후 리로드. 타입은 `vite-env.d.ts`에
  `vite-plugin-pwa/client` 레퍼런스 추가. dev에서는 SW 비활성(기본값)이라 HMR과 간섭 없음.
- **프리캐시**: `globPatterns`에 ico/png/svg/webmanifest를 추가해 autoCodeSplitting의 lazy 청크

  200 확인, dist manifest의 `start_url`/`scope`가 `'./'`로 유지됨을 확인.

# 2026-08-08 토스트 알림 시스템

## 문제

저장/삭제 mutation이 성공해도 실패해도 명시적 피드백이 없었다. 백업을 제외한 모든 mutation에
`onError`가 없어 실패가 조용히 묻혔고, "제출된 것 같은데 저장 안 됨" 착각 경로(건너뛰기 포커스
트랩, 관계 폼 Enter=포커스 이동)와 겹쳐 "입력했던 단어가 사라진 느낌"의 원인이 되었다.

- **발신 규칙**: `main.tsx`의 `MutationCache.onError`가 모든 mutation 실패를 토스트로,
  `onSuccess`는 `mutation.meta.successMessage`가 선언된 것만 성공 토스트로. 저장/삭제성
  mutation 전부에 meta를 부여했고, 랜덤 단어 뽑기 같은 비저장성 mutation은 무음.
  `useWriterForm`은 `saveSuccessMessage`/`deleteSuccessMessage` 옵션으로 호출자가 문구 전달.
  meta 타입은 `toast/types.ts`의 `Register.mutationMeta` 선언 병합으로 강제.
- **디자인**: pico conditional이라 `--pico-*` 변수·`article` 카드 스타일을 받으려면 토스트
  루트에 전역 `pico` 클래스를 문자열로 병기해야 한다(`cx('pico')`는 모듈에 없어 탈락).

  (`--pico-ins-color`/`--pico-del-color`)만 담당. 컨테이너는 `pointer-events: none`.
- **백업 notice 대체**: `useBackupActions`의 로컬 notice 상태와 `BackupPanel`의 인라인 `<p>`를
  제거하고 meta로 이관. `getErrorMessage`는 `utils/getErrorMessage.ts`로 승격.

검증: 헤드리스 크로미엄으로 라이트/다크 두 테마에서 4연속 발사(최오래 제거·순서·5초 소멸)와
실 플로우를 스크린샷 확인. 다크 테마 스크린샷이 프리뷰에서 흰 카드로 보이는 착시가 있었으나

# 2026-08-07 단어 입력기 화살표 키로 추천 목록 탐색

## 문제

추천 목록의 항목 선택이 클릭 또는 Tab+Enter뿐이었고, 그마저도 `SubjectWordField`를 제외한
사용처 4곳(WordWriter, WordEditor, TextWriterField, WordReplaceDialog)은 입력칸 blur 즉시
`isFocused`가 꺼져 목록이 언마운트되므로 키보드로 목록에 진입할 수 없었다.

## 해결

가상 포커스(activeIndex + aria-activedescendant) 대신 **실제 DOM 포커스 이동**을 택했다.
기존 결정(항목은 실제 button/Link, 버튼 Enter는 브라우저가 click으로 변환하므로 클릭과
Enter가 한 경로, 키는 컨테이너 위임이 아니라 해당 요소 스코프에서 처리)과 정합하고,
선택 상태나 ARIA 동기화 기계가 필요 없기 때문이다.

- `WordField`에 `onArrowDown?` 추가: 기존 `isComposing` 가드 아래에서 ArrowDown을
  `preventDefault`(캐럿 이동 차단) 후 위임. 미지정 사용처는 불변.
- `WordSuggestion`에 `ref`(React 19 ref-as-prop, 루트 article)와 `onExitUp?` 추가.
  `ul`의 onKeyDown 위임으로 항목 간 이동을 처리한다. `'li > :first-child'` 선택자로
  항목 라벨(button/Link)만 순회 대상이 되어 삭제(x) 버튼은 자연히 제외된다(Tab 접근 유지).
  마지막 항목의 ArrowDown은 첫 항목으로 순환하고, 첫 항목의 ArrowUp은 `onExitUp`으로
  입력칸에 복귀한다(ArrowUp은 순환하지 않는다 — 입력칸 복귀 경로와 겹치기 때문).
  목록 스코프 처리 덕에 목록이 `WordReplaceDialog`로 대체된 중첩 상태에서도 오염이 없다.
- `useQuery`에 `placeholderData: keepPreviousData` 추가: 타이핑 직후 100ms 스로틀 창에서
  ArrowDown으로 진입하면 새 queryKey의 로딩으로 목록이 언마운트되어 포커스가 body로
  추락하는 문제를 막는다.
- 전제조건인 포커스 단위 확장(컨테이너 focusin/focusout + `contains(relatedTarget)` 가드)이
  5곳에서 동형 반복되므로 `word/useSuggestionFocus.ts` 훅으로 추출했다. `SubjectWordField`의
  검증된 패턴이 원형이고, `focusSuggestion`/`focusField`는 기존 `focusFirstElement`를 재사용한다.
  `SubjectWordFields`의 `focusedIndex` state와 `isFocused` prop은 훅 로컬 상태로 대체되어
  제거했다(실 포커스는 어차피 배타적이다). blur 시 `appendWordIfNeeded`는 훅의
  `onFocusChange` 콜백으로 유지된다.

부수 변화(의도됨): 사용처 4곳에서도 컨테이너 안 다른 요소(저장 버튼 등)에 포커스가 있는 동안
목록이 열려 있다. Link 모드(WordWriter, WordEditor)의 항목 Enter는 단어 페이지 이동인데,
클릭과 같은 경로이므로 그대로 두었다. Playwright로 대시보드와 알려주기에서 진입/순회/복귀/
Enter 선택/다음 요소 포커스를 확인했다.

# 2026-08-07 알려주기 예문 단어 칸 동적 추가/삭제

## 문제

알려주기의 예문 만들기(`WordsUsage`) 입력칸이 3칸 고정이라, 탐색의 단어 수 상한 제거와
맞지 않고 4개 이상을 능동 입력할 수 없었다.

## 해결

`SubjectWordSpec`에 `isCountAdjustable`을 추가하고 `WordsUsage`를 `{ count: 2, minCount: 1 }`로
바꿔 초기 2칸(둘째만 optional)으로 했다. 동작은 `SubjectWordFields`가 소유한다.

- **추가**: 부모의 `handleFocusChange` falling edge에서 마지막 칸이 비지 않았으면
  `flushSync(() => onChange(prev => prev.concat('')))`. flushSync인 이유는 자식 `leaveField`의
  `onFocusChange(false) → focusNextElement` 순서에서 DOM에 새 칸이 이미 있어야
  Enter/추천 선택 시 새 칸으로 포커스가 가기 때문. Tab/클릭 blur는 `focusNextElement`를
  타지 않아 포커스를 빼앗지 않는다. leaveField와 실제 blur의 중복 호출은 flush 후
  `index !== words.length - 1`이 되어 무해하다.
- **삭제**: `WordField`에 `onEmptyBackspace` prop을 추가. **누르는 시점에 이미 빈** 칸에서
  백스페이스를 release해야 발화한다(keydown에서 빈 상태를 ref에 기록, keyup에서 소비).
  마지막 글자를 지운 release로는 삭제되지 않고, 홀드 반복으로 여러 칸이 지워지지도 않는다.
  한글 조합은 `isComposing`으로 무시. k>1 칸에만 연결하여 1칸 이하로 내려가지 않는다.
  삭제 시 루트 ref의 `querySelectorAll('input')[index - 1]`을 focus하고
  `setSelectionRange`로 커서를 맨 끝에 둔 뒤 제거한다(key가 index라 앞쪽 DOM은 안정적).

함정: 추천 선택 경로는 `onChange(value)` 직후 blur가 와서 부모의 `words`가 stale하다.
append/remove를 함수형 업데이트로 바꾸고 `RelationEditor.setWords`를
`Dispatch<SetStateAction<string[]>>`로 넓혀, 선택된 값이 덮어써지지 않게 했다.

`loadRelationSnapshot`의 `max(단어 수, count)`는 count 2로 그대로 맞아 수정하지 않았다.

# 2026-08-06 탐색 제출 후 답안 입력란 포커스

## 문제

탐색에서 텍스트 답안 유형(단어 설명, 예문 만들기, 이항 공통점, 이항 차이점)을 제출하면
다음 문제가 출제되지만 포커스는 제자리라, 매 문제마다 답안 입력란을 다시 클릭해야 했다.

## 해결

관계 폼과 달리 제출 성공 시 입력란이 즉시 살아있지 않다. `onSuccess` → `skip()` → `refetch`로
로딩 중에는 `AnswerSection`이 언마운트되므로, `onSuccess` 직후 동기 focus가 불가능하다.
그래서 `useExplore`에 `isFocusPending` ref를 두고 `onSuccess`에서 켠 뒤,
`[isFetching, pick]`을 보는 effect가 새 문제 렌더 후에 소비하며 포커스한다.

포커스 대상은 `ExploreForm`의 question 컨테이너(`answerRef`)에서 `ANSWER_INPUT_SELECTOR`
(`input:not([type="radio"])`, `textarea`)로 찾는다. `focusFirstElement`에 선택자 인자를 추가해 재사용했다.

- 라디오를 제외하는 이유: 이항 공통점/차이점은 단어/문장 모드 라디오가 입력란보다 먼저 렌더된다.
- 새 문제가 선택지 유형(`BinarySimilarity`, `TernaryIsolation`)이면 선택자에 걸리는 요소가 없어
  포커스하지 않는다. 선택지 버튼에 포커스가 가면 Enter가 숫자 단축키 체계와 충돌하기 때문이기도 하다.
- 건너뛰기와 유형 변경은 플래그를 켜지 않으므로 기존 동작 그대로다.
- `ExploreForm`을 공유하는 임베딩 실험 페이지에도 같은 동작이 적용된다(이항 공통점/차이점 포함).

# 2026-08-06 관계 제출 후 첫 입력폼 포커스

## 문제

관계 입력기(`/relation/new`)는 제출 성공 시 폼을 비우지만 포커스는 제자리에 남았다.
제출 직후 버튼이 `isSubmittable === false`로 disabled가 되면 포커스가 body로 떨어지기까지 해서,
연속 입력마다 첫 단어 칸까지 마우스나 Tab으로 되돌아가야 했다.

## 해결

`focusNextElement`의 `FOCUSABLE_SELECTOR`를 `utils/consts.ts`로 빼고,
컨테이너 내부의 첫 포커스 가능 요소에 `.focus()`하는 대칭 유틸 `focusFirstElement`를 추가했다.

호출 지점은 `useRelationEditor`의 제출 mutation `onSuccess`의 `isResetOnSave` 분기다.
`save()` 진입 경로가 셋(form submit, 답안란/참고사항 `onSubmit`, ChoiceGroup Enter 단축키)이라
성공 지점만이 모든 경로를 한 번에 덮는다. form ref도 훅이 만들어 반환하고 `RelationForm`의 `<form>`에 붙였다.

첫 단어 input은 리셋 전후로 단어 개수가 같아 언마운트되지 않으므로, setState 직후 동기 `focus()`로 충분하다.
수정기(`/relation/$relationId`)는 `isResetOnSave: false`라 폼이 비워지지 않고, 포커스도 건드리지 않는다(기존 동작 유지).

# 2026-08-06 관계 수정과 삭제

## 문제

관계는 만들기만 되고 고치거나 지울 수 없었다. 오타 하나를 고치려면 지울 방법조차 없어 잘못된 관계가 그대로 쌓였다.
이름도 어긋나 있었다. 관계를 만드는 화면이 `/teach`의 `src/teach`에 있었고, 목록은 `문답 기록`이었다.

## 해결

`src/teach/*`를 `src/relation/` 하위로 옮기고 `Teach*`를 `Relation*`로 개명했다. 라우트는 `/relation/new`가 됐다.
다만 `TEACH_SOURCE_PREFIX`와 `TEACH_TYPE_STORAGE_KEY`는 이름과 값을 그대로 뒀다.
앞은 이미 저장된 문장의 `source` 문자열과 맞아야 하고, 뒤는 사용자 localStorage 키라 바꾸면 선택이 날아간다.

생성과 수정이 같은 화면 구조를 쓰므로 `useTeach`를 `useRelationEditor`로 일반화했다.
초기값 팩토리(`getInitial`), 저장 함수(`persist`), 저장 후 초기화 여부(`isResetOnSave`), 삭제 함수를 옵션으로 받는다.
`getInitial`을 값이 아니라 함수로 둔 것은 `useState`의 지연 초기화에 그대로 넘겨,
localStorage 조회와 객체 생성이 매 렌더가 아니라 한 번만 일어나게 하기 위함이다.

관계 수정은 제출 절차와 같은 순서로 `put`한다. 답안/참고사항이 문장일 때가 까다로웠다.
문장은 제출 때마다 새로 만들어지므로 그 관계 전용이라 제자리 수정도 안전하지만,
내용이 달라졌는데 같은 `sentenceId`를 유지하면 그 문장을 가리키던 링크의 의미가 조용히 바뀐다.
그래서 내용이 같으면 기존 ID를 그대로 쓰고, 달라졌을 때만 새 문장을 만들기로 했다.
새로 만들 때는 밀려난 문장의 `source`를 물려받는다. 탐색에서 수확한 답을 고쳤다고 알려주기 출처로 둔갑하면 안 되기 때문이다.
밀려난 문장은 지우지 않는다.

삭제는 관계와 그 관계를 낳은 문제를 한 트랜잭션에서 함께 지운다.
문제만 남기면 건너뛴 문제와 구분되지 않아 영영 해석할 수 없는 잔재가 된다.
반대로 단어와 문장은 독립된 데이터라 남긴다.

목록에서는 행 클릭으로 들어간다. 셀 안에 단어/문장 링크가 있으므로,
`event.target.closest('a')`가 잡히면 행 이동을 하지 않고 링크에 양보한다.

## 남은 것

개별 단어/문장/문서 페이지에 있는 _미저장 수정 이탈 질의_(`useWriterForm`의 `useBlocker`)를 개별 관계에는 넣지 않았다.
`useWriterForm`은 `{ value: string }` 형태의 draft를 전제하는데 관계의 입력은 단어 배열과 답안·참고사항으로 갈라져 있다.

# 2026-08-06 대상 단어 칸의 키보드 흐름

## 문제

알려주기 페이지의 대상 단어 칸에서 Tab을 치면 포커스가 오버레이로 새는 것처럼 보였다.

처음에는 공백 에코를 의심했으나, 그 `div`에는 `tabindex`가 없어 원래부터 Tab 대상이 아니었다.
실제 범인은 DOM 순서상 입력칸 바로 뒤에 오는 `WordSuggestion`의 선택 버튼이었다.
입력칸이 blur되면 `isFocused`가 꺼져 목록이 언마운트되므로, 방금 포커스를 받은 버튼이 사라지며
포커스가 body로 떨어졌다. 사양은 [알려주기 화면](../../기획/화면/알려주기.md)에 적었다.

## 해결

포커스를 소유하는 단위를 입력칸 하나에서 **칸 전체(입력칸 + 추천 목록)**로 넓혔다.

- `SubjectWordField`의 감싸는 `div`가 `onFocus`/`onBlur`를 받는다(React의 focusin/focusout).
  blur에서 `event.currentTarget.contains(event.relatedTarget)`이면 무시하므로, 입력칸에서 목록 항목으로
  Tab해도 목록이 닫히지 않는다. 칸 밖으로 나가야 닫힌다.
- 항목 선택(`onSelect`)은 값 채우기에 더해 목록을 닫고 다음 요소로 포커스를 넘긴다.
  버튼의 Enter는 브라우저가 click으로 바꿔주므로 keydown을 가로챌 필요가 없었고,
  덕분에 클릭과 Enter가 한 경로를 공유한다.
- `focusNextElement(container)`는 문서 순서상 컨테이너 뒤에 오면서 컨테이너에 속하지 않는 첫 포커스 가능
  요소를 찾아 `focus()`한다. `compareDocumentPosition`으로 앞뒤를 가른다. 다음 칸의 input을 ref로 엮지
  않은 이유는, 마지막 칸에서 답안란으로 넘어가는 경우까지 같은 규칙으로 덮이기 때문이다.
- 상태 갱신보다 `focus()`를 먼저 호출한다. 리렌더로 목록이 언마운트되기 전에 포커스가 밖으로 나가야
  갈 곳을 잃지 않는다.

Enter는 컨테이너의 keydown이 아니라 `WordField`의 `onEnter?` prop으로 받았다.
컨테이너에서 가로채면 같은 컨테이너 안에 렌더되는 `WordReplaceDialog`의 대체 단어 입력까지 Enter를
빼앗기기 때문이다. 한글 조합 확정을 이동으로 오인하지 않도록 `nativeEvent.isComposing`을 거른다.
`onEnter`를 주지 않은 기존 사용처(대시보드 등)의 Enter 제출은 그대로다.

곁다리로 `WhitespaceEcho`에 `aria-hidden="true"`를 달았다. input 값을 복제한 장식이라 스크린리더에는
같은 문자열이 두 번 읽힐 뿐이다. `pointer-events: none`이 마우스에 대해 하던 일을 접근성 트리에 대해 한 셈이다.

# 2026-08-06 알려주기 페이지

## 문제

탐색은 시스템 출제에 수동적으로 답하는 방식뿐이라, 사용자가 이미 아는 관계를 능동적으로 넣을 수 없었다.
유형·대상 단어·답을 직접 지정해 문제와 관계로 저장하는 `/teach`(알려주기)가 필요했다.
사양은 [알려주기 화면](../../기획/화면/알려주기.md)에 있다.

## 해결

탐색의 제출 경로와 답안란을 그대로 재사용하는 것이 핵심이었다.

- `submitAnswer`의 유일한 탐색 고정 지점은 source 문구뿐이라, `sourcePrefix?: string` 파라미터로 뚫었다.
  기본값은 기존 exploration 문구라 탐색/실험 동작은 그대로다.
- `AnswerSection`은 `draft.question.type`과 `lexes[].value`만 소비한다. 대상 단어가 아직 DB에 없으므로
  배열 인덱스를 placeholder nodeId로 쓴 `QuestionDraft`를 합성해 넘기고,
  진짜 `NewQuestion`은 제출 시 `createWord`가 돌려준 실제 nodeId로 `createTeachQuestion`이 재조립한다.
  placeholder id가 DB에 절대 들어가지 않는 것이 불변식이다.
- 유형별 입력칸은 `SubjectWordSpecs`(`count`/`minCount`)로 선언하고, 비어있지 않은 단어들의 pairwise 상이를
  `checkSubjectWordsReady`로 검사한다. 같은 단어끼리의 퇴화 관계와 삼항 격리 선택지의 label 키 충돌을 함께 막는다.
- 검증 중 삼항 격리의 선택된 버튼이 secondary 색으로 보였으나, pico 버튼의 background transition(0.2초) 도중을
  스크린샷으로 찍은 것이었다. 실제로는 primary로 전환된다.
- 무응답 허용 유형(이항 공통점 등)은 대상 단어만 채워도 제출 가능 상태라, 대상 단어 칸의 Enter가
  브라우저 암묵 제출로 이어져 의도치 않은 회피 관계가 적재됐다. `SubjectWordFields` 래퍼의

# 2026-08-03 Prefix Additive Online Bayesian

## 문제

임베딩 실험장의 Naive 모델은 단어를 전부 독립으로 취급해, 접두사를 공유하는 단어 사이에 일반화가 일어나지 않았다.
[기획](../../기획/탐색-임베딩실험.md)의 개선안대로 Trie 노드별 임베딩의 경로 합으로 단어 임베딩을 정의해야 했다.
의사코드는 문자열 Trie를 새로 짓지만, 프로젝트에는 이미 IndexedDB `wordNodes`가 Trie다.

## 해결

기획서 말미의 지시대로 임베딩을 DB Trie의 노드 id에 바인딩했다. 새 모듈 `word/getWordTrie.ts`가
`wordNodes`를 `getAll()` 한 번으로 읽어 `{ parents, children, wordNodeIds }` 스냅샷을 만들고,
모델 코어(`embedWord`, `updateModel`, `proposePair`, `evaluateAccuracy`)는 전부 이 스냅샷을 인자로 받는다.
DFS 중 노드당 DB 왕복을 피하기 위한 구조다.

- `EmbeddingModel.words`(단어별)를 `nodes`(노드별)로 교체. 단어 임베딩은 경로 노드의 `mu`/`varr` 합.
- `updateModel`은 갱신 전 경로 합(`eu`/`ev`)을 스냅샷한 뒤 두 경로의 노드를 순차 갱신한다(의사코드와 동일).
  Naive 구현이 갱신 도중 값을 읽던 것과 달리, 의사코드가 스냅샷 기준이라 그쪽을 따랐다.
- `proposePair`는 노드별 노이즈를 `Map`으로 1회만 샘플링하고, 누산기 증감으로 Trie를 DFS한다.
  `u` 경로에서 뽑힌 노이즈가 후보 점수에도 재사용되는 결합이 의사코드의 핵심이라 그대로 유지했다.
- `evaluateAccuracy`는 호출 1회 내에서 단어별 경로 합 `mu`를 메모이즈했다. 매 스텝 전체 재평가 비용 때문이다.
- 출제 직전마다 `getWordTrie()`로 스냅샷을 갱신해, 응답 처리 시점의 Trie에 그 문제의 경로가 항상 존재한다.
- Local Storage 스키마는 v2(`nodes`)로 올렸다. 노드 임베딩과 단어 임베딩은 의미가 달라 v1은 복원하면 안 되는데,
  기존 버전 검사가 불일치 시 빈 배열을 돌려주므로 자동 폐기된다.
- 테스트는 고정 Trie 헬퍼로 재작성했다. 접두사 공유 단어로의 일반화, 경로 밖 노드 불변,
  `Math.random`을 0으로 고정해(Box–Muller가 0을 뱉는다) `proposePair`의 argmax·라벨 필터·폴백을 결정적으로 검증했다.

탐색 페이지(`explore/`)는 수정하지 않았다. `word/getAllWordNodeIds.ts`는 이 교체로 사용처가 사라졌으나,
llm 밖 파일 삭제는 허가가 필요해 남겨 두었다.

## 남은 것

사용 중 특정 단어가 상대로 연속 출제되는 현상이 나왔다. `v`가 argmax인 데다 `bias = -2`가
라벨 1/0의 갱신량을 비대칭(약 7배)으로 만들어, 한 번 관계를 얻은 단어의 norm이 커지는 되먹임이 원인이다.
`EMBEDDING_BIAS`를 0으로 바꿨더니 validation accuracy가 극도로 낮아져 -1로 절충했고,
argmax는 Gumbel-max 트릭(`argmax(s + τG)`, softmax 샘플링과 동치, `τ = 1`)으로 교체했다.
후보당 노이즈 한 줄 추가라 복잡도는 그대로다. 테스트는 `sampleGumbel`을 0으로 모킹해 결정성을 유지했다
(`Math.random` 0 고정 시 Gumbel이 무한대로 발산해 모듈 모킹으로 전환). 쿨다운은 보류 중이다.

이후 실험 페이지에도 유형 체크박스를 넣었다(기획 변경). `useExplore`의 `fixedTypes`를
`availableTypes` + `checkedTypesStorageKey`로 일반화해, 두 페이지가 같은 로직으로 각자의
유형 모집단과 저장 키(`lab/embedding/checkedTypes`)를 갖는다. `QuestionTypeSelector`는
선택적 `availableTypes`로 표시 유형을 거르고, `pickLabQuestion`은 체크된 유형을 인자로 받아
그 안에서만 출제한다(전부 해제 시 `noType`). 탐색 페이지는 옵션 기본값 경로라 동작 변화가 없다.

이후 bias를 학습 파라미터로 바꿨다(기획 변경). `EmbeddingModel`에 스칼라 `bias: { mu, varr }`를 두고
사전분포 `N(-3, 1)`에서 시작, 입력 계수가 1이라 `mu += varr * err`, `varr /= 1 + varr * gain`으로
노드와 같은 방식으로 갱신한다. 수동 튜닝(-2 → 0 → -1)을 데이터가 대신한다.
모든 후보에 동일하게 더해지므로 출제 선택 확률에는 영향이 없다. 저장 스키마는 v3(`bias` 필드)로 올렸다.

# 2026-07-31 대시보드 통계에 문답 추가

## 문제

총 보유 통계와 증가 추이 차트가 단어/문장/문서 세 종류만 다뤘다. 탐색의 질의응답도 함께 보여야 했다.
쟁점은 두 가지였다. 모집단을 `questions`와 `relations` 중 무엇으로 잡을지,
그리고 기존 `CountLog` 레코드에 새 필드가 없어 차트와 순증감 누산이 깨지는 문제였다.

## 해결

`relations`를 모집단으로 정했다. 관계 없이 남은 문제는 실패 잔재라 건너뛴 문제와 구분되지 않고,
문답 기록 페이지도 `relations`를 쓰기 때문이다. 근거는 [통계 구역 설계](../../설계/화면-대시보드-통계구역.md)에 남겼다.

`CountKind`에 `relationCount`를 더하자 `CountSeriesList` 기반의 총 보유 그리드와 차트 목록은 수정 없이 네 번째 항목을 얻었다.
관계 생성 기록은 `submitAnswer`의 관계 트랜잭션 커밋 직후 기존 규약대로 `recordCreation`을 부른다. 관계는 지워지지 않으므로 삭제 기록은 없다.

기존 레코드의 필드 결손은 `DB_VERSION`을 8로 올리고, 8 미만에서 오는 모든 업그레이드에서
통계 Store를 비워 재백필하는 것으로 풀었다. 이때 설정 페이지의 재구축과 로직이 겹쳐,
clear+백필을 `clearAndBackfillCountLogs`로 뽑아 양쪽이 공유하게 했다.

## 남은 것

배포 직후 문답 차트가 전부 0으로 나왔다. 개발서버가 켜진 채 작업해서,
`DB_VERSION = 8`이 재백필 코드보다 먼저 저장된 사이 HMR 리로드가 일어나
재백필 없는 구버전 업그레이드 코드로 DB가 8이 되어 버렸다.
이후에는 `oldVersion < 8` 조건이 영원히 거짓이라 재백필이 실행되지 않았다.
버전을 9로 올려 재소모하는 것으로 해결했다. 버전 상수와 마이그레이션 코드는 한 저장 단위로 같이 내보내야 한다.

이어진 피드백 셋도 반영했다. 계열명을 `문답`에서 `관계`로 바꿨고,
관계는 삭제가 없으므로 `CountSeries.hasDeletion`을 두어 관계 차트의 변화량에서 `삭제` 계열을 뺐다.
차트 `flex-basis`는 `18rem`에서 `14rem`으로 줄여 전체화면 기준 한 줄에 4개가 들어오게 했다.
x축 라벨 겹침은 Chart.js의 autoSkip이 걸러주므로 문제되지 않았다.
좁아진 폭에서 종횡비 2는 세로가 답답하다는 피드백으로, 종횡비를 `2 / 1.3`으로 낮춰 세로폭을 1.3배 키웠다.

## 문제

[기획](../../기획/탐색-임베딩실험.md)대로 `/lab/embedding`에 탐색과 거의 같은 페이지를 만들되,

궤적은 메모리에만 있어 재진입 시 비고, 이후 응답마다 다시 쌓인다.

관계 로그가 수천 건을 넘어가면 매 스텝 전체 평가가 느려질 수 있다.
그때는 평가 표본 상한(예: 2000쌍 고정 무작위 표본)을 두거나 Web Worker로 옮긴다.

# 2026-07-31 문답 기록 페이지

## 문제

`/qna`에서 출제된 문제와 응답을 최근 목록과 같은 UX(기간 검색, 커서 페이지네이션)로 보여줘야 했다.

**표는 relations만 읽는다.** 관계가 문제의 단어 필드를 복사해 가지므로([탐색 Store](../../설계/저장-탐색.md))
`questions`를 조회할 필요가 없고, 관계 없는 문제 잔재는 저절로 빠진다. `qna/hydrateQnaEntries`가
한 페이지의 단어 id(문제 단어 + word형 answer/comment)를 중복 제거해 `getWordValues` 1회로 배치 해석하고,
문장은 `getSentence`를 `Promise.all`로 모은다. 응답 셀은 `QnaAnswer` 태그 유니온(text/skip/similarity/selection)으로
유형별 분기를 hydrate 시점에 끝내, 렌더 컴포넌트는 kind만 본다. 삭제된 대상은 빈 문자열로 해석돼 `(삭제됨)`으로 그린다.

# 2026-07-29 탐색 페이지

## 문제

[탐색 화면 사양](../../기획/화면/탐색.md)은 답안란에 "대시보드의 입력기가 그대로 사용된다"고 적었지만,
`WordWriter`와 `SentenceWriter`는 저장 뮤테이션과 저장 버튼을 자기 안에 들고 있어 그대로 쓸 수 없었다.
답안은 제출 버튼을 눌러야 저장되고, 그때 문제와 관계까지 함께 적재되어야 하기 때문이다.

또 사양의 "변경된 상태는 다음 출제되는 문제부터 적용된다"가 react-query와 어긋났다.
체크박스 상태를 `useState`로 들고 `queryFn`에서 읽으면, `refetch()`는 그 시점의 `queryFn`을 즉시 실행하므로
바로 앞에서 `setState`한 값이 아니라 이전 렌더의 값을 쓴다.

## 해결

**입력 표현부만 Field로 뽑았다.** `WordField`는 `input`과 공백 에코 오버레이, `scrollLeft` 동기화를,
`SentenceField`는 `textarea`와 에코, `Tab` 삽입, `Ctrl + Enter`를 담는다. 둘 다 `value`/`onChange`를 받는 제어 컴포넌트다.
기존 Writer는 이것을 감싸며 저장 로직만 남겼고, 화면과 동작은 그대로다.

중복 단어 검사와 저장 버튼은 `WordWriter`에 남겼다. 대시보드에서는 이미 있는 단어를 또 저장할 이유가 없어 막아야 하지만,
탐색에서는 이미 있는 단어로 답하는 것이 오히려 정상이다. 같은 컴포넌트가 두 규칙을 다 만족할 수 없으므로 경계를 여기에 그었다.
`WordSuggestion`도 Field 밖에 뒀다. `WordWriter`는 `fieldset role=group` 안에 입력과 버튼을 나란히 두고 추천기를 그 아래에 놓으므로,
Field가 추천기까지 품으면 그 배치가 깨진다.

**대시보드의 모드 선택기를 공용으로 올렸다.** `routes/index.tsx`의 private 함수였던 것을
`writer/WriterModeSelector`로 옮기고 `modes`와 `name`을 받게 했다. 대시보드는 `단어`/`문장`/`문서` 셋을, 탐색은 둘을 넘긴다.
`name`을 받는 것은 한 화면에 라디오 그룹이 답안과 참고사항 둘이라, 이름이 겹치면 서로를 끈다.

**적용 시점은 `useRef`로 미뤘다.** 체크박스는 `useState`로 들되, 실제 출제에 쓰이는 유형은 `useRef`에 둔다.
건너뛰기와 제출이 `ref.current`를 갱신한 직후 `refetch()`를 부르므로, `queryFn`이 언제나 최신 값을 읽는다.
`useState`로는 갱신과 `refetch` 사이에 렌더가 끼어야 해서 한 박자씩 밀린다.

**출제 실패의 사유를 결과에 담았다.** `pickQuestion`이 `null` 대신
`{ status: 'ok' | 'noType' | 'noWord' }`를 돌려준다. 유형을 하나도 안 골라서 못 만든 것과 단어가 모자라 못 만든 것은
사용자에게 할 말이 다른데, `null` 하나로는 구분할 수 없고 화면이 ref를 들여다보게 만들면 렌더와 어긋난다.

**서술형과 범주형.** `AnswerSection`이 문제 유형으로 갈라, 서술형은 모드 선택기와 Field를,
범주형은 `ChoiceGroup`을 그린다. `ChoiceGroup`은 선택된 버튼에 클래스를 주지 않아 pico 기본(primary)을 쓰고,
나머지에 `secondary`를 준다. 최초에는 아무것도 선택되지 않아 제출이 막힌다.

`ExplorePage`는 단어 수 확인과 조립만 하고, 상태와 액션은 `useExplore`가, 문제와 답안의 렌더는 `ExploreForm`이 맡는다.
한 컴포넌트에 다 두면 60줄을 훌쩍 넘는다.

## 이후 조정

사용자 요청으로 네 가지를 더했다.

- 지시문과 대상 단어를 가로 중앙정렬했다.
- 참고사항을 `details`로 접었다. 선택 입력이라 평소에 자리를 차지할 이유가 없다.
- 참고사항 입력기의 placeholder에 `(optional)`을 넣었다. `WordField`와 `SentenceField`에 `placeholder` prop을 열었다.
- `WordExplain`과 `WordsUsage`는 문장으로만 답하게 했다.

마지막 항목은 모드 목록을 `TextWriterField`의 `modes` prop으로 올려 해결했다. 목록이 하나면 선택기를 그리지 않는다.
다만 `AnswerDraft.mode`는 문제 유형과 무관하게 살아 있으므로, 유형이 허용하지 않는 모드가 남아 있을 수 있다.
`getAnswerMode(type, mode)` 하나를 두고 화면과 `submitAnswer`가 함께 쓴다.
화면에서만 고정하면 저장 쪽이 옛 모드로 단어를 만들어버린다. 반대로 저장에서만 막으면 화면과 실제 결과가 어긋난다.

관계의 `answer` 타입은 `WordOrSentence` 그대로 뒀다. 어떤 유형이 무엇으로 답하는지는 앞으로 또 바뀔 수 있고,
이미 저장된 관계는 그 시점의 규칙을 따른다. 좁히면 옛 데이터가 타입에서 밀려난다.

## 유형 미선택에서 빠져나오지 못하던 버그

유형을 전부 해제하고 건너뛰면 `noType` 안내가 뜨는데, 이 화면은 폼 전체를 대체하므로 건너뛰기 버튼이 없다.
`appliedTypes`는 `useRef`이고 그것을 갱신하는 곳은 건너뛰기와 제출뿐이라, 유형을 다시 체크해도 갱신할 경로가 사라진다.
화면이 안내에 영영 고정됐다.

"변경된 상태는 다음 출제되는 문제부터 적용된다"는 사양이 **현재 문제가 있을 때**의 이야기임을 놓친 것이 원인이다.
문제가 없으면 다음 출제란 곧 지금이다. 체크 변경 시 `pick.status`가 `'ok'`가 아니면 `ref`를 갱신하고 바로 다시 뽑게 했다.
`noWord`도 같은 처지였으므로 함께 풀렸다.

안내 화면에 건너뛰기 버튼을 남기는 방법도 있으나, 유형을 고치는 것이 곧 해결책인 상황에서 버튼을 한 번 더 누르게 할 이유가 없다.

## 참고사항 상시 노출과 답안란 높이 통일

`details`로 접어둔 참고사항은 있는 줄도 모르게 됐다. 접기를 걷어내고 항상 보이게 되돌렸다.

문제 유형마다 답안란 높이가 달라, 유형이 바뀌면 참고사항과 버튼이 위아래로 움직였다.
실제로 재보니 범주형은 82px, 서술형 단어 모드는 133px, 문장 모드는 306px이었다.
사용자는 예문 만들기가 가장 높다고 봤지만 그것은 256px이고, 최대는 단어/문장 선택기 한 줄이 더 붙는 서술형 문장 모드다.
256px에 맞추면 그 경우에만 다시 흔들리므로 306px 쪽을 기준으로 삼았다.

값은 `min-height: calc(256px + 3.5rem)`이다. 처음에 `20rem`으로 뒀더니 400px이 나왔는데,
pico가 뷰포트에 따라 루트 폰트를 16~20px로 바꾸기 때문이다. 문장 입력기의 최소 높이 256px는 사양상 고정값이라 `px`로 두고,
폰트를 따라 커져야 하는 선택기 한 줄만 `rem`으로 잡았다. 어느 뷰포트에서도 최대 경우를 덮으면서 과하게 부풀지 않는다.

`height`가 아니라 `min-height`인 것은, 단어 모드에서 `WordSuggestion`이 최대 16개까지 늘어나기 때문이다.
그것은 입력 중에만 생기는 변화라 유형 전환의 흔들림과는 다른 문제다.

## 제시 순서 섞기와 중앙정렬

`getRandomWords`가 순번을 오름차순으로 정렬해 커서를 전진시키다 보니, 뽑힌 단어가 늘 추가 시각 순으로 나왔다.
어떤 단어가 뽑히는지는 균등 무작위였지만 그들 사이의 순서는 고정이었다. 사람은 먼저 본 것에 끌리므로 이것이 응답에 섞인다.
정렬은 커서 전진에 필요하므로 그대로 두고, 읽어온 뒤 Fisher-Yates로 섞었다.

답이 대상 단어 중 하나를 고르는 것이면 같은 단어가 지시문 아래와 선택지에 두 번 나온다.
`checkIsWordChoice`로 갈라 그런 유형에서는 대상 단어 목록을 그리지 않는다. 지금은 삼항 격리뿐이다.
그러자 지시문 영역 높이가 100px에서 30px로 줄어 버튼이 70px 올라갔다. 답안란에만 `min-height`를 준 것으로는 부족했던 것이다.
지시문 영역도 `min-height: 5rem`에 세로 중앙 정렬을 줬다. 단어 목록이 없어도 지시문이 영역 한가운데 놓인다.

선택지와 모드 선택기가 컨테이너 폭까지 늘어나는 것은 `width: fit-content`로 막았는데, `margin-inline: auto`가 먹지 않았다.
pico conditional의 `.pico [role=group]`이 특이도로 이기기 때문이다. 특이도를 더 올리는 대신 감싸는 요소를 하나 두고
거기에 `justify-content: center`를 줬다. 특이도 싸움은 pico를 올릴 때마다 다시 터진다.

폭을 줄이자 `단어`와 `문장` 라디오가 붙어버렸다. `[role=group]`이 원래 자식을 붙이는 버튼 그룹 스타일이라 그렇다.
`gap`으로 떼어놨다. 이 조정은 탐색 쪽 감싸개 안에서만 걸리므로 대시보드의 모드 선택기는 그대로다.

## 높이 고정이 만든 여백을 다시 줄이기

앞의 높이 고정에는 두 가지 결함이 있었다.

**첫째, 남는 공간이 전부 아래로 몰렸다.** `min-height`만 주고 내부 정렬을 주지 않아 내용이 위에 붙었다.
`justify-content: center`로 위아래에 고르게 나눴다.

**둘째, 지시문과 답안이 각자 여백을 가져 둘 사이가 벌어졌다.** 지시문 영역과 답안 영역에 각각 `min-height`를 주고
각각 중앙 정렬했더니, 지시문 아래 여백과 답안 위 여백이 겹쳐 삼항 격리에서 둘 사이가 93px이 됐다. 한 문제로 읽히지 않았다.
두 영역을 한 덩어리로 묶고 그 전체에만 `min-height`와 중앙 정렬을 줬다. 이제 유형별 차이가 덩어리 바깥의 위아래 여백으로만 간다.

그래도 범주형은 여백이 컸다. 기준값이 문장 입력기의 최소 높이 256px에서 나오는데,
탐색의 답안은 한두 문장이라 대시보드용 높이가 과했다. 탐색 안에서만 128px로 낮춰 덩어리 높이를 348px로 줄였다.
삼항 격리의 위아래 여백이 122px에서 98px로, 이항 서술형은 97px에서 38px로 줄었다.
사양상 256px는 [재사용 컴포넌트](../../기획/화면-컴포넌트.md)의 값이므로 `SentenceField` 자체는 건드리지 않고
탐색 쪽 감싸개에서 덮었다. 여기서도 `.pico` 특이도가 필요했다.

`min-height`를 `calc(128px + 11rem)`으로 잡은 것은, 최대 경우가 지시문 한 줄과 단어 한 줄, 모드 선택기, 문장 입력기를
모두 쌓은 이항 서술형의 문장 모드이기 때문이다. 처음 잡은 `8.5rem`으로는 그 경우만 40px 넘쳐 참고사항이 밀렸다.

# 2026-07-25 WordWriter 존재 확인 전 저장 차단

## 문제

`isExisting`이 100ms 스로틀된 값과 비동기 쿼리 결과에 의존해서, 단어를 치고 곧바로 Enter를 누르면
존재 확인이 끝나기 전에 `saveWord`가 실행됐다. `createWord`는 기존 단어면 no-op이라 데이터는 안전하지만,

`isChecking = throttledValue !== value || isFetching`을 두고, 제출 가드와 저장 버튼 `disabled`에 추가했다.
스로틀이 아직 안 따라온 창과 쿼리 fetching 중인 창 모두에서 저장이 잠긴다.
`isExisting`은 `!isChecking && typeof existingNodeId === 'number'`로 바꿔 확인이 끝난 뒤에만 참이 된다.

# 2026-07-23 최근 목록 날짜 표기와 네비게이터 크기

## 문제

날짜가 `Intl`의 `ko-KR` `dateStyle: 'short'` + `timeStyle: 'short'`라 `26. 7. 23. 오후 3:04`처럼 나왔다.
자릿수가 들쭉날쭉하고 `오전`/`오후`가 전각이라 mono 표에서 폭을 많이 먹는다.

페이지 네비게이터는 `PageNavigator.module.css`에 `justify-content: center`가 있는데도 버튼이 컨테이너 양끝으로 벌어졌다.

## 해결

`formatMinute`을 `YY-MM-DD HH:mm` 24시간제로 바꿨다. `getHours()`가 이미 24시간제이므로 `padStart(2, '0')`만 하면 된다.
`formatDateTimeLocal`과 자릿수 패딩이 똑같아 `splitDateTime`으로 뽑고 둘이 나눠 쓴다. 연도는 4자리로 만든 뒤 `slice(2)`로 두 자리를 취한다.
표 기준 날짜 열은 360px에서 160px에서 106px로 줄었고, 그만큼 내용 열이 77px에서 131px로 늘었다.

네비게이터는 또 conditional pico의 specificity 문제였다. `.pico nav`(0-1-1)의 `justify-content: space-between`이 `.root`(0-1-0)를 이긴다.
`:global(.pico) .root`(0-2-0)로 올려 해결했다. 같은 이유로 `.root button`(0-1-1)의 padding도 그동안 pico에 지고 있었고,
그래서 버튼이 50px 높이로 나오고 있었다. 승격 후에는 여기 적은 값이 실제로 먹으므로, **화면에 보이던 크기**의 80%가 되도록
`font-size: 0.8rem`, `min-width: 2.4rem`, `padding: 0.6rem 0.8rem`으로 잡았다. playwright로 재보니 50px→40px(360px 뷰포트),
56px→45px(768px 뷰포트)로 정확히 80%다. pico의 root font-size가 뷰포트마다 달라지므로 `em`이 아니라 `rem`으로 적어야 그 비율이 유지된다.

# 2026-07-23 최근 목록 표의 좁은 폭 대응

## 문제

`RecentTable`이 `white-space: nowrap`만 걸고 있어, 폭이 좁으면 표가 `article` 밖으로 튀어나가 페이지 전체에 가로 스크롤이 생겼다.
내용은 48자, 출처는 16자로 이미 자르지만 그 길이도 좁은 화면에는 넘친다.

## 해결

열마다 우선순위가 다르다. 날짜는 잘리면 못 읽으니 온전해야 하고, 내용과 출처는 줄임표로 잘려도 된다.

- `table-layout: fixed`는 쓰지 않았다. 그러면 날짜 열 너비를 `em`으로 어림해야 하는데, 폰트와 `font-size`가 바뀌면 어긋난다.
- 대신 auto 레이아웃에서 내용·출처에 `max-width: 0`, 날짜에 `width: 1%`를 줬다. 날짜는 min-content로 딱 붙고 남은 폭이 내용·출처로 간다. 출처는 `width: 20%`로 몫을 정했다.
- 세 열 모두 `overflow: hidden` + `text-overflow: ellipsis`. 셀에 클래스를 달아야 해서 `th`/`td`에 `value`, `source`, `date`를 부여했다.
- 576px 이하에서는 `font-size: 0.875em`과 좁은 `padding-inline`으로 pico 기본 좌우 여백(셀당 2rem)을 줄였다. 이 여백이 360px에서 폭의 1/4을 먹고 있었다.

playwright로 360/420/768/1280에서 `documentElement.scrollWidth === innerWidth`와 날짜 열 미절단을 확인했다. 360px에서 내용 열은 77px까지 줄어드는데, 날짜를 온전히 두는 이상 더 줄일 수 없는 값이다.

# 2026-07-23 문장의 선택적 출처

## 문제

출처는 문서에만 있었다. 인용문처럼 어디서 왔는지가 중요한 문장을 넣을 때 그 정보를 둘 곳이 없었다.
`DocumentWriter`의 출처 `label` + `input`을 `SentenceWriter`로 복사하면 같은 마크업이 두 벌이 된다.

## 해결

`writer/SourceField`로 뽑고 양쪽이 쓴다. `{ value, isEditable, onChange }`만 받으며 어떤 타입의 출처인지 모른다.
`useWriterForm`의 draft가 이미 문자열 레코드라 문장의 draft를 `{ value, source }`로 늘리는 것 외에 폼 로직은 건드릴 것이 없었다.

- 저장·수정 시 빈 출처의 키를 지우는 규약은 문서와 동일하다. `updateSentence`에 `delete sentence.source`를 넣었다.
- `RecentSentence`는 `Omit<Sentence, 'modifiedAt'>`이라 그대로 두면 `source`가 딸려 들어온다. 최근 목록은 본문만 보여주므로 `'source'`도 `Omit`에 더해 사본이 늘지 않게 막았다.
- mono 폰트 지정도 `SourceField.module.css`로 옮겼다. 옮기면서 `.source`(0-1-0) 하나로 줄일 뻔했는데, 그러면 pico의 `.pico input { font-family: inherit }`(0-1-1)에 진다. `DocumentWriter`가 `.root .source`(0-2-0)로 이기고 있던 것이므로 `label`에 `.root`를 주고 중첩 구조를 그대로 가져왔다.

## 남은 것

브라우저 확인을 하지 않았다. 이번 세션에는 playwright가 없어 타입 검사와 lint까지만 했다. 출처 `input`의 폰트, 문장 페이지에서 출처만 고쳤을 때의 수정 버튼 활성, 출처 유무별 저장 결과는 눈으로 봐야 한다.

# 2026-07-22 개별 항목 메타 정보 그리드

## 문제

단어/문장/문서 페이지가 각자 `<p>id: ...</p>` 한 줄만 보여줬다. `createdAt`, `modifiedAt`, `parentNodeId`는 아예 노출되지 않아 저장이 제대로 됐는지 화면으로 확인할 수 없었다.
세 페이지가 다루는 타입이 서로 달라 페이지마다 표시 코드를 따로 쓰면 세 벌이 된다.

## 해결

`meta/MetaFields`를 만들었다. `{ label, value }[]`만 받고 값의 출처를 모르는 읽기 전용 폼이다.

- `value`는 `string | number | Date | undefined`. `Date`는 `Intl.DateTimeFormat('ko-KR')`로, `undefined`는 `없음`으로 찍는다. 페이지가 포맷을 신경 쓰지 않는다.
- 렌더는 `label` + `input[readOnly]`로, `repeat(auto-fit, minmax(12rem, 1fr))` 그리드에 얹었다. 항목 수가 3개든 5개든 폭에 맞춰 접힌다. 값을 드래그해 복사할 수 있으므로 `p`보다 낫다.
- 단어 페이지는 `nodeId`만으로는 부족해 `getWordNode`(노드 전체 반환)를 추가하고, 기존 `getWordNodeId`를 그 위에 얹어 순회 로직 중복을 없앴다. 쿼리 키 `wordNode`도 무효화 대상에 넣었다.

문서의 `source`는 `DocumentWriter`가 편집하는 값이므로 메타에 넣지 않았다.

# 2026-07-22 문서 입력기와 개별 문서 페이지

## 문제

문서는 문장과 구조가 거의 같고 출처와 파일 드롭만 더 있다. 그대로 만들면 폼 로직이 두 벌, 버튼 행과 최근 목록이 세 벌이 된다.

## 해결

겹치는 것을 먼저 뽑고 문서를 얹었다.

- `writer/useWriterForm`: draft를 `{ value: string }`을 포함하는 문자열 레코드로 두고, 더티 판정은 초기 draft의 키만 얕게 비교한다. 문장은 `{ value }`, 문서는 `{ value, source }`다. 저장·삭제 뮤테이션, 생성 모드의 저장 후 초기화, 이탈 질의, `canSave`가 전부 여기로 왔다. `useSentenceWriterForm`은 지웠다.
- `writer/WriterActions`: 저장/수정/삭제 버튼 행.
- `recent/RecentLines`: 최근 목록의 `article` + `h2` + `ul`과 줄임표 CSS. `RecentWords`는 inline flex로 표현이 달라 그대로 뒀다.

문서만의 것들이다.

- 출처가 빈 문자열이면 저장·수정 시 키 자체를 지운다. `source: undefined`로 넣으면 IndexedDB에 키가 남는다. `getAll`로 `'source' in item === false`를 확인했다.
- 파일 드롭은 `dragover`를 `preventDefault`해야 `drop`이 온다. `preventDefault`는 `await`보다 먼저 부른다. 내용은 `file.text()`로 읽고 출처에 파일 이름을 넣는다.
- `preview`는 64자로 자르되 마지막이 상위 서로게이트면 한 글자 줄인다. 이모지가 반토막 나는 것을 막는다.
- 공백 에코는 달지 않았다. 기획이 탭을 보여주지 않아도 된다고 했고, 긴 산문에서 마커는 잡음이다. `Tab` 가로채기만 문장과 동일하다.
- `input`과 `textarea`의 mono 지정은 `.root` 하위로 중첩했다. pico의 `font-family: inherit`(0-1-1)을 이기려면 클래스 두 개가 필요하다.

타입 이름 `Document`는 DOM 전역과 겹치나 모듈 스코프라 안전하다. `DocumentWriter`에서 prop 이름 `document`가 전역 `document`를 가리는데, 그 안에서 전역을 쓸 일이 없고 쓰면 타입 에러가 나므로 그대로 뒀다.

검증은 playwright로 했다. 출처 유무별 저장 결과, 파일 드롭, `preview` 64자, 개별 문서 페이지의 값·출처 주입과 출처만 고쳤을 때의 수정 활성, 삭제 후 이동, 그리고 공용화로 건드린 문장 쪽 회귀를 확인했다.

개별 문장 페이지를 만들었으나 URL을 직접 치는 것 말고는 들어갈 길이 없었다.

`getRecentSentences`와 `RecentSentences`를 만들어 메인에 붙였다. `recentWords`와 같은 순환 큐라 읽는 방식도 같고, 칸 수만 4다. 순환 큐의 칸 수는 `sentence.service` 안의 `RECENT_SENTENCES_SIZE` 하나로 모았다.

문장은 개행을 품을 수 있는데, 링크 안에서는 일반 white-space 처리로 공백이 되므로 한 줄 미리보기로 그대로 쓸 수 있다. 길이 제한은 JS로 자르지 않고 `text-overflow: ellipsis`로 처리한다. 기획이 CSS로 자르라고 명시했고, 잘린 글자 수가 폭에 따라 달라지는 편이 자연스럽다.

# 2026-07-22 문장 입력기와 개별 문장 페이지

## 문제

단어만 구현돼 있고 문장은 Store 스키마만 있었다. `SentenceWriter`는 대시보드에서는 생성, 개별 문장 페이지에서는 수정/삭제로 쓰여야 해서 한 컴포넌트가 두 역할을 겸한다.

## 해결

`sentence/`에 `types`, `consts`, `utils`, `sentence.service`(`createSentence`/`updateSentence`/`deleteSentence`/`getSentence`)를 두고, `SentenceWriter`는 `sentence` prop 유무로 생성/수정 모드를 가른다. 라우트는 `/sentence/$sentenceId`이며 `routeTree.gen.ts`는 `vite build`로 재생성했다.

- 폼 상태·뮤테이션·이탈 차단을 `useSentenceWriterForm`으로 뽑았다. 한 컴포넌트에 다 넣으면 함수 정의가 60줄을 넘는다.
- 미저장 수정 이탈 질의는 `useBlocker`의 `shouldBlockFn`에서 `confirm` 후 저장하고 **항상 `false`를 반환**한다. 확인이든 취소든 이탈 자체는 허용하는 것이 기획이다. `disabled`에 삭제 성공 여부를 넣어야 삭제 후 메인으로 나갈 때 질의가 뜨지 않는다.
- `getSentence`는 정수가 아닌 `sentenceId`에 `null`을 반환한다. URL이 망가지면 `IDBObjectStore.get(NaN)`이 `DataError`로 죽는다.
- 공백 에코가 `WordWriter`와 중복이라 `writer/WhitespaceEcho`로 뽑고 `WordWriter`도 이걸 쓰게 고쳤다. 문자 단위로 쪼개던 것을 `/([ \t])/` 캡처 split로 바꿨다. 공백이 아닌 구간을 통째로 두면 결합 문자나 서로게이트 페어가 span 경계로 갈라지지 않는다.

오버레이가 `textarea`와 1px도 어긋나면 안 되므로 정합에 관련된 것만 따로 적는다.

- pico가 `textarea`에 `font-family: inherit`(0-1-1)을 걸어 `.textarea`(0-1-0)의 mono 지정이 죽는다. `.textareaWrapper .textarea`(0-2-0)로 승격했다.
- 스크롤바가 생기면 `textarea`의 줄바꿈 폭만 줄어 에코와 어긋난다. 양쪽에 `scrollbar-gutter: stable`을 걸어 항상 같은 폭을 쓴다. `tab-size: 4`도 양쪽에 명시한다.
- pico의 `textarea` `margin-bottom`이 wrapper 안에 남아 에코 박스가 18px 더 길어졌고, `textarea` 경계 아래로 다음 줄이 새어 나왔다. 마진을 wrapper로 옮겨 두 박스를 정확히 겹쳤다.
- 버튼 폭은 `width: auto`를 포기했다. `.pico button[type=submit]`은 (0,2,1)이라 CSS Module의 `.actions .action`(0,2,0)이 진다. **속성 선택자는 클래스와 같은 자리를 차지한다.** 이기려면 선택자를 더 꼬아야 하는데, 제출 버튼만 full width이고 나머지는 auto인 pico 기본 모양이 나쁘지 않아 그대로 뒀다.

`Tab` 키는 처음에 가로채지 않았다. 기획의 "스페이스와 탭만으로도 입력할 수 있으며"를 단어 입력기의 대응 문장과 같은 구조로 읽어 저장 가능성과 가시성만 뜻한다고 봤고, 포커스 이동을 뺏는 접근성 손해를 피하려 했다. 사용자 판단으로 뒤집혔다. 저장이 `Ctrl + Enter`라 다음 요소로 갈 `Tab`이 필요 없다는 것이다. 문장·문서 입력기에 한해 가로채기로 하고 [재사용 컴포넌트](../../기획/화면-컴포넌트.md)에 명시했다.

- `writer/insertTabIfPressed`로 뽑았다. 문서 입력기도 같은 동작을 써야 한다.
- 삽입은 `document.execCommand('insertText', ...)`다. 값을 직접 만지면 브라우저 실행취소 스택이 끊기고 캐럿을 손으로 되돌려야 한다. deprecated지만 대체제인 `EditContext`는 아직 이르다. 이 호출은 `input` 이벤트를 발생시키므로 제어 컴포넌트의 `onChange`가 정상으로 탄다.
- `Shift + Tab`과 수정 불가 상태는 가로채지 않는다. 포커스가 갇히면 키보드만으로 폼을 빠져나갈 수 없다.

검증은 playwright로 했다. 생성(`Ctrl + Enter`), 편집 진입 시 값 주입, 수정 버튼 활성 조건, 수정 반영, 이탈 질의 후 저장, 삭제 후 메인 이동과 부재, 스크롤 동기화, `Tab` 삽입과 `Shift + Tab` 포커스 이동, `WordWriter` 회귀를 확인했다.

playwright는 저장소에 넣지 않는다. 이 규모에 E2E 테스트를 유지하는 부담이 더 크다는 사용자 판단이다. 확인이 필요할 때마다 임시 디렉토리에 설치해 쓴다. 브라우저 바이너리는 `~/.cache/ms-playwright`에 머신 전역으로 남아 재설치가 아니다.

# 2026-07-22 WordWriter 중복 단어 저장 차단

## 문제

`createWord`는 도착 Trie 노드에 `createdAt`이 있으면 no-op이라 데이터는 안전했지만, UI는 그 사실을 몰랐다. 이미 있는 단어를 다시 입력해도 저장 버튼이 활성화되고 `Enter`도 먹었다. 사용자에게는 저장을 눌렀는데 입력창만 비워지는 것으로 보였다.

## 해결

`WordWriter`에서 `getWordNodeId`를 100ms throttle된 입력값으로 조회해 `isExisting`을 만들고, 버튼 `disabled`와 `handleSubmit` 조기 반환에 반영했다. 새 서비스 함수는 만들지 않았다. `WORD_NODE_ID_QUERY_KEY`는 `word.$word.tsx`가 이미 쓰던 키라 캐시가 공유된다.

- `throttledValue === value` 가드를 함께 건다. throttle 지연 중의 조회 결과는 이전 입력값에 대한 답이므로, 그 사이에는 중복이 아니라고 본다. 잘못 비활성화하는 것보다 잠깐 활성화된 채로 두는 쪽이 낫다. 서비스가 no-op이라 최악이라도 무해하다.
- 판정은 `typeof existingNodeId === 'number'`다. 미조회는 `undefined`, 미존재는 `null`이라 둘 다 걸러야 하고, `nodeId` 타입상 `0`이 truthy 검사에 걸린다.

`WORD_NODE_ID_QUERY_KEY`가 그동안 어디서도 무효화되지 않던 것이 이 변경으로 실제 버그가 됐다. 저장/삭제 후 같은 문자열을 다시 입력하면 낡은 캐시가 먼저 반환되어 판정이 뒤집힌다. 특히 `WordSuggestion`에서 삭제한 단어를 다시 저장하지 못한다. 무효화 대상이 3개로 늘어 두 컴포넌트에 같은 블록이 복사되므로 `word/utils.ts`의 `invalidateWordQueries(queryClient)`로 뽑아 양쪽에서 호출한다.

앞뒤 공백 정규화(trim)는 사용자 결정에 따라 하지 않는다. 스페이스만으로도 단어를 만들 수 있다는 기존 사양과 충돌하기 때문이다.

# 2026-07-22 목록 bullet 제거를 전역화

## 문제

RecentWords의 `ul`에 `list-style: none`을 줬는데도 bullet이 사라지지 않았다.

## 해결

pico가 `.pico ul li { list-style: square }`로 `li`를 직접 지정하기 때문이다. 마커는 `li`에서 결정되므로, `ul`에 건 값이 상속되기 전에 이 규칙에 덮인다. 개별 모듈마다 `li`를 다시 지정하는 대신 `global.css`에서 기본값을 `ul`로 옮겼다.

```css
:where(.pico ul) {
  list-style: square;
}

.pico ul li {
  list-style: inherit;
}
```

`.pico ul`(0,1,2)로 쓰면 이번엔 그게 CSS Module의 `.list`(0,1,0)를 이겨서 다시 square가 된다. 실제로 이 실수를 한 번 거쳤고, 빌드 산출 CSS와 브라우저 `getComputedStyle`로 확인해서 잡았다. 기본값 규칙은 어떤 저자 클래스에도 져야 하므로 `:where`로 specificity를 0으로 만들어야 한다.

`.pico nav ul`, `details.dropdown` 등 pico가 `li`를 직접 지정하는 다른 규칙은 specificity가 더 높아 그대로 동작한다. `ol`은 pico가 건드리지 않아 영향이 없다.

# 2026-07-22 WordWriter 레이아웃 및 공백 에코 수정

## 문제

WordWriter에서 input이 좁게, 저장 button이 넓게 나오다가, 수정 후에는 "저장"이 세로로 꺾이고 높이가 어긋났다. 공백 표시용 `␣` 글리프는 뒤 글자와 겹쳤다.

## 해결

핵심 원인은 이 프로젝트가 `pico.conditional.min.css`를 쓴다는 점이다. 모든 pico 선택자가 `.pico` 하위로 스코프되어 specificity가 한 단계씩 높아지므로, CSS Module의 한 단계짜리 클래스 선택자로는 pico 규칙을 못 이기는 경우가 많다.

- 레이아웃은 커스텀 flex 대신 pico의 `fieldset[role=group]` 패턴으로 교체했다. input+button이 결합된 한 줄이 pico 규칙만으로 나온다.
- "저장" 세로 출력: `.pico [role=group] > *`(0-2-0)의 `flex: 1 1 auto`가 `.group button`(0-1-1)의 `flex-shrink: 0`을 이겼다. 한국어는 글자 사이 줄바꿈이 허용되어 min-content가 한 글자 폭이라 shrink 시 세로가 된다. specificity 경쟁 대신 pico가 안 건드리는 `white-space: nowrap`으로 해결했다.
- input 폰트: `.pico input { font-family: inherit }`(0-1-1)가 `.input`(0-1-0)의 mono 지정을 무효화해 echo(mono)와 글자 폭이 어긋났다. `.inputWrapper .input`(0-2-0)으로 승격했다.
- `␣` 글리프 겹침: 폰트에 U+2423이 없으면 폴백 글리프의 폭이 공백과 달라진다. 실제 공백 문자로 폭을 잡고 `::before` 테두리로 열린 상자를 그려 글리프 의존을 제거했다.
- 마커 미표시: pico group의 `input:focus { z-index: 2 }`가 포커스 중 echo를 가렸다. `.echo`에 `z-index: 3`을 부여했다.

검증은 playwright(scratchpad에 설치)로 실제 렌더링을 스크린샷·좌표 측정하여 수행했다. CSS 이론만으로 두 번 틀렸고, 브라우저로 본 뒤에야 원인이 확정됐다.

# 2026-08-04 범주 선택형 문제의 키보드 조작

## 문제

탐색과 임베딩 실험의 범주 선택형 문제(`BinarySimilarity`, `TernaryIsolation`)는 선택도 제출도 마우스를 요구했다.
답이 한 번의 판단으로 끝나는 유형이라, 손을 옮기는 비용이 판단 자체보다 컸다.

## 해결

`ChoiceGroup`에 `hasKeyboardShortcut`, `onSubmit` prop을 더하고, 실제 처리는 `useChoiceShortcut`으로 분리했다.
숫자키 `1` ~ `N`은 해당 순번 선택지를, Enter는 선택된 상태에서 제출을 수행한다(`window`의 `keydown` 구독).

`ChoiceGroup`은 임베딩 실험의 모델 선택기(`ModelSelector`)도 쓰므로, 단축키는 opt-in으로 두어 `AnswerSection`에서만 켰다.

가로채면 안 되는 경우를 두 갈래로 나눴다.

- `checkIsTyping`: `input`(체크박스 등 비입력 타입 제외), `textarea`, `select`, `contenteditable`에 포커스가 있으면 무시한다.
  참고사항 입력 중의 숫자와 Enter를 뺏지 않기 위함이다. `isComposing`도 같이 걸러 한글 조합 확정을 제출로 오인하지 않는다.
- `checkIsForeignControl`: Enter에 한해, 그룹 바깥의 `button`/`a`/`summary`에 포커스가 있으면 무시한다.
  선택지 버튼을 클릭하면 포커스가 그 버튼에 남으므로 그룹 안쪽은 통과시켜야 하고, 반대로 건너뛰기 버튼의 Enter는 건너뛰기여야 한다.

제출 자체는 `useExplore.save`가 `isSubmittable`로 이미 막고 있어 별도 방어를 두지 않았다.

# 2026-08-07 알려주기 단어 입력기의 주사위 버튼

## 문제

알려주기 페이지에서 대상 단어를 항상 사용자가 직접 떠올려야 해서, 무엇을 가르칠지 막막할 때 시작 비용이 컸다.

## 해결

각 단어 칸 오른쪽에 🎲 버튼(이모지 금지 규칙의 사용자 승인 예외)을 두고, 기존 `getRandomWords`로 DB의 랜덤 단어를 그 칸에 채웠다. `hasRandomPick` prop을 `relation.new.tsx → RelationPage → RelationForm → SubjectWordFields`로 내려 알려주기에서만 켜고, 같은 구성을 쓰는 관계 수정 페이지는 손대지 않았다.

- DOM 안정성: 버튼이 없는 경로에서는 `fieldset[role=group]` 래핑 자체를 하지 않아 수정 페이지의 DOM이 변하지 않는다. 연타 중복 실행은 `isRolling` 가드로 무시하되 콜백 자체는 유지해 입력기 리마운트(포커스 손실)를 피했다.

# 2026-08-13 오프라인 중첩 경로 새로고침 수정

## 문제

오프라인에서 `/relation/new`처럼 2단계 이상 경로를 새로고침하면 화면이 뜨지 않았다.
SW의 `navigateFallback`이 해당 URL에서 `index.html`을 그대로 응답하는데, `base: './'`의
상대 자산 경로가 문서 URL 기준으로 해석되어 `./assets/...` → `/relation/assets/...`가 되고,
이 URL은 프리캐시에 없어 로드가 실패했다. `/explore` 같은 1단계 경로는 우연히 경로가
맞아떨어져 멀쩡했고, `/recent/documents` 등 깊이 2 이상은 전부 같은 문제였다.
2026-08-08 PWA 작업에서 온라인 404.html에 대해 인지했던 문제(상대 base + fallback 문서)를
workbox `navigateFallback`이 오프라인에서 재현한 것이다.

## 해결

`index.html` head의 자산 태그 앞에 인라인 스크립트를 추가했다. SW가 문서를 서빙하는 경우
`navigator.serviceWorker.controller.scriptURL`(동기 접근 가능)에서 앱 루트를 계산해
`<base>`를 주입한다. 이후 파싱되는 자산 태그의 상대경로가 SW 스코프 기준으로 풀려
어떤 깊이에서도 프리캐시에 적중한다. 배포 무영향 제약에 따라 `base: './'`는 유지했다.

- SW 미제어 상태(첫 방문, dev)에서는 controller가 없어 아무 일도 하지 않는다.
- 알려진 잔여: Chromium preload scanner가 base 삽입 전에 원본 바이트를 미리 스캔해
  잘못된 URL로 투기적 요청을 보내고 콘솔에 실패가 남는다. 실제 파서 시점 로드는 base가
  적용되어 성공하므로 무해하다. 완전 제거는 injectManifest 커스텀 SW로 fallback 응답
  본문에 base를 새겨야 하는데, 수동 SW 유지비용 대비 이득이 없어 하지 않았다.
- 검증: playwright로 `vite preview`에 SW 등록 후 오프라인 전환, `/relation/new`,
  `/recent/documents`, `/explore`, `/` 새로고침에서 렌더링과 CSS 적용을 확인했다.

# 2026-08-13 답안 확정 시 참고사항으로 포커스 이동 후 제출

## 문제

알려주기의 관계 짓기만 "단어칸 Enter → 포커스 전진 → 참고사항에서 Enter 제출" 흐름이었고,
나머지 유형(탐색·알려주기 공통)은 답안 지점에서 Enter가 곧바로 제출로 이어졌다.
경로가 세 갈래로 흩어져 있었다: 단어 답안은 `WordField`에 `onEnter`가 없어 브라우저 암묵적
폼 제출, 문장 답안은 `SentenceField` Ctrl+Enter → `save`, 범주형은 `useChoiceShortcut`의
window keydown 리스너가 Enter에 `save` 호출. 답안 모드 라디오(단어/문장)에 포커스가 있을 때의
Enter도 암묵적 제출이라 참고사항을 건너뛰는 회피 제출 구멍이었다.

## 해결

"답안에서의 확정 입력 = `focusNextElement`로 참고사항 영역 이동, 제출 = 참고사항에서만"으로 통일했다.

- `TextWriterField`: `onSubmit` prop을 `onComplete`(이 필드의 확정 동작)로 교체.
  단어 모드는 `WordField`에 `onEnter`(추천 목록 `leave` 후 `onComplete`)를 연결해 암묵적 제출을
  제거했고, 모드 라디오 래퍼에 Enter keydown을 달아 `preventDefault` 후 `onComplete`를 호출한다.
  답안 용도에서는 이동, 참고사항 용도에서는 `save`가 되어 라디오 회피 제출 구멍도 막힌다.
- `AnswerSection`: `onSubmit` prop 제거, 자체 ref div로 감싸 `onComplete`에 이동을 연결. 폼에서
  `save`를 내려받을 필요가 없어졌다.
- `useChoiceShortcut`: Enter를 "선택 존재 + target이 선택지 내부이거나 body"일 때만 가로채
  `focusNextElement`로 바꿨다. 그 외(참고사항 라디오/입력칸, 건너뛰기 버튼 등)는 네이티브 동작에
  맡기므로 기존 `checkIsForeignControl`은 제거했다. 숫자키 선택은 그대로다.
- `ANSWER_INPUT_SELECTOR`에 `button:not([disabled])` 추가. 새 흐름에선 제출 시점 포커스가
  참고사항에 있으므로, 재포커스가 범주형의 첫 선택지 버튼에 닿지 않으면 연속 출제에서 숫자키가
  참고사항에 글자로 입력돼버린다.
- 기획 문서(`기획/화면/탐색.md`, `기획/화면/알려주기.md`)의 제출 키 사양을 갱신했다.
- 검증: playwright로 dev 서버(5173)에 붙어 알려주기(이항 공통점·유사성·관계 짓기 회귀·미선택
  Enter 무동작)와 탐색(범주형 재포커스, 문장 답안 Ctrl+Enter) 22개 체크 전부 통과. tsc, vitest 41개 통과.
