# 개요

`npm run analyze-llm`(ts_dependency_graph, 진입점 `main.tsx`)의 출력(DOT)을 파싱해 fan-in/fan-out/순환/디렉토리 결합을 계산한 결과다. 2026-08-23 기준 노드 282, 간선 914. 모듈 경계를 옮기거나 공용 타입·상수를 손대기 전에 읽는다.

# 병목 지점

## 1. `db/openNoemaDB.ts` -> `statistic/backfillCountLogs.ts` (인프라 계층의 역참조) — 2026-08-24 해소

- `onupgradeneeded`에서 `oldVersion < 9`일 때 `clearAndBackfillCountLogs(transaction)`를 호출했다. 이 한 줄로 `db/`가 `statistic/consts`·`types`·`utils`를 값 import 했다.
- 실질 비용은 세 가지였다. (1) 디렉토리 경계로 보면 `db <-> statistic`이 양방향이었다(`statistic.service` -> `openNoemaDB` -> `statistic/backfillCountLogs`). 인프라가 도메인을 참조하는 형태라 3번의 `explore <-> relation`보다 나쁘다. (2) 통계 스키마를 고칠 때마다 DB 업그레이드 경로까지 리뷰 대상이 됐다. (3) HMR 중간 상태에서 마이그레이션이 잘못 실행될 위험 구간이 화면 코드 저장까지 넓어졌다.
- 근거로 쓸 수 없는 것: **번들 크기**는 무의미했다. `statistic/utils.ts`의 외부 값 의존은 0이고(`QueryClient`는 `import type`) 딸려오는 건 순수 함수 몇 개뿐이라 tree-shaking 대상이다. **"27개 모듈 해방"도 틀렸다**(아래 실측 참고).

### 해결

통계의 저장 계층 지식을 `db/countLog/`로 내리고 `statistic/`을 순수 화면 계층으로 만들었다.

```
db/countLog/
  types.ts     CountKind, TimeUnit, ChartMode, Totals, CountLog
  consts.ts    CountKinds, TimeUnits, ChartModes, CountStores, CountStoreNames
  binning.ts   getBinDate, shiftBin, createEmptyLog, createLog
  backfill.ts  clearAndBackfillCountLogs (+ SourceStores)

statistic/
  types.ts     CountSeries
  consts.ts    쿼리키, BinCounts, 라벨, CountSeriesList, 색
  utils.ts     invalidateStatisticQueries, createBins, formatBinLabel
```

`migrations/`가 아니라 `countLog/`인 이유: `types`/`consts`/`binning`은 `getCountLogs`와 `recordCreation`이 상시 쓰므로 마이그레이션 전용이 아니다. 그 안에서 마이그레이션 전용인 것은 `backfill.ts` 하나뿐이다.

곁들여 `CountKinds`의 파생 방향을 뒤집었다. 이전에는 `CountKinds = CountSeriesList.map((s) => s.key)`로 저장 개념이 화면 상수(색·라벨)에서 파생됐다. 지금은 `db/countLog/consts`가 리터럴로 갖고, `statistic/consts`의 `CountSeriesList`가 `Record<CountKind, CountSeries>`를 `CountKinds` 순서로 배열화한다(항목 누락은 `Record`가 컴파일 타임에 잡는다).

### 실측 (해소 후, 노드 285 / 간선 923)

| 대상 | 전이 의존자 |
| --- | --- |
| `statistic/types.ts` | 121 -> 93 |
| `statistic/consts.ts` | 92 |
| `statistic/utils.ts` | 91 |
| `db/countLog/types.ts` | 124 |
| `db/openNoemaDB.ts` | 108 |

`db/* -> statistic/*` 간선은 0이 됐고 `statistic -> db/countLog` 단방향만 남았다. 그러나 **모듈 27개가 풀렸다는 예측은 실질적으로 빗나갔다.** `statistic/types`의 전이 의존자는 예측대로 93으로 줄었지만, 저장 계층 타입이 `db/countLog/types`로 이름을 바꿔 `openNoemaDB`(108)를 통해 앱 전체에 닿으므로 전이 의존자가 124다. 통계 **레코드 스키마**로부터의 재컴파일 격리는 애초에 불가능했다. 실제로 얻은 것은 화면 상수·유틸(색, 라벨, 쿼리키, `invalidateStatisticQueries`)로부터의 격리와 의존 방향의 단방향화다.

이 사례의 교훈: 전이 의존자 수는 병목의 근거가 되지 못한다(6번에서 브로커를 병목이 아니라고 판정한 논리와 같다). 방향과 계층이 근거다.

## 2. `relation/types.ts` (직접 import 65건, 전이 139건, 최근 3개월 변경 14회)

- 단일 파일에 `WordRelationType`, `WordKey`, 관계 레코드, 질문 타입 등이 함께 있어 한 타입을 고치면 explore/qna/tag/search/extraction 전부가 영향권에 든다. 변경 빈도도 상위권이라 fan-in x churn 곱이 가장 크다.
- `db/consts.ts`(40건)도 같은 양상이나 스토어 이름 상수라 변경 빈도가 낮아 덜 위험하다.
- 해결 방향: 변하지 않는 식별 타입(`WordKey`, `WordRelationType`)과 자주 변하는 draft/폼 타입을 분리한다.

## 3. `explore` <-> `relation` 양방향 결합 (26 / 19건)

- `explore -> relation`: `relation/types`, `relation/questionSpecs` 중심. 자연스러운 방향.
- `relation -> explore`: `useRelationEditor`, `submitRelation`, `updateRelation`, `loadRelationSnapshot`, `createRelationDraft`, `RelationForm`이 `explore/types`(`AnswerDraft`, `CommentDraft`, `QuestionDraft`), `explore/consts`(`EmptyAnswer`, `EmptyComment`), `explore/submitAnswer`, `createNewRelation`, `createSource`, `getAnswerModes`, `AnswerSection`, `TextWriterField`를 가져온다.
- 즉 "답변 초안" 도메인이 `explore`에 놓여 있고 `relation` 편집기가 그것을 재사용한다. 두 디렉토리는 사실상 하나의 관심사인데 파일 위치만 갈라져 있어, 어느 한쪽을 고칠 때 다른 쪽을 항상 열어봐야 한다. 직전 커밋(질문 유형 라벨을 `QuestionSpecs`로 이관)도 이 역방향 간선을 줄이는 작업이었다.
- 같은 패턴이 `word <-> relation`(10 / 6)에도 있다.
- 해결 방향: `AnswerDraft`/`CommentDraft`/`submitAnswer`/`createNewRelation`/`createSource` 등 "관계 생성 도메인"을 `relation/answer/` 같은 곳으로 내리고 `explore`는 순수 소비자로 만든다.

## 4. 순환

- `word/WordReplaceDialog` <-> `word/WordSuggestion` (값 import 양방향, 실제 순환)
- `explore/ChoiceGroup/useChoiceShortcut` -> `ChoiceGroup`은 `import type`이라 컴파일 후 사라진다. ts_dependency_graph가 type import를 구분하지 않아 순환으로 잡힐 뿐, 실제 병목이 아니다.

## 5. 페이지 조립 지점 (fan-out)

- `RelationPage.tsx`(전이 107), `RelationForm.tsx`(94), `routes/relation.$relationId.tsx`(134)가 앱 전체의 1/3 이상을 끌어온다. 관계 화면이 가장 무거운 조립점이므로 위 1~3을 풀 때 회귀 검증의 기준 화면으로 삼는다.

## 6. 브로커(fan-in과 fan-out이 모두 큰 모듈)

- `word/utils.ts`(전이 in 44 / out 16), `relation/utils.ts`(27/22), `sentence.service.ts`(51/12), `qna/hydrateQnaEntries.ts`(24/26).
- out이 큰 정체: `relation/utils` -> `word/utils` -> `statistic/utils` 식의 `invalidateXxxQueries` 호출 사슬. 각 도메인 `consts.ts`의 query key가 전부 딸려온다. "관계가 바뀌면 단어·문장·태그·통계·S2W·D2S 캐시를 무효화한다"는 도메인 규칙을 코드로 적은 결과이지 파일이 복잡한 게 아니다.
- 병목이 아닌 이유: 새 query key 추가는 해당 도메인 `consts.ts`와 그 도메인의 invalidate 함수만 고치면 되고 상위 사슬은 자동 포함. 함수 시그니처가 `(queryClient) => void` 하나뿐이라 내부 목록이 바뀌어도 13개 호출처는 변경되지 않는다(in은 재컴파일 범위이지 수정 범위가 아니다). 서비스/하이드레이션 파일은 DB와 화면을 잇는 게 역할이라 양쪽이 큰 것이 정의이며, 변경 빈도 상위 15개에도 없다.
- 남겨 두는 이유: 도메인이 더 늘어 "관계 하나 저장 -> 앱 캐시 전체 무효화"에 가까워지면 성능 또는 누락 추적 문제가 된다. 그때 손댈 후보.
