# 탐색의 경우

- 상위문서: [타입별 Store](./저장-스토어.md)
- 문제와 관계의 개념, 문제 유형별 지시문은 [탐색 기획](../기획/탐색.md)에 있다.
- 화면의 동작은 [탐색 화면 사양](../기획/화면/탐색.md)에 있다.

탐색은 두 Store를 쓴다. 출제된 문제를 담는 `questions`와, 그 답으로 만들어진 관계를 담는 `relations`다.
둘 다 답을 제출할 때만 함께 쓰인다. 건너뛰면 어느 쪽에도 쓰지 않는다.

## 공용 타입

```ts
type WordOrSentence = {
  type: 'word' | 'sentence'
  id: number
}
```

`type`이 `'word'`면 `id`는 `wordNodes`의 `nodeId`이고, `'sentence'`면 `sentences`의 `sentenceId`다.
앞으로 문서를 가리키는 관계가 생길 수 있으므로, 이 자리는 값이 늘어나는 것을 전제로 다룬다.

`Similarity`는 다섯 단계의 수치다. Eraseable Syntax 제약으로 `enum`을 쓸 수 없어 리터럴 유니온과 상수 배열로 표현한다.

| 표시 | 값 |
| ---- | ---- |
| 매우 반대 | -1 |
| 약간 반대 | -0.5 |
| 서로 무관 | 0 |
| 약간 비슷 | 0.5 |
| 매우 비슷 | 1 |

## Question Store

Store 이름은 `questions`. Key Path로 `questionId`를 가지며 자동 증가한다.
`type`으로 갈라지는 태그 유니온이며, 유형별로 대상 단어를 담는 필드가 다르다.

```ts
interface QuestionBase {
  questionId: number
  createdAt: Date
}

type Question =
  | (QuestionBase & { type: 'WordExplain'; wordId: number })
  | (QuestionBase & { type: 'WordsUsage'; wordIds: number[] })
  | (QuestionBase & { type: 'BinaryCommon'; word1Id: number; word2Id: number })
  | (QuestionBase & { type: 'BinaryDifference'; word1Id: number; word2Id: number })
  | (QuestionBase & { type: 'BinarySimilarity'; word1Id: number; word2Id: number })
  | (QuestionBase & { type: 'BinaryAssociation'; wordId: number })
  | (QuestionBase & { type: 'TernaryIsolation'; word1Id: number; word2Id: number; word3Id: number })
```

출제 자체는 저장하지 않는다. 화면이 들고 있는 것은 `questionId`와 `createdAt`이 없는 초안이며,
제출 순간에 `add`가 `questionId`를 발급하고 그때의 시각이 `createdAt`이 된다.
따라서 건너뛴 문제는 `questionId`를 소비하지 않는다.

## Relation Store

Store 이름은 `relations`. Key Path로 `relationId`를 가지며 자동 증가한다.
`questionId`로 자신을 낳은 문제를 가리킨다.
[개별 관계](../기획/화면-페이지.md) 화면에서 고칠 수 있으므로 `modifiedAt`을 가지며, 한 번도 고치지 않았으면 없다.

```ts
interface RelationBase {
  relationId: number
  questionId: number
  createdAt: Date
  modifiedAt?: Date
  comment?: WordOrSentence
}

type Relation =
  | (RelationBase & { type: 'WordExplain'; wordId: number; answer: WordOrSentence })
  | (RelationBase & { type: 'WordsUsage'; wordIds: number[]; answer: WordOrSentence | null })
  | (RelationBase & BinaryWords & { type: 'BinaryCommon'; answer: WordOrSentence | null })
  | (RelationBase & BinaryWords & { type: 'BinaryDifference'; answer: WordOrSentence | null })
  | (RelationBase & BinaryWords & { type: 'BinarySimilarity'; similarity: Similarity })
  | (RelationBase & BinaryWords & { type: 'BinaryAssociation' })
  | (RelationBase & TernaryWords & { type: 'TernaryIsolation'; selection: 1 | 2 | 3 })
```

`BinaryWords`는 `word1Id`, `word2Id`를, `TernaryWords`는 거기에 `word3Id`를 더한 것이다.
문제의 대상 단어를 관계가 그대로 복사해서 갖는다. `questionId`를 따라가지 않고도 관계만으로 조회할 수 있어야 하기 때문이다.

`answer`는 `WordsUsage`, `BinaryCommon`, `BinaryDifference`에서 `null`일 수 있다.
`WordsUsage`는 말이 안 되는 단어 조합이 나와 응답을 회피한 경우고,
이항 공통점/차이점은 무응답(빈 문자열)을 제출한 경우다.
`answer`가 `null`인 관계는 `answer` 인덱스에서 저절로 빠진다.
`BinaryAssociation`은 답한 단어 자체가 `word2Id`이므로 `answer` 필드가 없다. 무응답도 없다.
기존 `word1Id`/`word2Id` 인덱스가 그대로 담으므로 새 인덱스나 버전 변경이 필요 없다.
`comment`는 어느 유형에서나 선택이며, 비어 있으면 키 자체를 두지 않는다. 문장/문서의 `source`와 같은 규약이다.

## 인덱스

`relations`는 참조 대상으로 거슬러 조회할 일이 많으므로, 대상을 가리키는 모든 필드에 인덱스를 둔다.

| 인덱스 | Key Path | 담기는 유형 |
| ------ | -------- | ----------- |
| `createdAt` | `createdAt` | 전부 |
| `wordId` | `wordId` | `WordExplain` |
| `wordIds` | `wordIds` (`multiEntry`) | `WordsUsage` |
| `word1Id` | `word1Id` | 이항, 삼항 |
| `word2Id` | `word2Id` | 이항, 삼항 |
| `word3Id` | `word3Id` | `TernaryIsolation` |
| `answer` | `['answer.type', 'answer.id']` | 답이 있는 유형 |
| `comment` | `['comment.type', 'comment.id']` | 참고사항이 있는 관계 |

`questions`는 `createdAt` 하나를 둔다.

Indexed DB는 Key Path가 `undefined`인 레코드를 인덱스에 넣지 않으므로, 각 인덱스는 그 필드를 가진 유형만 저절로 담는다.
유형을 걸러내는 별도의 조건이 필요 없다. `answer`가 `null`인 `WordsUsage` 관계도 같은 이유로 `answer` 인덱스에서 빠진다.

`answer`와 `comment`는 값이 `WordOrSentence`라 `type`과 `id`를 함께 봐야 한다. 복합 Key Path로 한 번에 조회한다.
`type` 자리가 문자열로 열려 있으므로, 앞으로 `'document'`가 들어와도 인덱스 정의를 고칠 일이 없다.

`wordIds`는 배열이므로 `multiEntry`로 둔다. 배열의 각 원소가 개별 키가 되어, 단어 하나로 그 단어가 쓰인 예문 관계를 찾을 수 있다.

## 제출 절차

이 절차는 탐색과 알려주기가 공유한다.
알려주기는 대상 단어를 사용자가 직접 입력하므로, 1번보다 먼저 대상 단어들을 `createWord`로 확보해 `nodeId`를 얻는다.

답안과 참고사항은 단어 또는 문장이며, 제출하는 순간에 만들어진다.
탐색에서 만들어진 문장의 `source`는 사용자가 적는 값이 아니라 그 문장을 낳은 문제로 정해진다.
따라서 `questionId`를 가장 먼저 발급한다. 순서는 다음과 같다.

1. `questions`만 범위로 하는 `readwrite` 트랜잭션에서 `questions.add`로 `questionId`를 발급받는다.
   이때의 시각이 `createdAt`이며, 관계도 같은 값을 쓴다.
2. 답안이 단어면 `createWord`, 문장이면 `createSentence`로 개체를 확보하고 그 ID를 받는다.
   `createWord`는 이미 있는 단어면 기존 `nodeId`를 그대로 돌려주므로 중복 단어가 생기지 않는다.
   문장의 `source`는 낳은 페이지에 따라 접두가 다르다. 단어에는 출처가 없다.
   - 탐색: `Harvest via NOEMA system exploration, qid=<questionId>`
   - [알려주기](../기획/화면/알려주기.md): `Taught via NOEMA system teaching, qid=<questionId>`
3. 참고사항도 같은 방식으로 처리하며, 문장이면 답안과 같은 `source`를 받는다.
   비어 있으면 아무것도 만들지 않고 `comment`를 넣지 않는다.
4. `relations`만 범위로 하는 `readwrite` 트랜잭션에서 `questionId`를 담아 `relations.add`한다.
   커밋 직후 [통계 구역](./화면-대시보드-통계구역.md)의 규약대로 `relationCount` 증가를 동기적으로 기록한다.

네 단계는 각자 트랜잭션을 열며 하나로 묶이지 않는다.
문장을 만들려면 발급된 `questionId`가 있어야 하는데, 한 트랜잭션 안에서 다른 트랜잭션을 기다리면
그 사이 대기 중인 요청이 없어 원래 트랜잭션이 먼저 커밋되기 때문이다.
단어와 문장은 그 자체로 독립된 데이터라, 관계 적재가 실패해 남더라도 고아가 되지 않는다.
문제는 관계 없이 남을 수 있으며, 이는 건너뛴 문제와 구분되지 않는다.

## 수정 절차

관계는 [개별 관계](../기획/화면-페이지.md) 화면에서만 고칠 수 있다. 유형은 고정이며 대상 단어, 답안, 참고사항만 바뀐다.
제출 절차와 순서가 같되 `add` 대신 `put`을 쓰고, `questionId`와 `createdAt`은 그대로 둔다.

1. 비어있지 않은 대상 단어를 `createWord`로 확보해 `nodeId`를 얻는다. 이미 있는 단어면 재사용한다.
2. `questions`를 `readwrite`로 열어 대상 단어 필드를 갈아끼운 문제를 `put`한다.
   문제 레코드가 없으면(먼저 지워졌으면) 건너뛴다.
3. 답안과 참고사항의 대상을 정한다.
   - 비어 있으면 `null`. `answer`는 `null`이 되고 `comment`는 키 자체가 빠진다.
   - 단어면 `createWord`로 확보한다. 원래 가리키던 단어는 손대지 않는다.
   - 문장인데 원래도 문장이었고 내용이 같으면, 기존 `sentenceId`를 그대로 쓴다.
   - 문장인데 내용이 달라졌으면 `createSentence`로 **새 문장**을 만든다.
     이때 `source`는 밀려난 문장의 것을 물려받아 출처를 보존하고, 물려받을 것이 없으면 알려주기 접두를 쓴다.
4. `relations`를 `readwrite`로 열어 `modifiedAt`을 지금으로 갱신한 관계를 `put`한다.
   관계 개수가 변하지 않으므로 통계에는 아무것도 기록하지 않는다.

밀려난 문장은 지우지 않는다. 문장은 그 자체로 독립된 데이터이며, 어떤 관계도 가리키지 않는 문장이
남아 있는 것은 이 시스템에서 정상 상태다.

## 삭제

관계를 지우면 그 관계를 낳은 문제도 함께 지운다. 한 트랜잭션에서 `relations`와 `questions`를 모두 `delete`하고,
커밋 직후 `relationCount` 감소를 기록한다. 문제는 관계 없이 남아도 건너뛴 문제와 구분되지 않으므로,
관계를 지운 뒤에도 남겨두면 영영 해석할 수 없는 잔재가 된다.

관계가 가리키던 단어와 문장은 지우지 않는다. 둘 다 독립된 데이터이며 다른 곳에서 참조될 수 있다.

문장, 문서를 지워도 그것을 참조하던 관계와 문제를 지우지 않는다. 관계는 사라진 대상을 가리킨 채 남는다.

단어는 다르다. 단어를 수정하거나 삭제하면 그 nodeId를 참조하던 값을 남는 단어의 nodeId로 교체한다.
삭제의 경우 사용자가 대체 단어를 지정하며, 지정하지 않으면 삭제 자체가 취소된다.
전체 절차는 [단어 Store](./저장-단어.md)의 수정/삭제 규칙에 있다.

- `relations`는 위 인덱스 표의 단어 참조 인덱스들로 대상을 찾아 교체한다.
  한 관계가 여러 인덱스에 걸릴 수 있으므로 `relationId`로 모아 한 번씩만 다시 쓴다.
- `questions`는 단어 인덱스가 없어 전수 스캔으로 교체한다. 기록용 스토어라 규모가 작을 때만 수용 가능한 비용이다.
- `answer`/`comment`는 `type`이 `'word'`인 것만 교체 대상이다. 문장 참조는 건드리지 않는다.
- 관계 자체는 지우지 않는다. 병합/교체로 `word1Id === word2Id` 같은 퇴화 관계가 생길 수 있으며 그대로 둔다.
