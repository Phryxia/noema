# 설정과 백업

`/settings`. 전체 DB를 JSON 파일로 내보내고, 파일로 덮어쓴다. 공통 헤더의 `설정` 링크로 들어간다.

## 코드

- 디렉토리: `packages/client/src/backup/`
- 페이지: `routes/settings.tsx` -> `backup/BackupPanel/BackupPanel.tsx`
- 동작 훅: `backup/useBackupActions.ts`(내보내기·가져오기 mutation, `isBusy`)
- 서비스: `backup/backup.service.ts`(`exportBackup`, `importBackup`), `backup/downloadBackup.ts`
- 형식: `backup/types.ts`, `backup/consts.ts`(`$date` 태그, 파일명 접두), `backup/serialize.ts`(`encodeValue`/`decodeValue`)
- 검사와 승격: `backup/utils.ts`(`parseBackup`, `createBackupFileName`), `backup/upgradeBackup.ts` + `upgradeBackup.test.ts`

## 사양

- `내보내기`: 전체 DB를 JSON 파일 하나로 내려받는다. 파일명은 `noema-backup-<연월일시분>.json`.
- `가져오기`: 파일을 고르면 표준 confirm으로 확인한 뒤 기존 내용을 무시하고 파일 내용으로 덮어쓴다. 끝나면 모든 쿼리를 무효화한다.
- 작업 중에는 두 버튼을 비활성화한다. 성공·실패는 토스트가 알린다. 패널 안에 문구를 그리지 않는다.
- 파일 형식은 `{ dbName, version, exportedAt, stores }`, `stores`는 Store 이름별 `{ key, value }` 배열이다. 항목 단위 병합은 없다.
- `dbName`이 다르거나 `version`이 현재 `DB_VERSION`보다 높으면 거부한다. 낮으면 `upgradeBackup`이 현재 스키마로 승격한다(v11 미만: `questions` Store 폐기, `relations`의 `questionId` 제거. v12 미만: 문서마다 기본 제목 문장·`DocumentTitle` 관계 entry 추가, `recentDocuments` 칸의 `preview` 제거. v14 미만: 제목 문장을 `recentSentences` 칸의 가장 새것으로 넣어 다시 만든다). 승격이 만드는 entry의 `key`는 그 Store의 숫자 키 최댓값 + 1부터다.

## 결정 근거와 제약

- Indexed DB는 브라우저가 저장 공간을 회수하면 통째로 사라진다. 사용자가 스스로 백업할 수단이 이 페이지다. `navigator.storage.persist()` 요청 시점은 미정이다([plan](../plan.md)).
- Store 목록은 상수가 아니라 열린 연결의 `objectStoreNames`에서 얻는다. Store가 늘어도 백업 코드를 고칠 일이 없다.
- `Date`를 `{ "$date": ISO }`로 감싸는 이유, replacer를 못 쓰는 이유, `put(value)`로 ID를 보존하는 이유, `!store.keyPath` 비교: [저장개발참고](../참고/저장개발참고.md#백업).
- 가져오기는 전체 Store 단일 `readwrite` 트랜잭션이다. 중간 실패면 통째로 되돌아간다.
- 스키마를 바꿀 때는 `upgradeBackup`에 승격 단계를 더하고 테스트를 추가한다. 마이그레이션과 승격이 한 쌍이다.

## 알려진 함정

- 승격 함수는 `Date`를 만들지 않는다(승격은 디코딩 전에 돈다): [저장개발참고](../참고/저장개발참고.md#백업).
- 옛 백업이 승격되는지는 `upgradeBackup.test.ts`로 고정한다. 실제 파일로는 루트의 `corpus.json`(v9)을 가져와 확인한다([검증참고](../참고/검증참고.md)).
