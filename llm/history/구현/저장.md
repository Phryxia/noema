# 2026-07-23 통계와 총 보유의 불일치 제거

## 문제

"삭제는 통계에서 무시한다"는 원래 사양이 실제로 쓰면서 무너졌다. 누적 차트의 마지막 값과 총 보유 수가 갈라진다.

1. 삭제할 때마다 오차가 1씩 쌓여 시간이 갈수록 벌어진다. 되돌아올 방법이 없다.
2. 버전 2로 올라가는 사용자는 데이터가 이미 있는데 통계 Store가 비어 있다. 누적이 0에서 시작해 오차가 처음부터 총 보유량만큼이다.

## 해결

**순증감 기록.** `delta`를 순증감으로 바꿨다. 추가는 +1, 삭제는 -1이라 음수가 될 수 있다.
`recordCreation`/`recordDeletion`은 부호만 다른 얇은 껍데기이고 `recordCountChange(db, kind, amount)`가 실제 일을 한다.
`acc`는 삭제 직후에도 총 보유량 스냅샷을 덮어쓰므로 이제 총 보유 통계와 정의상 어긋날 수 없다.

없는 항목을 지우려 한 경우는 기록하지 않는다. `deleteSentence`/`deleteDocument`가 존재 확인 없이 `delete`를 부르고 있어서,
그대로 두면 실패한 삭제가 `delta`를 -1 시킨다. `count(key)`로 확인한다. `get`을 쓰면 문서 본문까지 읽는다.
`deleteWord`는 `createdAt`이 없으면 이미 조기 반환하므로 그 경로를 그대로 쓴다.

**백필.** 스키마를 만든 직후 같은 `versionchange` 트랜잭션에서 `backfillCountLogs`가 돈다.
세 Store를 커서로 전수 순회해 `createdAt`을 bin에 집계하고, 시간순 누적합으로 `acc`를 만든다.

- `getAll`이 아니라 커서다. 문서 본문이 통째로 메모리에 올라오는 것을 피한다.
- `void`로 흘리지만 `versionchange` 트랜잭션이 끝나야 `open`이 완료되므로 순서는 보장된다.
  `async` 함수의 첫 `await`가 `openCursor`를 동기적으로 건 뒤에 오기 때문에 트랜잭션이 살아있다.
- 이미 삭제된 항목은 `createdAt`이 없어 세지 않는다. 과거 bin의 `delta`는 당시 실제 증가량보다 작을 수 있으나,
  `acc`의 마지막 값은 현재 총 보유량과 정확히 일치한다. 불일치를 없애는 것이 목적이므로 이 손실은 받아들인다.

**차트 3분할.** 사용자 결정으로 한 차트에 세 종류를 겹치던 것을 종류별 차트 3개로 나눴다.
단어가 문장·문서보다 훨씬 빨리 늘어 나머지가 바닥에 눌리는 문제도 함께 사라졌다.
변화량 모드는 `증가`(양수부)와 `삭제`(음수의 절댓값) 2계열, 누적 모드는 `보유` 1계열이다.
음수를 그대로 그리지 않으므로 축이 0 아래로 내려가지 않는다.
`useGrowthChart`는 `useCountChart`로, 데이터 조회는 `GrowthChart`가 한 번만 하고 세 `CountChart`가 나눠 쓴다.

처음에는 셋을 세로로 쌓았더니 통계 구역이 화면 세 개 분량으로 길어져 한 행에 나란히 놓는 것으로 바꿨다.
`flex-wrap`에 `flex-basis: 18rem`이라 폭이 모자라면 알아서 다음 줄로 밀린다. 미디어 쿼리를 쓰지 않는다.
`flex` 자식에 `min-width: 0`이 필요하다. 없으면 Chart.js가 canvas에 박아 넣는 인라인 폭이 min-content가 되어 줄어들지 않는다.
제목 `h3`는 `.root .title`(0-2-0)로 걸었다. `.pico h3`가 (0-1-1)이라 클래스 하나짜리로는 로드 순서에 운을 맡기게 된다.

검증은 playwright로 했다. v1 스키마에 시각이 다른 데이터를 심고 올라와 bin 위치와 개수가 맞는지,
삭제 후 `delta`가 음수가 되고 같은 bin에서 추가하면 순증감이 되는지, 그리고 매 단계마다 총 보유와 누적 마지막 값이 일치하는지 확인했다.

# 2026-07-22 대시보드 통계 구역

## 문제

총 보유 수와 증가 추이를 보여줘야 하는데, 추이를 매번 전수 스캔으로 계산하면 데이터가 늘수록 대시보드가 느려진다.
추가 시점에 bin별로 누산해두는 방식은 세 가지가 걸린다.

1. Store 6개(`hourDelta`/`hourAcc`/`dayDelta`/`dayAcc`/`weekDelta`/`weekAcc`)가 새로 필요하다. DB 버전을 올려야 한다.
2. 설계상 통계 기록은 단어/문장/문서 저장을 붙잡지 않아야 한다(`await` 금지).
   그런데 저장 직후 `invalidateQueries`가 조회를 띄우므로, 기록이 조회보다 늦으면 방금 넣은 값이 안 보인다.
3. 누적 모드에서 레코드가 없는 bin의 값이 기획에 명시되지 않았다.

## 해결

**1. 마이그레이션.** `DB_VERSION`을 2로 올리고 `switch (event.oldVersion)`에 `case 1`을 얹었다.
`break`가 없으므로 신규 사용자(`oldVersion` 0)는 `case 0`을 지나 `case 1`까지 실행된다.
Key Path는 `beginDate`(`Date`)다. Indexed DB는 `Date`를 유효한 키로 다루고 시간순 정렬도 그대로 되므로 별도 인덱스가 필요 없다.

**2. 순서 보장.** `recordCreation(db, kind)`을 `async`가 아닌 **동기 함수**로 만들었다.
호출되는 즉시 `readwrite` 트랜잭션을 열고, 실제 쓰기는 `void`로 흘려보낸다.
`createWord`는 자기 트랜잭션이 커밋된 직후 이것을 호출하므로, 트랜잭션 생성 순서가 확정된다.
Indexed DB는 범위가 겹치는 트랜잭션을 생성 순서대로 실행하므로 이후 어떤 조회도 이 기록 뒤에 놓인다.
`async`로 두면 `openNoemaDB()`를 `await`하는 사이 조회 트랜잭션이 먼저 열릴 수 있어 경합이 생긴다.

기록 트랜잭션 범위에 `wordMeta`/`sentences`/`documents`도 넣었다. `acc`에 쓸 총 보유량을 같은 트랜잭션에서 읽어야 하기 때문이다.

**3. 결측 bin.** `delta`는 0, `acc`는 직전 값 이어받기로 정했다. 근거는 [통계 구역 설계](../../설계/화면-대시보드-통계구역.md)에 적었다.
`acc`는 노출 구간 시작 이전의 마지막 레코드가 초기값으로 필요해서, `upperBound(시작bin, true)`에 `prev` 커서로 1건을 더 읽는다.

**그 외.** Chart.js는 v4라 `LineController` 등 필요한 요소만 `Chart.register`했다.
`useGrowthChart`가 인스턴스 수명(생성/파괴)과 데이터 갱신을 각각 다른 `useEffect`로 나눠 들고 있어, 필터를 바꿔도 차트를 다시 만들지 않는다.
단어/문장/문서 세 계열의 라벨과 색은 `CountSeriesList` 하나에서 나오며, 총 보유 수 표시도 같은 상수를 쓴다.

# 2026-07-21 대시보드 단어 컴포넌트와 로직 구현

## 문제

기획 문서만 있고 구현이 없었다. 구현에 들어가며 `wordMeta` 사양의 충돌을 발견했다.

- `trieNodeSize` 초기값이 [저장-단어](../../설계/저장-단어.md)는 1, [저장-공통](../../기획/저장-공통.md)은 0
- `wordSize`가 저장-공통의 초기값 표에 누락
- 삭제 규칙에 미정의 키 `wordNodeSize` 등장

## 해결

사용자 판단으로 루트를 포함해 `trieNodeSize=1`, `wordSize=0`, `nextNodeId=1`로 통일하고 두 문서를 정정했다.
루트가 최초 생성 시 존재하고 삭제 규칙이 노드 제거마다 감소시키되 루트는 제거하지 않으므로, 루트를 세는 쪽이 정합적이다.

구현은 `packages/client/src` 하위에 다음과 같이 배치했다.

- `db/`: `openNoemaDB`(싱글턴, `onupgradeneeded` 계단식 switch, Store 8개 + 초기값을 같은 트랜잭션에서), `consts`, `utils`(요청/트랜잭션 Promise 헬퍼)
- `word/`: `types`(`TrieNode`, `Lexis`, `RecentWord`), `word.service`(`createWord`/`deleteWord`/`getWordNodeId`/`getWordsByPrefix`/`getRecentWords`), `WordWriter`, `WordSuggestion`, `RecentWords`
- `relation/`: `deleteRelationsReferencing`(전수 스캔, 삭제된 관계를 새 대상으로 삼아 연쇄 전파)
- `utils/useThrottledValue`: `WordSuggestion`의 100ms throttle
- `routes/index.tsx`(모드 선택기 + 단어 모드, 문장·문서는 disabled), `routes/word.$word.tsx`(최소 스텁)

주의했던 지점들:

- Indexed DB 트랜잭션 안에서 promisify한 요청을 `await`해도 마이크로태스크라 트랜잭션이 살아있다. 단 트랜잭션 밖 Promise를 await하면 안 된다.
- 단어 저장의 중복 판정: 도착 노드에 `createdAt`이 있으면 경로 전체가 기존재했다는 뜻이므로 no-op이며 `recentWords`도 건드리지 않는다.
- `getWordNodeId`는 `null`을 반환한다. react-query v5의 `queryFn`이 `undefined`를 금지하기 때문이다.
- 스페이스 에코는 input 위 절대배치 오버레이로, 스페이스는 마커, 나머지는 `color: transparent`로 자리만 차지시킨다. input의 `scrollLeft`를 `translateX`로 동기화한다.

검증은 사용자 결정에 따라 단위 테스트 없이 dev 서버 수동 확인으로 한다. `tsc -b`와 `eslint`, `prettier`는 통과했다.
사용자 확인 시나리오는 승인된 계획 문서의 Verification 절 참고(저장/Enter, 공백 에코, 접두사 추천 16개, 중복 no-op, 가지치기, 순환 큐, 스텁 페이지).
