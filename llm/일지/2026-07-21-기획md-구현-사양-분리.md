# 2026-07-21 기획.md 구현 사양 분리

## 문제

`기획.md`가 396줄로 `CLAUDE.md`의 200줄 분할 규칙에 걸렸다.
전체의 87%인 51~396줄이 Indexed DB 스키마와 컴포넌트 사양 같은 구현 세부였고,
동기와 데이터 개념 정의 같은 기획 본체는 앞의 49줄뿐이었다.
구현 사양 한 줄을 확인하려고 문서 전체를 읽어야 하는 상태였다.

## 해결

내용을 한 글자도 바꾸지 않고 세 문서로 옮겼다. 헤딩 레벨만 독립 문서에 맞게 한 단계씩 올렸다.

- [저장 공통 규약](../기획/저장-공통.md): 원본 51~122줄. DB 설정, 스키마 생성, 연결 수명 주기, 공통 규약.
- [타입별 Store](../설계/저장-스토어.md): 원본 124~281줄. 단어, 문장, 문서, 관계 각각의 Store.
- [화면 사양](../기획/화면.md): 원본 283~396줄. 재사용 컴포넌트와 페이지.

**"저장에 관하여"를 다시 둘로 쪼갠 이유.** 이 절만 231줄이라 통째로 빼면 그 자체가 다시 분할 규칙 대상이 된다.
경계는 데이터 타입 의존성으로 정했다. 앞쪽 절반은 어떤 데이터를 다루든 항상 적용되는 규약이고,
뒤쪽 절반은 특정 타입을 건드릴 때만 필요하다. 문장을 저장하는 코드를 쓰는 사람은 Trie 가지치기를 읽을 필요가 없다.

**허브를 3단계로 만들지 않았다.** `기획.md` → `저장.md` → `저장-공통.md`처럼 중간 허브를 두는 대신
세 문서를 평평하게 두고 `기획.md`가 직접 링크한다. 링크 한 번 더 타는 비용이 분류의 이득보다 크다.
대신 각 링크마다 단어 몇 개짜리 요약을 붙여, 목적지를 열어보지 않고도 고를 수 있게 했다.

역방향 링크도 걸었다. 세 문서 모두 초입에 원본이 `기획.md`임을 밝히고,
저장 문서 둘은 서로를, 화면 문서는 `저장-스토어.md`를 가리킨다. 컴포넌트가 읽고 쓰는 스키마가 거기 있기 때문이다.

문서 간 링크는 전부 `[제목](./상대경로)` 형태의 마크다운 링크로 쓴다. 절대경로 문자열은 쓰지 않는다.

이 작업으로 이전 항목의 "남은 것" 중 분할 건은 해소되었다. 영속성 규약은 그대로 남아 [plan](../plan.md)으로 옮겼다.

## 남은 것

- 데이터 영속성(`navigator.storage.persist()`)과 백업/내보내기 규약. [plan](../plan.md)에 있다.
