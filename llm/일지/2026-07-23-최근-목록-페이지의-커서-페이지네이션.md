# 2026-07-23 최근 목록 페이지의 커서 페이지네이션

## 문제

대시보드의 최근 목록은 순환 큐에 미리 써둔 4건짜리 사본이라 그보다 과거를 볼 수 없었다.
날짜 범위를 잘라 내림차순으로 훑는 목록이 필요한데, 두 가지가 걸렸다.

1. `sentences`, `documents`는 Key Path 인덱스밖에 없었고, 저장 공통 규약이 "Key Path 외의 인덱스를 두지 않는다"로 못박고 있었다.
   자동 증가 ID 순서가 사실상 추가 시각 순이므로 그 커서로도 정렬은 되지만, 날짜를 경계로 잡을 수 없어 범위 밖까지 훑게 된다.
2. Indexed DB는 커서만 준다. `OFFSET`이 없으니 "5페이지를 보여줘"를 바로 처리할 수 없고, 총 페이지 수도 미리 알 수 없다.

## 해결

인덱스 규약을 "커서 순회의 순서 자체가 그 인덱스여야 하는 곳에만 둔다"로 고치고, DB 버전 3에서 두 Store에 `createdAt` 인덱스를 더했다.
단순 조회 가속 목적의 인덱스는 여전히 두지 않으므로, `relations` 전수 스캔은 그대로다.

- 커서는 `index.openCursor(range, 'prev')`. 범위는 시작 날짜가 있으면 `bound`, 없으면 `upperBound`다.
- 한 페이지를 32건 읽고 멈추지 않고 **33번째까지 커서를 한 칸 더 민다**. 그 위치를 `nextCursor`로 돌려주고, 33번째가 없으면 `null`이다.
  `null`이 곧 끝이라는 뜻이므로 별도의 count 질의 없이 마지막 페이지를 판정한다. 다음 페이지가 0건인 경우도 구조적으로 생기지 않는다.
- 다음 페이지는 커서를 새로 열고 첫 콜백에서 `continuePrimaryKey(createdAt, id)`로 그 위치까지 점프한다.
  `createdAt`은 고유하지 않아 같은 시각이 여럿일 수 있는데, `continue(key)`로는 그 무리의 어디부터인지 지정할 수 없다.
- 페이지 캐싱 키는 `[접두사, 시작 시각, 종료 시각, 페이지 번호]`이고 만료되지 않는다.
  페이지 `n`의 queryFn은 `n-1`을 `ensureQueryData`로 확보한 뒤 그 `nextCursor`를 쓴다. 캐시에 있으면 즉시 반환되므로 실제 재귀는 한 단계뿐이다.
- 종료 날짜는 입력이 분 단위여서 그대로 쓰면 같은 분에 방금 넣은 항목이 빠진다. `59.999`초까지 늘려 잡는다.

화면 쪽은 노출 페이지 번호 계산만 `computePagination`으로 떼어 vitest로 먼저 고정했다.
탐사된 페이지가 항상 1부터 연속이라는 전제 덕에 입력이 `{ 현재 페이지, 탐사된 페이지 수, 끝에 닿았는지 }` 셋으로 끝나고, 경계 조합이 여기에 다 몰린다.
사양은 [최근 목록](../../기획/화면/최근-목록.md)에 있다.

## 버전만 올라가고 인덱스가 없는 DB를 두 번 만든 일

인덱스 신설 뒤 사용자 브라우저에서 목록이 빈 채로 나왔다. 원인은 데이터도 커서도 아니고 **편집 순서**였다.

`DB_VERSION`을 3으로 올리는 편집을 먼저 저장하고, `createCreatedAtIndexes` 호출을 그 다음 편집으로 넣었다.
그 사이 켜져 있던 dev 서버의 HMR이 브라우저에 반영되었고, 브라우저는 **인덱스를 만드는 코드가 아직 없는 상태로** 버전 3 업그레이드를 성사시켰다.
`onupgradeneeded`는 버전이 오를 때만 불리므로, 코드가 완성된 뒤에도 그 DB에는 인덱스가 영영 붙지 않는다.

버전 4에 `case 3`을 더해 구제하려 했으나 똑같은 실수를 반복했다. `DB_VERSION = 4`를 먼저 저장한 순간 HMR이 돌았고,
그때 `switch`에는 아직 `case 3`이 없어 **아무 분기도 타지 않은 채 버전만 4로 커밋**되었다.

두 번 다 원인이 같다. 인덱스 생성이 `switch (event.oldVersion)` 안에 있었다는 것이다.
버전 분기는 "이번에 무엇을 새로 만들지"를 정하는 자리이지, "있어야 할 것이 있는지"를 확인하는 자리가 아니다.

그래서 `ensureCreatedAtIndexes`를 `switch` 밖으로 빼 버전과 무관하게 매번 돌린다. `indexNames.contains`로 걸러 멱등하다.
이제 어떤 버전에서 올라오든 인덱스는 반드시 보정되며, 분기를 건너뛴 DB가 또 생겨도 다음 업그레이드 한 번으로 복구된다.
버전은 5까지 올라갔다. 3과 4는 이 사고로 소모한 번호다.

편집 순서도 교훈으로 남는다. dev 서버가 켜져 있으면 **중간 저장 상태 하나하나가 실제로 실행된다**.
스키마를 바꿀 때는 로직을 먼저 안전하게 만들고 버전 번호를 마지막에 올려야 한다. 반대로 하면 중간 상태가 DB에 영구 흔적을 남긴다.

조회 실패가 화면에 드러나지 않았던 것도 문제를 키웠다. `useQuery`의 `error`를 무시해 인덱스 부재가 "해당 범위에 아무것도 없습니다"로 보였고,
기본 retry 3회 탓에 한참 로딩까지 돌았다. `retry: false`로 바꾸고 에러 문구를 띄운다.
`getRecentPage`는 커서를 열기 전에 인덱스 유무를 확인해, 없으면 열린 DB의 버전까지 담은 문구로 던진다.

## 검증

playwright를 설치해 실제 Chromium으로 확인했다. 네 경로 모두 최신 버전으로 올라가며 인덱스가 붙는다.

- 신규 생성, 버전 2에서 올라오는 DB, 인덱스 없는 버전 3 DB, 인덱스 없는 버전 4 DB(사용자가 겪은 상태 그대로)
- 문장 70건으로 32/32/6건 세 페이지가 나뉘고, 마지막 페이지에서 `...`이 사라지며 `>`가 비활성화된다
- 내용 48자와 출처 16자가 줄임표와 함께 잘리고, 날짜가 분 단위로 나온다

## 남은 것

DB 버전이 5가 되었으므로 기존에 받아둔 버전 2 백업 파일은 가져오기가 거부된다.
가져오기는 `dbName`과 `version`이 현재와 같을 때만 허용하는 규약이라 의도된 동작이지만, 사용자가 옛 백업을 들고 있다면 곤란해진다.
