# 탐색의 스키마

- 원본: [탐색 Store](./저장-탐색.md)에서 2026-08-16에 분리됐다.
- 문제와 관계의 개념, 문제 유형별 지시문은 [탐색 기획](../기획/탐색.md)에 있다.
- 제출/수정/삭제 절차는 [탐색의 절차](./저장-탐색-절차.md)에 있다.
- `relations`에 함께 담기는 `DocumentToSentence`는 [문서-문장 관계 Store](./저장-관계-문서문장.md)에 있다.

탐색은 두 Store를 쓴다. 출제된 문제를 담는 `questions`와, 그 답으로 만들어진 관계를 담는 `relations`다.
둘 다 답을 제출할 때만 함께 쓰인다. 건너뛰면 어느 쪽에도 쓰지 않는다.

## 공용 타입

```ts
type WordOrSentence = {
  type: 'word' | 'sentence'
  id: number
}
```

`type`이 `'word'`면 `id`는 `wordNodes`의 `nodeId`이고, `'sentence'`면 `sentences`의 `sentenceId`다.
앞으로 문서를 가리키는 관계가 생길 수 있으므로, 이 자리는 값이 늘어나는 것을 전제로 다룬다.

`Similarity`는 다섯 단계의 수치다. Eraseable Syntax 제약으로 `enum`을 쓸 수 없어 리터럴 유니온과 상수 배열로 표현한다.

| 표시 | 값 |
| ---- | ---- |
| 매우 반대 | -1 |
| 약간 반대 | -0.5 |
| 서로 무관 | 0 |
| 약간 비슷 | 0.5 |
| 매우 비슷 | 1 |

## Question Store

Store 이름은 `questions`. Key Path로 `questionId`를 가지며 자동 증가한다.
`type`으로 갈라지는 태그 유니온이며, 유형별로 대상 단어를 담는 필드가 다르다.

```ts
interface QuestionBase {
  questionId: number
  createdAt: Date
}

type Question =
  | (QuestionBase & { type: 'WordExplain'; wordId: number })
  | (QuestionBase & { type: 'WordsUsage'; wordIds: number[] })
  | (QuestionBase & { type: 'UnaryProperty'; wordId: number })
  | (QuestionBase & { type: 'BinaryCommon'; word1Id: number; word2Id: number })
  | (QuestionBase & { type: 'BinaryDifference'; word1Id: number; word2Id: number })
  | (QuestionBase & { type: 'BinarySimilarity'; word1Id: number; word2Id: number })
  | (QuestionBase & { type: 'BinaryAssociation'; wordId: number })
  | (QuestionBase & { type: 'TernaryIsolation'; word1Id: number; word2Id: number; word3Id: number })
  | (QuestionBase & { type: 'TernaryComposition'; word3Id: number })
  | (QuestionBase & { type: 'NamedAssociation'; word1Id: number; word2Id: number; word3Id: number })
```

출제 자체는 저장하지 않는다. 화면이 들고 있는 것은 `questionId`와 `createdAt`이 없는 초안이며,
제출 순간에 `add`가 `questionId`를 발급하고 그때의 시각이 `createdAt`이 된다.
따라서 건너뛴 문제는 `questionId`를 소비하지 않는다.

## Relation Store

Store 이름은 `relations`. Key Path로 `relationId`를 가지며 자동 증가한다.
`questionId`로 자신을 낳은 문제를 가리킨다.
[개별 관계](../기획/화면-페이지.md) 화면에서 고칠 수 있으므로 `modifiedAt`을 가지며, 한 번도 고치지 않았으면 없다.

```ts
interface RelationBase {
  relationId: number
  createdAt: Date
  modifiedAt?: Date
}

interface WordRelationBase extends RelationBase {
  questionId: number
  comment?: WordOrSentence
}

type WordRelation =
  | (WordRelationBase & { type: 'WordExplain'; wordId: number; answer: WordOrSentence })
  | (WordRelationBase & { type: 'WordsUsage'; wordIds: number[]; answer: WordOrSentence | null })
  | (WordRelationBase & BinaryWords & { type: 'UnaryProperty' })
  | (WordRelationBase & BinaryWords & { type: 'BinaryCommon'; answer: WordOrSentence | null })
  | (WordRelationBase & BinaryWords & { type: 'BinaryDifference'; answer: WordOrSentence | null })
  | (WordRelationBase & BinaryWords & { type: 'BinarySimilarity'; similarity: Similarity })
  | (WordRelationBase & BinaryWords & { type: 'BinaryAssociation' })
  | (WordRelationBase & TernaryWords & { type: 'TernaryIsolation'; selection: 1 | 2 | 3 })
  | (WordRelationBase & TernaryWords & { type: 'TernaryComposition' })
  | (WordRelationBase & TernaryWords & { type: 'NamedAssociation' })

type Relation = WordRelation | DocumentToSentenceRelation
```

스토어에서 읽은 값은 `Relation`이고, 단어 관계 전용 코드는 `WordRelation`을 받는다. 둘의 구분은 [문서-문장 관계 Store](./저장-관계-문서문장.md)에 있다.

`BinaryWords`는 `word1Id`, `word2Id`를, `TernaryWords`는 거기에 `word3Id`를 더한 것이다.
문제의 대상 단어를 관계가 그대로 복사해서 갖는다. `questionId`를 따라가지 않고도 관계만으로 조회할 수 있어야 하기 때문이다.

`answer`는 `WordsUsage`, `BinaryCommon`, `BinaryDifference`에서 `null`일 수 있다.
`WordsUsage`는 말이 안 되는 단어 조합이 나와 응답을 회피한 경우고,
이항 공통점/차이점은 무응답(빈 문자열)을 제출한 경우다.
`answer`가 `null`인 관계는 `answer` 인덱스에서 저절로 빠진다.
`BinaryAssociation`은 답한 단어 자체가 `word2Id`이므로 `answer` 필드가 없다. 무응답도 없다.
기존 `word1Id`/`word2Id` 인덱스가 그대로 담으므로 새 인덱스나 버전 변경이 필요 없다.
`UnaryProperty`(속성)는 `word1Id`가 `word2Id`의 속성을 가짐을 뜻한다. 문제는 주어진 `wordId`(=`word1Id`)만 담고
답한 속성 단어가 `word2Id`가 되므로, `BinaryAssociation`과 필드 구성이 같다. 이쪽도 새 인덱스나 버전 변경이 필요 없다.
`NamedAssociation`(관계 짓기)은 `word1Id`에서 `word2Id`로 향하는 유향 관계의 이름이 `word3Id`다.
세 단어가 모두 문제의 대상이라 `answer` 필드가 없고, 세 단어 모두 필수라 무응답도 없다.
탐색에서는 출제하지 않으며(`ExploreQuestionTypes`에서 제외) [알려주기](../기획/화면/알려주기.md)에서만 만든다.
`TernaryIsolation`과 같은 필드 구성이므로 이쪽도 새 인덱스나 버전 변경이 필요 없다.
`TernaryComposition`(삼항 합성)은 `word3Id = word1Id + word2Id`다. 문제는 주어진 `word3Id`만 담고(`BinaryAssociation`의 `wordId`와 같은 기조),
답한 두 단어가 관계의 `word1Id`, `word2Id`가 되므로 `answer` 필드가 없다. 두 단어 모두 필수라 무응답도 없다.
관계는 `NamedAssociation`과 같은 필드 구성이라 새 인덱스나 버전 변경이 필요 없다.
`comment`는 어느 유형에서나 선택이며, 비어 있으면 키 자체를 두지 않는다. 문장/문서의 `source`와 같은 규약이다.

## 인덱스

`relations`는 참조 대상으로 거슬러 조회할 일이 많으므로, 대상을 가리키는 모든 필드에 인덱스를 둔다.

| 인덱스 | Key Path | 담기는 유형 |
| ------ | -------- | ----------- |
| `createdAt` | `createdAt` | 전부 |
| `wordId` | `wordId` | `WordExplain` |
| `wordIds` | `wordIds` (`multiEntry`) | `WordsUsage` |
| `word1Id` | `word1Id` | 이항, 삼항 |
| `word2Id` | `word2Id` | 이항, 삼항 |
| `word3Id` | `word3Id` | `TernaryIsolation`, `TernaryComposition`, `NamedAssociation` |
| `answer` | `['answer.type', 'answer.id']` | 답이 있는 유형 |
| `comment` | `['comment.type', 'comment.id']` | 참고사항이 있는 관계 |
| `documentId` | `documentId` | `DocumentToSentence` |
| `sentenceId` | `sentenceId` | `DocumentToSentence` |

`questions`는 `createdAt` 하나를 둔다.

Indexed DB는 Key Path가 `undefined`인 레코드를 인덱스에 넣지 않으므로, 각 인덱스는 그 필드를 가진 유형만 저절로 담는다.
유형을 걸러내는 별도의 조건이 필요 없다. `answer`가 `null`인 `WordsUsage` 관계도 같은 이유로 `answer` 인덱스에서 빠진다.

`answer`와 `comment`는 값이 `WordOrSentence`라 `type`과 `id`를 함께 봐야 한다. 복합 Key Path로 한 번에 조회한다.
`type` 자리가 문자열로 열려 있으므로, 앞으로 `'document'`가 들어와도 인덱스 정의를 고칠 일이 없다.

`wordIds`는 배열이므로 `multiEntry`로 둔다. 배열의 각 원소가 개별 키가 되어, 단어 하나로 그 단어가 쓰인 예문 관계를 찾을 수 있다.
