# 태그

문장·문서에 단어를 붙이는 `Tag` 관계와, 문장·문서 입력기 본문 아래의 태그 카드 편집기. 편집 중에는 DB 무변경, 저장 시 스냅샷 차이만큼 관계를 추가·삭제한다.

## 코드

- 디렉토리: `packages/client/src/tag/`
- 편집기: `tag/TagEditor/TagEditor.tsx`(`useCards` 소유, `removeUnlessLast`), `createInitialTagValues.ts`, `normalizeTagValues.ts`, `useTagResults.tsx`(결과 팝업)
- 제출: `tag/submitTags.ts`(스냅샷 차이), `getTagOutcomeLabel.ts`
- 서비스·판정: `tag/tag.service.ts`, `checkIsSentenceTag.ts`, `hydrateTagEntries.ts`, `types.ts`, `consts.ts`, `utils.ts`(`invalidateTagQueries`)
- 화면: `tag/TagTable.tsx`·`TagCells.tsx`(`PairTable` 기반), `tag/WordTags/`(개별 단어의 `태그된 문장/문서`), `tag/TagRelationPage/`(`PairRelationPage` 기반), 대표 표현 `relations/RelationExpression/TagExpression.tsx`
- 폼 연결: `writer/useWriterForm.ts`의 `confirmSave(draft)`·`onSaved`·`resetKey`, `writer/checkIsBodyChanged.ts`

## 사양

- 본문 편집기 바로 아래 인라인 라벨 `tags:`와 단어 카드 한 줄. 대시보드 신규 작성 폼과 개별 문장/문서 수정 폼 양쪽에 있다.
- 카드 조작은 [단어-추출](./단어-추출.md)과 같다(값 끝 Enter로 새 카드, 빈 카드 Backspace로 삭제). 태그가 없으면 빈 카드 1장이 있고 마지막 1장은 삭제되지 않는다. 진입 시 카드는 DB의 태그 관계에서 오며 단어가 삭제된 관계는 카드로 만들지 않는다.
- 편집은 폼 draft(`tags: string[]`)에만 반영된다. 빈 값·중복을 제거해 정규화한 목록이라 뒤에 빈 카드가 남거나 같은 값 카드가 둘이어도 dirty에 영향이 없다. 저장/수정 버튼, `Ctrl+Enter`, 미저장 이탈 질의의 저장이 본문·출처와 함께 태그도 제출한다.
- 신규 작성: 문장/문서를 만든 뒤 그 ID로 태그를 추가. 성공하면 폼과 카드 초기화(`resetKey`). 수정: 본문/출처가 바뀐 경우에만 갱신하고 태그는 차이만큼 추가/삭제. 태그만 바뀐 저장은 관계 영향 질의를 띄우지 않는다. 저장 후 쿼리 무효화로 새 스냅샷을 읽어 버튼이 비활성으로 돌아오고 카드는 남는다.
- 결과 팝업(`ResultDialog`): 차이가 1건 이상일 때만. 추가 초록(단어 신규 여부 구분 없음), 삭제 주황, 실패 빨강. 차이가 없으면 토스트만.
- 저장: `{ type: 'Tag', wordId, sentenceId | documentId, createdAt }`, `comment` 없음, 수정 없음(값 변경은 삭제 + 추가). 대상 종류는 어느 필드가 있는지로 가른다(`checkIsSentenceTag`). 새 인덱스·버전 없이 `sentenceId`/`documentId`/`wordId` 인덱스를 공유한다.
- 제출 절차 `submitTags(target, previous, values)`: `values` 정규화(`trim` 없음) → `added = next − previous`, `removed = previous − next`(값 기준. 삭제된 단어의 entry는 값이 `''`라 항상 `removed`) → 둘 다 비면 트랜잭션 없이 `[]` → `[wordMeta, wordNodes, recentWords, relations]` 단일 트랜잭션에서 `added`는 `addWord` + `relations.add`(값별 예외는 `실패`로만), `removed`는 `delete` → 커밋 후 단어·관계 통계 기록(`recordDeletion`에 `amount`).
- 다른 화면: 개별 문장/문서의 관계 표에는 나오지 않는다(입력기가 그 역할). 개별 단어에는 `태그된 문장/문서` 구역. `/relations`에는 `태그`, 대표 표현 `[문장/문서] ~ [단어]`(30% 고정). `/relation/<id>`는 메타 + 대상 줄 + 단어 줄 + 삭제. 관계 검색 모집단에서 제외. 문장/문서를 지워도 관계는 남아 `(삭제됨) ~ [단어]`.
- 단어 개명·대체·삭제 게이트는 `wordId` 인덱스 덕에 따라온다. 문장 수정의 관계 영향 질의 건수에 태그가 들어가되 태그만 바뀐 저장은 건너뛴다. 문서는 질의하지 않는다.

## 결정 근거와 제약

- `type`을 `Tag` 하나로 둔 이유: 사용자가 개념을 하나로 부르고 유형 라벨도 하나다.
- 카드 ↔ draft 연결: `TagEditor`가 `useCards`를 소유하고 `useEffect`로 정규화된 `string[]`만 부모 draft에 올린다. draft에 카드 리스트를 넣으면 dirty 비교와 리셋이 복잡해지고, `string[]`로 완전 제어하면 카드 ID가 사라진다. 루프를 막기 위해 `cards`를 `useMemo`로 안정화하고 부모 `onChange`는 `useCallback` + 함수형 `setDraft`다.
- 정규화를 `TagEditor.onChange`, 초기값, `submitTags` 세 곳이 같이 쓰는 이유: 처음엔 카드 값을 그대로 넣었더니 뒤의 빈 카드 때문에 저장 후에도 dirty가 풀리지 않았다.
- `tag` 토큰을 `extraction` 토큰과 따로 둔 이유: 배치가 다르다(30% 고정 대상 + `~` + 단어 vs 70% 자식 + `from` 30% 부모).
- 개별 단어 화면은 처음 구현에서 빠뜨려 지적받았다. `QnaTable`은 문제 기반이라 태그를 끼울 수 없어 별도 구역이다.
