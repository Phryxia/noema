# 관계

단어 관계 10종의 모델, 제출·수정·삭제 절차, 알려주기 페이지 `/relation/new`, 개별 관계 페이지 `/relation/$relationId`. 추출 관계 2종과 태그는 [문장-추출](./문장-추출.md), [단어-추출](./단어-추출.md), [태그](./태그.md)에 있고, 목록은 [관계-목록](./관계-목록.md), 출제는 [탐색](./탐색.md)에 있다. 배치 모드는 [관계-배치](./관계-배치.md).

## 사양

### 모델

- 관계는 `relations` Store 한 곳에 담기며 `type`으로 갈린다. 단어 관계 10종(`WordRelation`)과 비단어 관계 3종(`DocumentToSentence`, `SentenceToWord`, `Tag`). 공통 필드는 `relationId`, `createdAt`, 수정 시 `modifiedAt`. 단어 관계만 선택적 `comment`(`WordOrSentence`)를 갖고, 비면 키 자체를 두지 않는다.
- 10종의 뜻과 지시문은 `getQuestionPrompt.ts`, 필드 배치는 `QuestionSpecs`의 `given`/`answer`가 진실이다. 요약:
  - 단어 설명 `WordExplain`(`wordId`, 문장 답), 예문 만들기 `WordsUsage`(`wordIds`, 문장 답 또는 `null`)
  - 이항 공통점/차이점 `BinaryCommon`/`BinaryDifference`(`word1Id`/`word2Id`, 단어·문장 답 또는 `null`), 유사성 `BinarySimilarity`(`similarity` 5단계, 라벨은 `explore/consts.ts`), 연상 `BinaryAssociation`·속성 `UnaryProperty`(답한 단어가 `word2Id`, `answer` 없음)
  - 삼항 격리 `TernaryIsolation`(`selection` 1|2|3), 삼항 합성 `TernaryComposition`(`word3 = word1 + word2`, 답한 둘이 `word1Id`/`word2Id`), 관계 짓기 `NamedAssociation`(`word1 -word3-> word2`, 답 없음, 탐색 미출제)
- 문제(`RelationQuestion { type, wordIds }`)는 저장하지 않는다.

### 제출 절차 (탐색·알려주기 공용)

0. 알려주기는 대상 단어를 먼저 `createWord`로 확보한다. 답이 단어 자체인 유형은 답 단어도 확보하고, 삼항 유형은 중복 검사를 한다([저장개발참고](../참고/저장개발참고.md#중복-차단)).
1. `{ type }`만 담은 레코드를 `add`해 `relationId`를 예약한다. `createdAt`이 없어 어느 인덱스에도 잡히지 않는다.
2. 답안이 단어면 `createWord`, 문장이면 `createSentence`. 문장 `source`는 탐색 `Harvest via NOEMA system exploration, rid=<id>`, 알려주기 `Taught via NOEMA system teaching, rid=<id>`. v11 이전 문장의 `qid=`는 해석 불가.
3. 참고사항도 같게. 비면 만들지 않고 `comment`를 넣지 않는다.
4. 완성된 관계를 `put`하고 커밋 직후 `recordCreation('relationCount')`. 2~4 실패 시 예약 레코드를 `delete`하고 다시 던진다.

### 수정·삭제

- 수정은 유형 고정, 대상 단어·답안·참고사항만. 단어는 `createWord`로 재확보, 삼항 중복 검사에서 자기 자신 제외. 문장 답은 내용이 같으면 기존 id, 다르면 새 문장을 만들고 밀려난 문장의 `source`를 물려받는다(없으면 알려주기 접두). `modifiedAt` 갱신, 통계 미기록. 밀려난 문장은 지우지 않는다.
- 삭제는 `relations`에서 `delete` 후 `recordDeletion`. 가리키던 단어·문장은 지우지 않는다. 문장·문서를 지워도 관계는 남는다. 단어만 참조 교체로 따라온다([단어](./단어.md)).

### 알려주기 `/relation/new`

- 최상단 라디오로 유형 하나 선택(localStorage `teach/type`). 유형을 바꾸면 칸 수가 조정되고(앞부분 유지) 답안은 초기화.
- 대상 단어 칸 수·최소는 `QuestionSpecs.subject`. 예문 만들기만 동적(2칸 시작, 마지막 칸이 비지 않은 채 blur면 추가, 빈 칸에서 Backspace release면 삭제, 1칸 이상 유지). 각 칸은 `WordField` + `WordSuggestion`, 오른쪽에 주사위 버튼(DB 랜덤 단어, 다른 칸과 겹치지 않게, `tabIndex=-1`, 알려주기 전용). 필수가 아닌 칸은 placeholder `(optional)`.
- 관계 짓기는 `단어 1 ── 관계 ──▶ 단어 2` 한 줄(DOM 순서 [0,2,1]), 답안란 없음. 삼항 합성은 `단어 3 = 단어 1 + 단어 2` 한 줄, 답안이 단어 두 칸. 삼항 격리는 단어가 준비되기 전 `대상 단어를 먼저 입력하세요`.
- 비어 있지 않은 단어는 서로 달라야 한다. 관계 짓기와 삼항 합성은 예외(`아버지 ─아버지─▶ 친할아버지`, `곳곳 = 곳 + 곳`).
- 단어는 입력한 순서 그대로 저장한다. 지시문·답안란·참고사항·제출 키는 [탐색](./탐색.md)과 같다. 건너뛰기, 최소 단어 수 가드, 높이 고정은 없다.
- 제출 성공 시 대상 단어·답안·참고사항을 비우고 첫 칸에 포커스, 유형은 유지.

### 개별 관계 `/relation/$relationId`

- 비단어 관계는 메타·참조 링크·삭제만(`PairRelationPage` 기반 `D2sRelationPage`/`S2wRelationPage`/`TagRelationPage`).
- 단어 관계는 알려주기와 같은 구성. 유형 라디오는 비활성, `MetaFields`(`relationId`, `createdAt`, `modifiedAt`), 수정 버튼(제출과 같은 활성 조건, 입력 유지), 삭제 후 관계 목록으로. 없는 id면 `존재하지 않는 관계: <id>`. 미저장 이탈 질의는 없다.

## 결정 근거와 제약

- 트랜잭션을 나누는 이유(문장이 `relationId`를 필요로 하고, 다른 트랜잭션 대기 중 자동 커밋), 관계 적재 실패 시 단어·문장이 고아로 남아도 무해한 이유: [저장개발참고](../참고/저장개발참고.md#트랜잭션).
- 예약 레코드에 `createdAt`을 넣지 않는 이유: 넣었더니 `/relations` 목록에 빈 행이 보였다.
- 연상·속성·삼항 합성이 `answer` 필드 없이 답을 단어 필드에 넣는 이유: 답과 단어의 이중 저장을 피하고 기존 인덱스로 DB 무변경. 새 유형은 기존 필드 구성에 맞추는 것이 먼저다.
- `QuestionSpecs`로 통합한 이유: 유형별 switch가 6곳에 반복되어 유형 하나에 여섯 군데를 고쳤다. 라벨·표시 순서도 여기서 파생되어 하위 모듈이 `explore/`를 역참조하지 않는다.
- 관계 짓기의 시각 재배치는 렌더 계층에서만 한다. `words` 배열은 `[w1, w2, w3]` 그대로이고 포커스 순서는 DOM 순서를 따른다.
- 대상 단어 칸 Enter가 제출이 아닌 이유: 무응답 허용 유형에서 회피 관계가 적재된다. 답안 확정은 참고사항 이동, 제출은 참고사항에서만.
- `TEACH_*` 상수는 이름·값을 바꾸지 않는다. 저장된 `source` 문자열과 사용자 localStorage 키다.
- 관계 목록 대표 표현 `[w1] ──[w3]─→ [w2]`는 요청 원문 `-[w2]→ [w3]`이 저장 의미와 어긋나 채택하지 않았다.
