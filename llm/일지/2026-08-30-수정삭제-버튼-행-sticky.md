# 2026-08-30 수정·삭제 버튼 행 sticky

## 문제

개별 단어·문장·문서 페이지에서 본문이 길면 수정/삭제 버튼이 화면 아래로 밀려 스크롤을 끝까지 내려야 누를 수 있었다. 문서는 `field-sizing: content`라 본문 길이만큼 늘어나므로 특히 심했다. 요구는 버튼 행이 자연 위치로 화면에 들어오면 제자리, 자연 위치가 화면 아래면 화면 bottom에 떠 있기, 자연 위치가 화면 위로 지나가면 내용과 함께 올라가기(위에 고정하지 않기)였다.

## 해결

세 페이지가 공유하는 `writer/WriterActions`의 CSS만 고쳤다. `position: sticky; bottom: 0`이 요구 동작 그대로다. containing block은 부모 `form`이고 행이 그 마지막 자식이라, 폼 아래쪽이 화면 밖에 있는 동안만 bottom에 붙고 폼 끝이 보이면 제자리로 돌아간다. `top`은 주지 않았다. 주더라도 마지막 자식이라 위에 붙을 여지가 없다. IntersectionObserver로 fixed를 토글하는 JS 방식은 CSS 한 줄로 되는 일이라 기각했다.

떠 있을 때 본문이 버튼 사이 `gap`과 둥근 모서리로 비치지 않도록 `background: var(--pico-card-background-color)`를 줬다. 세 입력기 모두 `article` 카드 안이다. 다크 테마 실측값은 `rgb(24, 28, 37)`(`#181c25`)로 카드와 같았다.

버튼 위 여백은 앞 형제가 만든다(문장·문서는 태그 편집기 `.root`의 `margin-bottom`, 단어는 `WordField` input의 pico `margin-bottom`). 그대로 두면 떠 있을 때 버튼 위 1rem이 투명해 본문이 비친다. `margin-top: calc(var(--pico-spacing) * -1)` + `padding-top: var(--pico-spacing)`으로 그 1rem을 행의 padding으로 흡수했다. 자연 위치의 버튼 `top`은 변경 전후 모두 2147px(1280x800, 문서 18)로 같았고 앞 형제와의 간격도 20px 그대로다. 아래쪽은 pico가 `[type=submit]`·`[type=button]`에 주는 `margin-bottom` 1rem이 flex 컨테이너 content box 안에 있어 배경이 덮으며, 떠 있을 때 버튼 bottom이 뷰포트 bottom에서 20px 위에 온다.

`z-index: 3`으로 뒀다. `WordSuggestion`(4)보다 낮아 단어 페이지의 추천 목록이 여전히 행 위에 그려진다. 목록이 닫힌 상태에서 삭제 버튼을 누르면 [2026-08-15](./2026-08-15-개별-단어-페이지-삭제-버튼이-추천-목록에-가려짐.md)대로 클릭 1회에 click 1건이 발화했다. 목록이 열린 채로 누르면 목록이 버튼을 덮어 click이 목록으로 가는데, 이는 변경 전과 같고 [입력-포커스참고](../참고/입력-포커스참고.md#클릭-소실-mousedown과-blur)에 이미 있는 동작이다. 행을 4 이상으로 올리면 반대로 행이 목록의 아래쪽 항목을 가리므로 올리지 않았다. `WhitespaceEcho`(3)와 같은 값이지만 DOM 순서상 뒤라 행이 위이고, pico `[role=group] :focus`(2)보다 높아 태그 카드 포커스가 떠 있는 행을 뚫지 않는다.

대시보드의 문장·문서 생성 폼도 같은 컴포넌트라 저장 버튼이 함께 sticky가 된다. `WordWriter`는 `WriterActions`를 쓰지 않는다.
