# 2026-07-23 최근에 추가된 단어 목록

## 문제

문장과 문서에는 최근 목록 페이지가 있는데 단어에는 없었다. 같은 구성을 단어에도 주려니 셋이 걸렸다.

1. `wordNodes`에는 `createdAt` 인덱스가 없었다. `nodeId` 순서는 노드가 생긴 순서라 단어가 추가된 순서와 다르고, 단어가 아닌 중간 노드까지 섞여 있다.
2. 커서가 주는 것은 단어의 마지막 글자 노드 하나뿐이다. `value`가 한 글자여서 그대로는 표에 내보낼 것이 없다.
3. 기존 최근 목록은 Store 이름 하나만 받아 커서를 열고 그 레코드를 그대로 항목으로 썼다. 단어는 그 사이에 복원 단계가 필요하다.

## 해결

**인덱스.** DB 버전 6에서 `wordNodes`에도 `createdAt` 인덱스를 걸었다.
`createdAt`은 단어인 노드에만 있고, Indexed DB는 Key Path가 `undefined`인 레코드를 인덱스에 넣지 않는다.
그래서 이 인덱스는 저절로 단어 노드만 담으며, 중간 노드를 걸러내는 조건이 따로 필요 없다.
단어를 지울 때 `createdAt`을 지우는 기존 동작이 인덱스에서 빼는 일까지 겸한다.

`ensureCreatedAtIndexes`가 이미 `switch` 밖에 있어 이번에는 Store 이름 하나를 배열에 더한 것이 전부다.
아래 사고의 교훈대로 **인덱스 코드를 먼저 저장하고 `DB_VERSION`을 나중에 올렸다**. dev 서버가 켜져 있었으므로 순서를 뒤집었으면 같은 사고가 세 번째로 났다.

**문자열 복원.** `parentNodeId`를 루트까지 거슬러 오르며 `value`를 모은다.
한 페이지 32건을 각각 거슬러 오르면 짧은 단어라도 글자 수만큼 `get`이 드는데, 노드 ID에서 그 노드까지의 문자열로 가는 `Map`을 두어 이미 복원한 조상을 재사용한다.
접두사를 공유하는 단어가 나란히 있을수록 덜 읽으며, 최악이어도 기존과 같다. 이 재귀는 `getWordValues`로 떼어 `word.service.ts`가 200줄을 넘지 않게 두었다.

**RecentSource.** `getRecentPage`가 Store 이름 대신 `{ storeName, hydrate? }`를 받는다.
`hydrate`는 커서로 읽은 항목 배열을 받아 항목 배열을 돌려주는 선택적 후처리이고, 단어만 이것을 채워 `value`를 복원한 문자열로 바꾼다.
복원은 커서 트랜잭션이 끝난 뒤 새 트랜잭션에서 돈다. 커서 콜백 안에서 다른 `get`을 섞으면 커서 순회 중에 트랜잭션이 죽을 수 있다.

한 페이지를 다 읽고 나서 한 번에 복원하므로, 복원 비용은 페이지당 한 번이고 페이지네이션 로직은 그대로다.
커서와 캐싱은 문장·문서와 똑같이 쓴다. 단어에는 출처가 없어 표의 출처 열만 `hasSource`로 뺐다.
