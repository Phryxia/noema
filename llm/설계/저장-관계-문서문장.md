# 문서-문장 관계의 경우

- 상위문서: [타입별 Store](./저장-스토어.md)
- 단어 관계(`WordRelation`)의 스키마와 절차는 [탐색 Store](./저장-탐색.md)에 있다.
- 만드는 화면은 [문장 추출](../기획/화면/문장-추출.md)이다.

`DocumentToSentence`는 문서 하나에서 문장 하나가 추출되었음을 뜻한다. 별도 Store 없이 `relations`에 다른 관계와 함께 저장되며,
`relationId`를 공유하므로 [개별 관계](../기획/화면-페이지.md) 화면 `/relation/<id>`를 같이 쓴다.

## 타입

```ts
interface RelationBase {
  relationId: number
  createdAt: Date
  modifiedAt?: Date
}

interface WordRelationBase extends RelationBase {
  questionId: number
  comment?: WordOrSentence
}

interface DocumentToSentenceRelation extends RelationBase {
  type: 'DocumentToSentence'
  documentId: number
  sentenceId: number
}

type WordRelation = ...  // 탐색 Store의 10개 유형
type Relation = WordRelation | DocumentToSentenceRelation
```

- `questionId`가 없다. 문제에서 태어난 관계가 아니기 때문이다. `comment`도 없다.
- `modifiedAt`은 타입에만 있고 아직 쓰는 경로가 없다. 개별 관계 화면에 수정이 없다.
- 스토어에서 읽은 값은 `Relation`이며, 단어 관계 전용 코드로 넘기기 전에 `type === 'DocumentToSentence'`로 갈라야 한다.
  filter 자리에는 `checkIsWordRelation`을 쓴다.

## 인덱스

`relations`에 두 인덱스를 더한다. `DB_VERSION` 10.

| 인덱스 | Key Path | 담기는 유형 |
| ------ | -------- | ----------- |
| `documentId` | `documentId` | `DocumentToSentence` |
| `sentenceId` | `sentenceId` | `DocumentToSentence` |

`ensureIndexes`가 버전 분기 밖에서 멱등하게 만든다. 문서별 조회는 `documentId` 인덱스의 `getAll`이며
결과는 기본키(`relationId`) 오름차순 = 삽입 순서 = 문서 내 문장 순서라 따로 정렬하지 않는다.

## 삽입 절차

`submitExtraction(documentId, values)`

1. `createdAt`을 한 번 찍는다.
2. `[sentences, recentSentences, relations]`를 범위로 하는 하나의 `readwrite` 트랜잭션을 연다.
   다른 트랜잭션의 결과를 기다릴 일이 없어 탐색 제출과 달리 한 트랜잭션으로 묶인다.
3. `addSentences`(문장 Store의 트랜잭션 스코프 헬퍼)로 문장을 순서대로 `add`하고 `recentSentences` 순환 큐를 갱신한다.
   모든 문장의 `createdAt`이 같고 `source`는 `Extracted via NOEMA system extraction, did=<documentId>`다.
4. 돌려받은 `sentenceId`마다 `{ type: 'DocumentToSentence', documentId, sentenceId, createdAt }`을 `relations.add`한다.
5. 커밋 후 `recordCreation(db, 'sentenceCount', n)`, `recordCreation(db, 'relationCount', n)`.

`createSentence`도 같은 `addSentences`를 값 1개로 호출한다.

## 목록

`/relations/w2w`와 `/relations/d2s`는 같은 `createdAt` 인덱스를 커서로 훑는다.
`RecentSource.toEntry`가 `null`을 돌려주면 커서가 그 레코드를 건너뛰므로, w2w는 `DocumentToSentence`를, d2s는 그 밖을 `null`로 만든다.
반대 유형이 몰린 구간을 지나가는 비용이 있으나 규모상 수용한다. 필요해지면 `['type', 'createdAt']` 복합 인덱스로 d2s 쪽을 먼저 줄인다.

관계 검색(`qnaSearch.service`)의 전수 조회와 임베딩 실험의 전수 조회는 `DocumentToSentence`를 걸러낸다.

## 수정과 삭제

- 관계 수정은 없다.
- 관계 삭제는 `relations`만 지운다. `questions`에 짝이 없으므로 `deleteRelation`이 `type`을 보고 범위를 줄인다. 문서와 문장은 그대로 둔다.
- 문서 원본을 수정·삭제해도 관계는 그대로 둔다. 개별 문서 화면은 관계 영향 질의를 하지 않는다.
- 문장을 수정하면 개별 문장 화면의 관계 영향 질의 건수에 이 관계가 들어간다(`countReferencingRelations`가 `sentenceId` 인덱스도 센다).
  문장을 삭제해도 관계는 남으며 목록에서 `(삭제됨)`으로 보인다.
- 단어 수정/삭제의 참조 교체는 단어 인덱스만 훑으므로 이 유형에 닿지 않는다.
