# 저장 공통

Indexed DB 연결, 스키마, 마이그레이션, ID·날짜·트랜잭션 규약. 데이터 종류와 무관하게 적용된다. 화면은 없다.

## 코드

- 디렉토리: `packages/client/src/db/`
- 이름·버전·Store·인덱스 상수: `db/consts.ts`(`DB_NAME`, `DB_VERSION`, `*_STORE`, `*_INDEX`)
- 인덱스 선언 목록: `db/indexSpecs.ts`
- 연결과 `onupgradeneeded`: `db/openNoemaDB.ts`(싱글턴, `createInitialSchema`, `ensureIndexes`, `removeQuestions`)
- 요청/트랜잭션 Promise 헬퍼: `db/utils.ts`(`awaitRequest`, `awaitTransaction`)
- 통계 레코드의 저장 계층: `db/countLog/`([통계](./통계.md))
- localStorage 정리: `storage/clearLegacyStorage.ts`([라우팅-쿼리참고](../참고/라우팅-쿼리참고.md#localstorage))
- 백업 형식과 가져오기: [설정-백업](./설정-백업.md)

## 사양

- DB 이름은 `noema`, 현재 버전은 `db/consts.ts`의 `DB_VERSION`이다. 버전 이력은 `openNoemaDB.ts`의 분기와 `일지/`가 갖는다. 3, 4, 8은 개발서버 HMR 사고로 소모된 번호라 어떤 분기에도 대응하지 않는다.
- Store 목록과 Key Path, 자동 증가 여부는 `createInitialSchema`·`createCountLogSchema`가 진실이다. Store 이름과 내부 키는 전부 `camelCase`다.
- 인덱스는 `IndexSpecs` 배열이 진실이다. `wordNodes`·`sentences`·`documents`·`relations`의 `createdAt`과 `relations`의 참조 필드(`wordId`, `wordIds`(multiEntry), `word1Id`~`word3Id`, `answer`/`comment` 복합, `documentId`, `sentenceId`)가 있다.
- `onupgradeneeded`는 `event.oldVersion` 기준 `break` 없는 계단식 `switch`로 새 Store를 만들고, 그 뒤 `ensureIndexes`가 버전과 무관하게 없는 인덱스를 보정한다. 버전 조건부 작업(통계 재백필, `questions` 제거)은 `switch` 뒤에 `oldVersion < N`으로 건다.
- 최초 생성 시 `wordMeta`(`trieNodeSize` 1, `wordSize` 0, `nextNodeId` 1), 루트 노드 `{ nodeId: 0, value: '', children: {} }`, 순환 큐의 `next` 0을 같은 트랜잭션에 넣는다. 순환 큐 칸은 미리 `null`로 채우지 않는다. `get`이 `undefined`든 `null`이든 빈 칸이다.
- `db.onversionchange`에서 연결을 닫고 싱글턴을 비운다. `open`의 `onblocked`는 다른 탭을 닫으라는 문구로 reject한다. 시크릿 모드 등에서 `open`이 실패하면 정상인 척하지 않고 실패를 표시한다.

## 결정 근거와 제약

- **모든 ID는 `number`이고 내용 기반 중복 제거를 하지 않는다.** UUID v5는 내용 기반 중복 제거를 공짜로 주지만 수정할 때마다 ID가 바뀐다. 노에마는 항목보다 항목 사이의 관계가 핵심 가치라 관계의 양 끝이 수정 한 번에 무효화되는 것을 받아들일 수 없었다. 유일한 예외는 삼항 관계의 중복 차단이다([저장개발참고](../참고/저장개발참고.md#중복-차단)).
- **ID 발급은 Store의 자동 증가 키 생성기에 맡긴다.** 직접 카운터를 관리하면 그것 자체가 트랜잭션 경합 대상이다. `wordNodes.nodeId`만 `wordMeta.nextNodeId`에서 발급한다. 루트가 0을 차지해야 하는데 자동 증가는 1부터다. ID를 비운 채 `add`하면 발급 값이 요청 `result`로 오며 순환 큐 사본에 그 값이 필요하다.
- **ID는 내용이 바뀌어도 불변이고 재사용되지 않는다.** 단어만 예외로, 개명은 새 `nodeId` 발급 + 참조 교체다([단어](./단어.md)).
- **날짜는 `createdAt`/`modifiedAt`으로 통일한다.** 수정 개념이 없는 항목(관계 대부분)은 `createdAt`만 갖고, 수정된 적이 있을 때만 `modifiedAt`이 생긴다.
- **하나의 조작이 여러 Store를 건드리면 전부를 범위로 하는 단일 `readwrite` 트랜잭션이다.** 단어 추가는 `wordMeta`·`wordNodes`·`recentWords`, 단어 수정·삭제는 거기에 `relations`까지(`word/consts.ts`의 `WordRewriteStoreNames`). 외부 대기 때문에 묶을 수 없는 경우는 [저장개발참고](../참고/저장개발참고.md#트랜잭션).
- **인덱스는 두 이유에만 둔다.** 커서 순회의 순서 자체가 그 인덱스여야 하는 경우(`createdAt`: 최근 목록이 날짜 범위를 내림차순으로 훑는다. 자동 증가 ID 순서는 날짜 경계를 못 잡고, `nodeId` 순서는 단어 추가 순서와 다르며 중간 노드가 섞인다), 참조를 거슬러 찾아야 하는 경우(`relations`: 가리켜지는 쪽은 자신이 어디 쓰였는지 모른다). 갱신 비용이 있으므로 단순 조회 가속용은 두지 않는다. 최초 규약은 "Key Path 외 인덱스 금지, 관계는 전수 스캔"이었고 2026-07-23과 07-29에 두 단계로 완화됐다.
- **인덱스 보정을 `switch` 밖에 두는 이유**와 **버전 상수를 마지막에 저장하는 이유**는 [저장개발참고](../참고/저장개발참고.md#마이그레이션)에 있다. 세 번 재발한 사고다.
- `questions` Store는 v11에서 삭제됐다. 제출마다 쓰였지만 어디서도 읽히지 않았고 관계가 대상 단어를 전부 복사해 갖고 있어 중복이었다. `LEGACY_QUESTIONS_STORE` 상수는 마이그레이션과 백업 승격에만 남아 있다.

## 알려진 함정

- 트랜잭션 안에서 비-IDB Promise `await` 금지, 공유 인덱스의 `type` 필터, `advance`의 전제, HMR 버전 소모, 백업 직렬화: 전부 [저장개발참고](../참고/저장개발참고.md).
- `relations`의 `wordId`/`sentenceId`/`documentId` 인덱스는 한 유형만 담지 않는다. 유형별 필드는 `relation/types.ts`에서 확인한다.
