# 2026-07-23 설정 페이지와 DB 내보내기/가져오기

## 문제

Indexed DB는 브라우저가 저장 공간을 회수하면 통째로 날아간다. 사용자가 스스로 백업할 수단이 없었다.
전체 DB를 JSON으로 주고받는 것 자체는 단순하지만, 두 군데가 조용히 깨진다.

1. `JSON.stringify`는 `Date`를 문자열로 만든다. `hourDelta` 계열은 `beginDate`가 Key Path라 문자열로 굳으면
   `IDBKeyRange`를 쓰는 통계 조회가 아무 것도 못 찾는다. 예외도 안 난다.
2. 자동 증가 Store를 비우고 다시 채울 때 ID를 잃으면, `relations`가 가리키는 대상이 전부 어긋난다.

## 해결

`Date`는 `{ "$date": ISO 문자열 }`로 감싸 내보내고 가져올 때 되돌린다.
`JSON.stringify`의 replacer는 `Date.prototype.toJSON`이 이미 문자열로 바꾼 뒤의 값을 받으므로 쓸 수 없다.
값 트리를 직접 재귀 순회하는 `encodeValue`/`decodeValue`로 처리했다.

ID는 Key Path가 있는 Store에서 `put(value)`로 넣어 보존한다. 인라인 키가 값 안에 있고,
명시적 키로 `put`하면 자동 증가 키 생성기가 그 키 이상으로 올라가므로 이후 발급이 기존 항목과 겹치지 않는다.
Key Path가 없는 Store만 `put(value, key)`를 쓴다. 이 분기는 상수 표가 아니라 `store.keyPath`로 판단하므로
Store가 늘어도 백업 코드는 그대로다. `lib.dom`의 `keyPath` 타입에는 `null`이 없어 `=== null` 비교가 타입 오류라, `!store.keyPath`로 쓴다.

가져오기는 전체 Store를 범위로 하는 단일 `readwrite` 트랜잭션에서 비우고 다시 채운다. 실패하면 통째로 되돌아간다.
끝난 뒤에는 `queryClient.invalidateQueries()`를 필터 없이 불러 화면 전체를 무효화한다. 덮어쓴 뒤 남는 캐시는 전부 거짓말이다.

검증은 playwright로 실제 브라우저에서 했다. 단어 2개 저장 → 내보내기 → 단어 1개 추가 → 가져오기 순으로 돌려,
최근 단어와 총 보유가 백업 시점으로 돌아오고 `dayAcc`의 `beginDate`가 전부 `Date` 인스턴스로 복원되는 것을 확인했다.
